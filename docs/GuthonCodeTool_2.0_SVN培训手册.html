1. 30 分钟时间安排

0–2 分
开场：2.0 是 DATABASE + SVN 双模式；本次只演示 SVN 日常开发主线。
2–9 分
从零建项目：新增项目、选择 SVN、配置登录与范围、检出源码。
9–13 分
索引与 Nexus：看驾驶舱、谷神源码、完整索引、调用方和 AI 上下文。
13–18 分
修改与保存：打开虚拟源码、修改、保存、查看 SVN BASE 差异。
18–22 分
提交 SVN：选择范围、提交说明、revision 与交付回执。
22–25 分
冲突处理：三方合并、标记解决、重新审查。
25–28 分
团队能力：安装 guthon-team，说明规范、Linter、Hook 和 API 索引。
28–30 分
测试能力：用 guthon-testing 做开发/测试库只读排查与正式验证。

2. 演示前准备

演示策略：不要临场制造真实冲突。如果没有 SVN 提交授权，就在提交确认前停止，并展示已有回执截图或口头说明。

新增项目

操作：在 Guthon Nexus 点击“添加产品或项目” → 选择“项目” → 输入项目名称和稳定 ID → 源码来源选择“SVN”。

项目是一个独立版本快照，不需要先创建产品。稳定 ID 会进入明确的 workspaceKey，后续工具不会靠文件夹名猜工作区。

配置 SVN 登录与精确范围

操作：展开新项目，依次点击“设置工作区 SVN 登录” → “导入/粘贴 SVN checkout 配置” → “编辑 SVN 范围配置”。导入只解析 .sh/.bat 或粘贴文本，不执行脚本。

重点展示：公共 svn.url、去重后的精确 svn.scope、项目自己的系统/数据源映射。

2.0 只检出当前项目明确授权的范围，不会扫描其他项目或整个 SVN。

检出源码并自动生成索引

操作：再次设置登录以输入一次密码，然后点击“从 SVN 范围配置检出/更新”。核对预览范围后确认，并打开“输出 → GuthonCodeTool”查看授权、checkout/update、扫描、建索引的阶段进度。

成功标志：驾驶舱显示 working copy 和本地事实索引已就绪；无权限或不存在的单项会记录为跳过。

checkout 是唯一源码事实；context/index.db 只是可重建的检索索引，不是第二份源码。

4. 展示 Nexus 与索引能力（4 分钟）

工作区驾驶舱

查看索引状态、working copy、本地变更、跳过范围和最近一次 SVN 提交；状态行可直接进入操作。

谷神源码

按业务目录浏览 PAGE、过程函数、系统脚本、表和视图；PAGE 可按 GSS、JS、SQL、字段打开。

完整索引搜索

搜索源码名称、ID、函数、条件、赋值、异常、表读写和调用事实，不依赖树节点是否已展开。

导航与 AI 上下文

复制函数名或“包名.函数名”，查看调用方并跳到调用行；可复制精简/详细 AI 上下文。

现场动作：搜一个函数名，再搜一个业务表名；打开结果、查看调用方、复制精简 AI 上下文。强调索引只负责先缩小范围，实际修改前仍以 checkout 局部源码为准。

索引记录对象、片段、调用、表读写和逻辑事实，帮助我们回答“源码在哪、谁调用它、它读写什么”；索引可重建，不能当成运行结果证明。

生成的索引表速查

表名表注释一句话解释作用
gusen_source_record源码对象主表：保存对象身份、来源、版本、路径和索引状态，是其他事实表的关联入口。先确定“这份源码是谁、在哪里、当前是什么版本”。
gusen_source_fragment源码片段表：把 PAGE、过程函数和系统脚本拆成可定位片段，保存 JSON Pointer、语言和内容哈希。让 Nexus 和 AI 精确打开目标脚本或 PAGE 片段。
gusen_invoke_call静态调用边表：记录能够确定目标的函数调用，用于转到定义、查找引用和调用链分析。回答“谁明确调用了谁”。
gusen_dynamic_call动态调用线索表：记录无法静态确定目标的调用表达式及原因，供人工或 AI 继续核验。保留无法自动解析的调用线索，避免影响分析漏项。
gusen_page_relationPAGE 关系表：记录字段、组件、映射键等 PAGE 元素之间的结构关系与置信度。串起页面字段、组件和配置之间的关系。
gusen_bill_route单据路由表：关联数据源、单据类型和业务表，支持按单据快速定位源码入口。从单据类型或业务表快速找到对应源码入口。
gusen_data_access数据访问事实表：记录源码对业务表的读写操作、行号、作用域和有界证据。回答“哪段源码在什么位置读写了这张表”。
gusen_logic_fact逻辑事实表：记录条件、赋值、返回和异常等结构化事实，支持有界检索与原因解释。按业务条件、赋值或异常快速定位关键逻辑。
gusen_sync_state索引同步状态表：保存索引构建和增量刷新所需的轻量键值状态。记录索引构建与刷新过程需要的状态。

5. 修改文件、保存并提交 SVN（9 分钟）

从 Nexus 打开并修改

操作：从“谷神源码”打开预先选好的 PAGE/过程函数/系统脚本，增加一行安全注释，按 Ctrl+S（macOS 为 Cmd+S）。

展示行号槽、整行背景和概览标尺中的新增/修改标记。

虚拟编辑会校验对象身份、内容 hash、SVN BASE 和片段位置；同一文件的旧编辑会话不能覆盖新保存。

在 SCM 审查差异

操作：打开“源代码管理”，点击本地变更查看 SVN BASE ↔ 工作副本。演示单文件、多选文件、子系统组和全部范围入口。

SVN SCM 没有 Git 式暂存区。多选只决定本次提交范围，保存仍然只是本地 working copy 变化。

提交 SVN 并看回执

操作：检查远端变更 → 选择目标文件 → 填写可选提交说明 → “提交所选 Nexus 修改”。成功后展示 revision，再回驾驶舱打开最近提交回执。

跨多个 working copy 时可能产生多个 revision；回执会记录交付编号、revision、文件和时间。

SVN revision 只证明源码已提交 SVN。之后仍需回谷神平台完成最终提交，并做编译或业务流程验证。

三层边界：① Ctrl/Cmd+S = 本地保存；② SVN 提交 = revision/回执；③ 谷神平台最终提交 + 运行验证 = 功能实际生效证据。

6. 冲突处理（3 分钟）

检查远端变化
→
更新并合并
→
打开三方合并
→
保存正确结果
→
标记已解决
→
重新审查
  • 文本冲突：以 SVN 旧基线、本地修改、远端修改完成三方合并；保存物理工作结果后，显式“标记 SVN 冲突为已解决”。
  • 标记已解决不等于提交：它只执行 resolve 并刷新索引，之后还要重新查看差异再决定提交。
  • 属性冲突、树冲突、新增/删除范围不清：不要强制覆盖，联系负责人处理。

冲突时先把最终内容合正确，再标记解决；任何时候都不靠强制覆盖跳过审查。

7. 安装 guthon-team（3 分钟）

先确认 GitHub 私有仓库访问权限，再在固定目录克隆并安装到 GuthonCodeTool 的本地数据目录 var/：

git clone https://github.com/SidWuu/guthon-team.git cd guthon-team python3 tools/guthon_team.py install --workspace "/你的本地数据目录/var"

Windows 最后一行改为：

py -3 tools/guthon_team.py install --workspace "D:\你的本地数据目录\var"

规范与基线

统一安装 AGENTS、开发基线、模块规范和开发模式文档。

机器门禁

guthon-lint 检查受保护路径、Velocity、API、SQL 等规则。

Hook 与 pre-commit

在支持的 Agent 生命周期和 Git 提交前执行检查；按 ACTION_REQUIRED 完成信任。

API 事实

提供私有谷神 API 索引，防止 AI 按通用语言经验猜平台接口。

边界：安装成功不等于 Hook 已实际触发；Linter 通过也不等于 SVN 已提交、平台已发布或业务已验证。

8. 使用 guthon-testing Skill（2 分钟）

适用：谷神需求开发、开发库/测试库只读排查、修复后的数据库验证。它不用于生产库，也不会因为“测试一下”自动选择测试环境。

场景你可以这样提问Skill 会做什么
快速排查“使用 guthon-testing，排查测试库单号 XXX 为什么没有生成结果，只做分析。”解析当前 workspaceKey 和 test 目标，先看索引/表结构，再用只读 SELECT 查询；区分源码、数据库、平台版本和运行证据。
功能开发“使用 guthon-testing 开发这个谷神需求，源码走当前 SVN 工作区，完成后做定向验证。”按当前 provider 定位调用链；SVN 只通过受控会话修改；保存、SVN、平台和数据库证据分别报告。
正式验证“对已发布到测试环境的版本执行数据库测试闭环，按验收条件生成报告。”使用显式 full target、允许表和租户范围，核验平台版本/触发证据，生成计划、结果和报告。
数据库安全：只连接 dev/test 专用只读账号；只执行可确认安全的单条 SELECT；不做 DML、DDL、存储过程、锁、副作用函数或自动清理，不在对话中粘贴密码。

9. 30 秒收尾复述

建议原话：“从今天开始，SVN 项目统一从 Nexus 建工作区和精确范围，checkout 是源码事实，索引负责定位，虚拟文档负责安全修改，SCM 负责审查、更新、冲突和提交。SVN revision 后还要完成谷神平台最终提交和运行验证。团队规范用 guthon-team 安装，开发库和测试库排查用 guthon-testing，只读、分环境、留证据。”
