1. 安装

1.1 准备与下载

Windows 的 GuthonCodeSetup 下载清单与首次配置统一见 Windows 安装步骤第一章：一键安装配置。使用统一安装器的用户先完成该页向导；本章后续步骤用于 macOS 或手动安装。

下载前确认：

  • 手动安装需准备 VS Code 或 CodeBuddy，以及对应系统的应用；需要网页辅助时再准备 Chrome。
  • 使用 guthon-team 治理时，另需内网 Git 个人账号和团队 Marketplace 权限，详见第 3 章。
  • 使用 DATABASE 时准备对应数据源的只读账号；使用 SVN 时安装 SVN 1.10+，并取得账号和唯一根 checkout 配置。

SVN 首次没有地址配置时，可导入谷神平台提供的 svnCheckoutHere.sh 或 svnCheckoutHere.bat。Nexus 只解析配置，不执行脚本。

打开 GitHub Releases 或 Gitee Releases ，在同一个版本下载：

  • macOS M1 及后续型号：GuthonCodeTool-macos-arm64.zip
  • Windows x64：GuthonCodeTool-windows-x64.exe
  • VS Code 双模式扩展 Guthon Nexus：guthon-nexus-vscode.vsix
  • Chrome 扩展 Guthon Bridge：GuthonCodeTool-chrome.zip
  • 按需使用数据库开发/测试库验证时，下载 guthon-testing.zip 并按 Skill 说明安装。
  • 团队规范与开发门禁由独立的团队 Marketplace 分发 guthon-guard，不在 GuthonCodeTool Release 中。

macOS 可分别固定应用目录和本地数据目录；Windows 建议使用一个根目录，在其下放发行版 EXE 与 var 等运行数据。图文步骤见Windows 安装步骤。

text 
Windows 根目录：D:\Develop\GuthonWork\
├── GuthonCodeTool-windows-x64.exe
├── config\  # 设置工作空间后生成
└── var\     # 运行数据、源码、索引和 Workcopy

1.2 安装应用

macOS

  1. 确认 Mac 为 M1 或后续型号：可在“关于本机”中查看。
  2. 解压 GuthonCodeTool-macos-arm64.zip，得到一个 GuthonCodeTool 文件夹，其中包含同名启动文件与 _internal 运行库。把整个文件夹放入固定应用目录，不要只移动其中某个文件。
  3. 在 Nexus 里选择应用时，进入这个文件夹并选中同名 GuthonCodeTool 启动文件；选择器只接受文件。
  4. 如果启动文件没有执行权限，在终端执行：
bash
chmod +x "/你的应用目录/GuthonCodeTool/GuthonCodeTool"

若系统阻止运行，请先确认文件来自本项目 Release，再打开“系统设置 → 隐私与安全性”，对被阻止的 GuthonCodeTool 选择“仍要打开”。

Windows

  1. 把 GuthonCodeTool-windows-x64.exe 放到工作区根目录，例如 D:\Develop\GuthonWork\。
  2. 不要放进经常清理的“下载”或临时目录。
  3. 若 SmartScreen 拦截，先确认文件来自本项目 Release，再选择“更多信息 → 仍要运行”。

1.3 安装 Nexus

  1. 打开 VS Code 的“扩展”面板。
  2. 点击右上角 ...，选择“从 VSIX 安装...”。
  3. 选择 guthon-nexus-vscode.vsix。
  4. 安装后执行“Developer: Reload Window”或重新启动 VS Code。
  5. 确认左侧活动栏出现“Guthon Nexus”图标。

1.4 设置工作空间

  1. 点击 VS Code 左侧“Guthon Nexus”。
  2. 展开“工作区”，单击“设置工作空间”。
  3. 在确认框点击“执行”。
  4. 选择当前系统的 GuthonCodeTool 应用。
  5. 选择长期保存私有数据的本地数据目录；可以选择空目录。
  6. 等待输出面板显示 GuthonCodeTool 完成：setup。

设置后，入口变为“切换工作空间”。普通用户保持“发行模式”即可。需要源码开发或 Python 调试时，再查看运行模式说明。

在另一 IDE 中使用已有数据时，执行“设置/切换工作空间”，选择同一个包含 config/ 和 var/ 的本地数据目录。之后点击“刷新已有工作空间状态”即可读取新增项目与现有索引。

看到 setup 完成后，继续“添加产品或项目”。此时配置模板为空是正常状态；还需完成下一章的业务连接配置。

2. Nexus

先创建产品或项目，再选择一条源码路线。DATABASE 与 SVN 的配置、同步和编辑方式不同，不要混用操作。

2.1 创建产品或项目

  1. 在 Nexus 点击“添加产品或项目”。
  2. 选择产品或项目并填写名称；ID 会自动生成，建议改为易读且稳定的 ID。
  3. 选择源码来源：DATABASE 或 SVN。
  4. 向导创建工作区后，继续完成对应路线的配置。

产品和项目分别管理。后续命令或 MCP 配置需要工作区键时，从 Nexus 或配置中读取 products.<id> / projects.<id>，不要使用显示名称代替。配置项的完整职责见工作区配置参考。

选择 AI 任务目标

安装配套版本的 GuthonCodeTool 和 guthon-guard 后，CodeBuddy 可继续打开 var/。输入 /guthon-use 项目 项目名称 或 /guthon-use 产品 产品名称；若客户端显示命名空间，使用 /guthon-guard:guthon-use。Codex 可调用 $guthon-use 并说明目标。

核对返回的产品/项目名称后继续提需求。提交 Hook 可从需求中识别唯一注册名称；后续追问沿用当前对话目标。需要切换时再次明确选择；输入 list 列候选、status 查看当前目标、clear 清除绑定。只作为参考的其他项目不会成为写入目标。

出现重名、多个目标或目标冲突时，按候选明确选择后再修改。没有实际 Hook 时仍可解析目标，由 Agent 在当前对话中携带上下文；不要把解析成功当作已保存会话绑定。详细适用条件见任务目标解析。

2.2 DATABASE 路线

  1. 确认工作区显示“源码来源：DATABASE”。
  2. 在 datasource.yaml 填写只读数据库连接。
  3. 在 products.yaml 或 projects.yaml 填写 datasource、system_id 和 data_source_id。
  4. 保存配置，刷新 Nexus。
  5. 点击“同步工作区全部资料”。
  6. 等待源码、表结构、单据类型、系统脚本和视图全部完成。
  7. 后续只在 source/workcopy 开发；source/readonly 用于比较。

系统 ID 和数据源 ID 必须由配置管理人员提供。不要猜测，也不要复制其他项目的值。需要排查开发库或测试库时，在工作区执行“配置数据库只读目标”添加专用只读连接；快速查询只允许单条 SELECT。

查询开发库或测试库时，先核对工作区、环境和业务键，再执行连接探测与只读查询；数据库查询结果还需与平台结果分别核对。需要 AI 协助排查时，可按所用客户端的 Skill 安装方式安装同一 Release 的 guthon-testing.zip。

2.3 SVN 路线

  1. 确认工作区显示“源码来源：SVN”。
  2. 点击“设置工作区 SVN 登录”，先保存公共用户名。
  3. 点击“导入/粘贴 SVN checkout 配置”。选择公司提供的脚本，或粘贴唯一根地址/checkout 命令。
  4. 保存并关闭编辑器，让 Nexus 解析地址。脚本只用于提取配置，不会执行。
  5. 点击“编辑 SVN 地址配置”，确认只有一个 svn.url。
  6. 再次打开“设置工作区 SVN 登录”，输入一次密码。
  7. 点击“检出/更新完整 SVN 仓库”，核对根地址后执行。
  8. 大型仓库检出后会继续建立索引；输出会定期显示已扫描文件数。若操作中断，先检查工作区与索引状态，再决定是否重试。
  9. 完成后从“谷神源码”打开 PAGE、过程函数或系统脚本。

使用团队提供的根地址、系统与数据源映射，不自行猜测。用户名保存在配置中，密码由 SVN 凭据缓存或系统钥匙串管理。认证或权限失败时查看SVN 问题解答。

2.4 驾驶舱与工作区管理

  • “工作区驾驶舱”集中显示索引、同步状态、SVN working copy、本地变更和最近一次 SVN 提交。
  • 普通 SVN 本地修改单独显示为“有本地修改”，不计入健康问题；可点击本地变更行查看实时 SVN 状态。
  • 检查当前项目时，点击“检查此工作区环境”；“维护 → 检查本地环境”检查全部已配置工作区。结果按“需处理”“需留意”“通过”“本次未使用”显示，选择问题项可进入对应运行入口、配置或 Bridge 操作，也可查看完整报告；处理后重新检查。
  • 外部修改后若索引显示“待恢复”，暂时性读取故障会自动重试，解析或身份错误需先按输出修复；仍未恢复时，点击驾驶舱的索引行，或执行“重试 SVN 索引失败文件”。重开 IDE 后仍可从该入口处理已记录的失败文件。
  • 切换 DATABASE/SVN 只影响当前工作区，不影响其他产品或项目。
  • 删除工作区时，右键 PRD/PRJ 选择“删除产品或项目”，先核对预览范围，再确认移入废纸篓。

查找源码、调用、条件、赋值、异常或表读写事实：

  1. 在目标项目选择“搜索工作区完整索引”，在搜索窗口输入关键词；编辑器中已选中的文字会带入搜索框。
  2. 结果出现后选择对象并按回车打开源码；需要 AI 上下文时，点击该结果右侧的精简、详细或导出按钮。“快速打开 SVN 源码”使用相同的搜索方式，只列出源码对象。
  3. 提示“结果已截断”时，补充对象名称、编码或更具体的关键词缩小范围。没有结果时核对工作区和索引；搜索失败可在原窗口按回车重试。

3. guthon-team

3.1 安装治理插件

团队治理分成两层：本机安装 Marketplace、guthon-guard 插件和生命周期 Hook；工作区安装 AGENTS.md、规范、API 索引、Linter 与可选的 Git pre-commit。两层需要分别安装和检查。当前流程不需要克隆完整的 guthon-team 仓库，也不要求 GuthonCodeTool 的 var/ 必须由本地 Git 管理。

第一次连接内网 Git

  1. 连接公司内网或 VPN，确认终端中可以运行 git --version 和 python3 --version。
  2. 查看本机是否已有 SSH 公钥。macOS/Linux 执行 ls ~/.ssh/*.pub；Windows PowerShell 执行 Get-ChildItem $env:USERPROFILE\.ssh\*.pub。
  3. 如果没有公钥，在终端执行 ssh-keygen -t ed25519 并按提示保存。如果默认文件已经存在，不要覆盖仍在使用的密钥。
  4. 复制对应 .pub 文件的完整内容。macOS/Linux 可执行 cat ~/.ssh/id_ed25519.pub；Windows PowerShell 可执行 Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub。实际文件名不同时按真实路径调整。没有 .pub 后缀的私钥必须只保存在本机，不能上传或发送。
  5. 使用自己的账号登录团队内部发布的 <内网 Git Web 地址>，进入“用户设置 → SSH / GPG 公钥”，点击“增加密钥”，填写设备标题并粘贴公钥。
  6. 执行下面的只读命令。首次出现主机指纹时，先与团队公布的指纹核对；无法核对时不要直接确认。
bash
git ls-remote "<团队 Marketplace SSH 地址>" HEAD

看到一行提交哈希和 HEAD 表示连接成功。若提示 Permission denied (publickey)，先检查公钥是否添加到了当前登录的个人账号；公钥正确但仍无权访问时，再联系管理员检查账号或仓库权限。

Codex 安装

  1. 在终端添加团队 Marketplace。添加市场与安装插件是两个独立步骤，两条命令都要执行：
bash
codex plugin marketplace add "<团队 Marketplace SSH 地址>" --ref main
  1. 安装团队治理插件：
bash
codex plugin add guthon-guard@guthon-team
  1. 如果提示已存在同名 Marketplace，先确认现有来源是否正确。只有确认是旧来源或错误来源时，才移除后重新添加；不要直接覆盖未知配置。
bash
codex plugin marketplace remove guthon-team
codex plugin marketplace add "<团队 Marketplace SSH 地址>" --ref main
codex plugin add guthon-guard@guthon-team

CodeBuddy 安装

在 CodeBuddy 的对话输入框中依次执行；这些是 CodeBuddy 命令，不是在系统终端中执行：

text
/plugin marketplace add <团队 Marketplace SSH 地址>
/plugin install guthon-guard@guthon-team --scope user
/reload-plugins

如果只希望当前项目使用，可将 --scope user 改为 --scope project。市场添加成功但插件未安装时，规范和 Hook 仍不会生效。

3.2 信任 Hook

  1. 重新打开 Codex 或 CodeBuddy，在输入框中输入 /hooks。
  2. 找到 guthon-guard 提供的 Hook，展开查看实际命令和插件来源。
  3. 确认来源属于团队 Marketplace 后，将该 Hook 设为信任。
  4. 关闭当前任务，再从目标 var/ 或业务子目录打开新任务，才能触发受信任的 SessionStart。

插件已安装、插件已启用、Hook 已信任、Hook 已实际执行是四个不同状态。必须完成后续工作区状态检查，不能只看到插件名称就认为治理已经生效。

3.3 初始化并检查

  1. 确认 GuthonCodeTool 已设置本地数据目录，并且其中已经存在 var/。不要仅为安装治理而执行 git init。
  2. 从 <本地数据目录>/var 或其任意业务子目录打开一个新的 Codex 或 CodeBuddy 任务，例如某个 var/workspace/PRD ... 目录。
  3. 等待 SessionStart 完成。受信任的 Hook 会根据 GuthonCodeTool 标识向上定位 var/ 并进行幂等初始化；普通目录和普通 Git 仓库不会被写入 Guthon 治理文件。

自动初始化总会安装项目 AGENTS.md 和团队规范、.guthon 配置与版本锁、API 索引、工作区本地 Linter、tools/guthon-lint。只有 var/ 本身是 Git 根时，才额外安装 Git pre-commit 并设置 core.hooksPath=.githooks。

检查治理状态

  1. 在新任务中输入以下提示词：
text
使用 $guthon-bootstrap 检查当前工作区治理状态，只查看，不修改

预期看到 STATUS state=ready。当前 Codex 使用 Skill，不要输入 /guthon-guard:guthon-init；该命令不会在 Codex 注册。CodeBuddy 可在输入框执行 /guthon-guard:guthon-init status。

  1. 如果 var/ 使用 Git，在 var/ 或其子目录的终端检查 Git Hook；非 Git 工作区跳过本步：
bash
git config --get core.hooksPath

预期输出 .githooks。如果输出其他路径，不要覆盖；这说明工作区已经使用其他 Hook，需要由维护人员确认整合方式。

  1. Git 工作区可从实际 PRD 或 PRJ 工作目录执行变更范围检查：
bash
tools/guthon-lint --changed --write-target

非 Git 工作区不能使用 --changed 或 --staged 自动取得文件列表，应把本次修改的文件逐个传入，例如 tools/guthon-lint "workspace/示例项目/目标文件.vm"。

  1. 如果初始化更新了 AGENTS.md，再打开一次新任务，确保 Codex 从启动阶段加载最新版规则。

3.4 手动与无 Hook 安装

Hook 未信任、宿主不支持 SessionStart 或自动识别失败时，在目标 var/ 工作区或其子目录打开 Codex，先预览计划：

text
使用 $guthon-bootstrap 初始化当前 Guthon 工作区，先执行 dry-run，只展示计划

确认目标 var/ 和文件清单正确、没有冲突后，再输入：

text
使用 $guthon-bootstrap 初始化当前 Guthon 工作区

只安装 AGENTS、规范、API 索引和 Linter，不配置 Git pre-commit 时，在请求中增加 --no-git-hook；非 Git 工作区必须使用这一模式。遇到 CONFLICT 时先逐个检查冲突文件，不要直接使用 --force；确需替换时，安装器会先将旧文件备份到 .guthon/backups/bootstrap-<时间戳>/。

没有 Marketplace 或 Hook 的宿主，应使用团队随 guthon-guard 发布物提供的自包含安装器，不要为此克隆完整团队仓库。安装器的 --workspace 必须明确指向 var/；如果它位于 Git 仓库中，则还必须是该 Git 根：

bash
python3 guthon-guard/scripts/guthon_workspace.py init --workspace "/本地数据目录/var"

# 只安装基础能力，不配置 Git pre-commit
python3 guthon-guard/scripts/guthon_workspace.py init --workspace "/本地数据目录/var" --no-git-hook

安装后重新打开任务并检查状态。规范、Linter、Hook 与 Git 检查的职责见团队治理说明；安装冲突或 Hook 未运行时查团队规范问题解答。

4. Bridge 网页辅助

需要从谷神网页拉取对象、复制字段、跳转源码或改善管理列表滚动时，使用 Chrome Bridge。

4.1 安装 Chrome 扩展

  1. 使用 Windows 一键安装器时，选择向导提供的扩展目录。手动安装时，解压同一 Release 的 GuthonCodeTool-chrome.zip 到固定目录。
  2. 打开 chrome://extensions，开启“开发者模式”，点击“加载已解压的扩展程序”，选择直接包含 manifest.json 的 extension 目录。
  3. 将 Guthon Bridge 固定到 Chrome 工具栏，刷新已经打开的谷神平台页面。
  4. 额外平台地址未获支持时，按团队提供的规则修改独立的 host-settings.js，重新加载扩展后刷新页面。

4.2 启动与配对

  1. 在 Nexus 中点击“启动 Guthon Bridge”，保持 IDE 窗口打开。
  2. 在启动通知中点击“复制配对令牌”。
  3. 打开 Chrome 的 Guthon Bridge 弹窗，展开配对设置，粘贴令牌，点击“保存并连接”。两端端口须一致，默认 17361。
  4. 打开目标谷神页面，从 Bridge 弹窗确认已连接。需要选择工作区时，核对产品或项目后再操作。

令牌只用于本机配对，不要发送给他人。配对失败请查Bridge 问题解答。

4.3 使用网页辅助

  • DATABASE 拉取：打开目标页面、过程函数或系统脚本，在弹窗或页面按钮中选择对应拉取操作，完成后在 Nexus 查看 Workcopy。SVN 工作区的源码编辑从 Nexus“谷神源码”进入。
  • 平台 → Nexus：选中 PAGE 或过程函数页签，点击“在 Nexus 中打开…”或“在 Nexus 定位”，选择正确 SVN 工作区与候选源码。
  • Nexus → 平台：在源码树右键 PAGE 或过程函数，选择“在谷神平台定位源码”，按提示选择已打开的平台页签。
  • 复制与粘贴字段：在模块开发页打开复制模式，勾选需要的字段（含灰色标识的隐藏字段），再选择目标组件粘贴。检查字段与继承脚本结果后，手动保存平台页面。
  • 管理列表：数据表管理主列表、表字段列表、开发日志和增量发布保留顶部按钮；模块参数、系统脚本的查询区和左侧树保留可见。直接滚动列表，小屏幕可用横向滚动条访问操作列。

字段辅助和列表滚动可在扩展加载后直接使用；源码拉取及双向定位还需本地服务与相应工作区。长任务结果不明时，先在弹窗点击“查询待恢复任务”，确认原结果后再决定是否重拉。

5. SVN MCP（按需）

需要 AI 客户端查询或修改本地 SVN 源码时再配置本章。仅在 Nexus 中手工编辑的用户可以跳过。

5.1 准备索引

  1. 先按 2.3 节在 Nexus 完成 SVN 工作区检出与索引，确认驾驶舱显示索引就绪。
  2. 记下应用启动文件、本地数据目录的绝对路径，以及目标 workspaceKey。
  3. 确认所用 AI 客户端支持本地 stdio MCP。

5.2 配置客户端

在客户端新增名为 guthon-svn 的本地服务。命令选择应用启动文件，参数按顺序分别填写 mcp、--stdio、--home、本地数据目录。只允许查询时，再增加 --read-only。

Codex 配置示例

在个人 ~/.codex/config.toml 中合并以下服务配置，保留其他设置。把两处示例路径换为本机绝对路径；Windows 的命令指向 EXE。

toml
[mcp_servers."guthon-svn"]
command = "/应用目录/GuthonCodeTool/GuthonCodeTool"
args = ["mcp", "--stdio", "--home", "/本地数据目录"]

CodeBuddy 配置示例

在 CodeBuddy 的 MCP 设置中添加下列服务；已有配置只合并 mcpServers 内的条目。Windows JSON 路径使用正斜杠，或将反斜杠正确转义。

json
{
  "mcpServers": {
    "guthon-svn": {
      "type": "stdio",
      "command": "/应用目录/GuthonCodeTool/GuthonCodeTool",
      "args": ["mcp", "--stdio", "--home", "/本地数据目录"]
    }
  }
}

ZCode 可在“设置 → MCP 服务器 → 新建”中选择 stdio，按同一命令与参数填写。其他客户端以其 MCP 配置入口为准。

保存后重启或重载客户端，确认服务已连接。完整工具与协议参数见SVN MCP 参考；连接失败查MCP 问题解答。

5.3 查询源码

向 AI 说明工作区、对象和任务，例如：

text
请使用 guthon-svn MCP，在 workspaceKey=products.<id> 中查询目标 PAGE 或过程函数。
先检查索引与对象身份，再读取源码，给出相关位置和证据；本次只读，不修改或提交。

将示例工作区和对象换成真实目标。出现重名候选时，按路径与工作副本核对；索引过期或不完整时，先按客户端提示刷新对应工作区。

5.4 修改 PAGE 脚本或 SQL

明确提出要改的 PAGE、脚本或 SQL 以及预期行为。要求 AI 先读取现状、预览差异，再修改已授权的本地源码；完成后在 Nexus SCM 审阅差异。MCP 不提交 SVN，也不替代平台测试。

5.5 修改过程函数

提供完整包名、函数名和目标工作区。确认候选与差异后再修改。若提示写入结果未知，先查询原操作记录，不重复发起同一次修改；处理方法见MCP 写入问题。

5.6 用 AI 调整 PAGE 设计

让 AI 调整已授权 PAGE 的字段、按钮、事件、数据源或布局时，明确页面、所属区域和预期行为。已有页面无需先在平台填写事件占位注释；整页新建、复制、删除按下一节操作；菜单仍按平台流程准备。

  1. 更新后重启 MCP，确认存在结构编辑工具；没有时让 AI 核对当前 CLI 是否支持同一受控入口。
  2. 让 AI 先查询设计能力并检查当前页面，再按平台配置准备候选、补齐绑定并预览差异。删除或移动前核对依赖关系。
  3. 检查后保存本地候选；在平台核验字段显示、后续属性编辑、按钮点击、查询联动和权限，确认保存重开后成员数量及配置正确，随后按团队流程提交或发布。

单字段新增和同集合拷贝仍可使用原入口；图形面板的常用属性编辑以面板显示的范围为准。支持范围和接口参数见结构编辑参考。

5.7 用 AI 新建、复制或删除整个页面

  1. 更新工具和 Bridge Chrome 扩展，重启 MCP。登录谷神平台，选择目标系统并展开模块目录，在 Bridge 弹窗绑定目标工作区。
  2. 向 AI 说明目标模块、页面类型、名称和别名；复制时提供来源页面，删除时明确精确目标。AI 应先读取当前平台上下文和页面版本，再展示操作预览。
  3. 核对预览的平台、来源、目标和操作范围后执行。此处会直接改变平台页面；源码结构编辑则仍保存到本地。
  4. 若结果等待中或未知，让 AI 查询原操作记录，先在平台核对，不能换请求重复创建或删除。成功后刷新平台目录，再按现有同步流程更新本地源码和索引。

整页操作不会自动提交 SVN 或发布。详细参数和状态含义见PAGE 生命周期参考。

6. 日常工作流

每次先确认 Nexus 中的产品或项目，以及其 DATABASE / SVN 源码来源。

6.1 DATABASE 工作流

  1. 选择目标工作区，按需执行“同步工作区全部资料”，等待五个阶段全部成功；只处理一个对象时也可从 Bridge 拉取。
  2. 在 source/workcopy 修改源码，保留 source/readonly 作为比较基线。
  3. 完成后点击“检查或打包 Workcopy”，检查 diff.md。
  4. 将确认后的内容回填谷神平台，完成平台测试与提交。

再次拉取提示差异时，先查看并决定保留内容；不要直接覆盖。需要恢复旧 Workcopy 时，查看Workcopy 问题解答。

6.2 SVN 工作流

更新与开发

  1. 需要获取远端修改时，点击“更新全部远程变更”，先查看文件列表与差异，再确认更新。取消时保留列表，不执行更新。
  2. 从“谷神源码”打开 PAGE、过程函数、系统脚本或视图 SQL。表格定义与视图字段保持只读。
  3. 按 Ctrl+S（macOS 为 Cmd+S）保存到本地工作副本。
  4. 在源代码管理中打开文件，检查“SVN BASE ↔ 工作副本”差异。

更新后若“输出 → Guthon Nexus SVN”出现“冲突阻断”，表示这些文件存在未解决的 SVN 冲突：其余文件已按本次更新建立索引，被阻断文件保留上一次索引内容且不再自动重试。按下方“提交与冲突”逐个完成三方合并并标记已解决，再重建索引。

“刷新 Guthon Nexus”只刷新界面；“刷新 SVN 变更”查看本地状态；“更新全部远程变更”访问服务器。按需要选择入口，避免重复执行正在进行的任务。

项目继承脚本会显示展开内容，并用背景区分产品段与项目段。只改项目段时保留继承；改动产品段时会把完整内容写入项目源码。保存前核对来源，保存后检查实际差异。

本地查看与图形化调整 PAGE

字段、按钮和代码编辑可以直接使用；只有查看原版页面布局时才需要准备平台资源。此功能用于 SVN 工作区的 JSON PAGE。

打开页面并编辑字段、按钮和代码
  1. 在“谷神源码”树单击 PAGE，或在源代码管理中对 JSON PAGE 文件点击“在 Nexus 中编辑”，打开本地页面编辑器，不再选择页面分块。双击源码树中的 PAGE 或点击展开箭头，可继续使用原有事件与字段节点；右键“本地页面编辑与预览”也可打开。
  2. 在左侧选择区域、字段或按钮。中间清单会定位到对应项；点击整行字段或区域上方的按钮，可在右侧修改已有属性，或使用“上移”“下移”调整顺序。
  3. 需要编辑事件或 SQL 时，从左侧树或右侧事件按钮打开代码。它与源码树使用同一代码标签，项目继承脚本也按相同规则展开。
  4. 先在代码标签按 Ctrl/Cmd+S 保存代码，再点击页面顶部“保存到本地”保存字段、按钮等调整。页面支持撤销、重做和“比较改动”；保存完成后，从源代码管理检查 SVN 差异。

本地编辑器默认只打开字段与代码管理；需要查看布局时，再点击“原版设计视图”。保存排序前先保存代码。排序保存会关闭此 PAGE 的已保存代码标签，需要时从页面重新打开事件。保存到本地不会自动同步、编译或提交谷神平台。

准备并打开原版设计视图
  1. 在页面顶部“谷神”按钮组点击“平台资源”，选择“连接谷神平台并准备资源”，填写当前工作区的平台 /guthon/index.html 地址。
  2. 等待资源准备。通知和“输出 → Guthon Nexus SVN”显示下载进度；完成后提示资源已校验，并自动打开原版设计视图。
  3. 后续点击“原版设计视图”查看布局；点击原版视图中的“草稿与代码”返回字段与代码管理。两处调整均需保存到本地。
  4. 平台升级时，通过“平台资源 → 检查平台资源更新”检查并选择是否切换；需要回退时选择“选择已缓存版本 / 回退”。已有资源包可用“导入已有本地资源包”。

准备资源与浏览器登录的关系见登录与下载问题；下载没有进度或失败时，查看进度与失败处理。字段清单用于管理，不表示实际页面布局。

比较修改并到平台验收
  1. 在本地页面点击“比较改动”，选择“与 SVN 基线比较”查看 SVN BASE 到本地已保存源码的差异，或选择“与本地保存版本比较”查看窗口未保存调整。中间显示只读的修改前后内容，点击“返回当前草稿”继续编辑。
  2. 左侧树中，M 使用与 Nexus 源码树相同的 SVN 修改色，● 使用蓝色标识窗口未保存调整；两种标记可同时存在。展开“SVN 已删除项”可查看删除内容。保存后 ● 清除，M 保留至差异消除；原版视图中的“查看本地保存版本”仅切换本地基线布局。
  3. 外部源码更新后，结构和目标身份保持一致时，窗口会载入文件版本并保留互不冲突的属性或脚本调整；双方已改成相同值的调整不再显示为未保存。
  4. 出现“外部修改冲突”时，核对原先加载的值、当前文件值和窗口草稿值，逐项选择“保留窗口修改”或“采用文件修改”。全部选择完成后会重新核对文件并返回草稿，检查结果后再“保存到本地”；若文件又发生变化，按新的冲突重新选择。
  5. 页面结构、属性类型或目标身份变化，代码有未保存输入，或原版设置对话框尚未确认时，按提示保留输入并导出草稿，再重新载入。原版设置输入需先自行保留并关闭对话框；旧草稿和冲突报告可从导出内容核对。
  6. 需要与在线平台对照时，将窗口宽度设为平台页面内容区宽度，确认浏览器已登录对应平台，再点击“去平台对照”。
  7. 按既有流程完成平台同步、编译与实际页面验证。同一页面版本、内容区宽度和缩放下的效果仍需核验。

保存结果不明确或发生冲突时，先“导出草稿”保留输入；提示保存待核对时使用“恢复保存检查”。完整支持范围、缓存位置和验证边界见本地页面编辑与预览说明。

常用定位与辅助

  • 使用“搜索工作区完整索引”查找对象；已知编码时可在命令面板选择“按页面编码定位本地 PAGE”或“按包名和函数名定位本地过程函数”。
  • 过程函数调用使用 Cmd/Ctrl 点击或“转到定义”。在虚拟 GSS 中输入 @ 可补全本地函数；PAGE 字段集合可补全 selectCodefieldId。
  • 右键源码对象选择“预览源码影响”或“浏览影响证据”，再打开具体源码核对。静态提示不能代替平台验证。
  • 需要交给 AI 分析时，右键“导出 AI 上下文文件”，选择摘要或所需内容，使用返回的文件路径。

提交与冲突

  1. 选择全部、业务组或所选文件范围，执行对应提交入口。
  2. 核对提交文件、说明和返回的 SVN revision。保存到本地与提交到 SVN 是两个步骤。
  3. 发生文本冲突时，点击“打开 SVN 三方合并”，保存合并结果，再“标记 SVN 冲突为已解决”。
  4. 属性、树冲突或无法判断的新增删除，保留现场并联系负责人；不要强制标记解决。

目标文件成功提交并取得 revision，表示源码交付完成；平台编译、发布与业务结果按项目流程另行验证。

6.3 更新工作流

更新 GuthonCodeTool、Nexus 与 Bridge

  1. 先保存编辑，等待同步、SVN 和 Bridge 任务完成。
  2. 在“运行模式 → 检查更新”核对当前组件、候选版本与更新来源。
  3. 确认更新并等待安装完成，按提示重新加载使用 Nexus 的 IDE 窗口。
  4. Chrome 按提示使用固定扩展目录；保存平台编辑后刷新页面，让网页增强生效。
  5. 更新后执行“检查本地环境”，再试一次实际使用的功能。应用异常时可选择“回退到上一版本”；其他组件的回退范围见 QA。

数据目录和本地修改应保留。独立配置的 MCP 应用路径和 Skill 按需要分别更新。

更新团队治理

在所用客户端的插件市场更新 guthon-team 与 guthon-guard，重载插件后从目标 var/ 打开新任务，按 3.3 节检查治理状态。规范冲突时保留原文件并查看提示，不直接覆盖。

7. 迁移与使用检查

7.1 系统支持

macOS 使用 Apple Silicon（M1 及后续型号）目录包；Windows 使用 x64 EXE。Nexus 的工作区和编辑操作基本相同。应用无法启动、路径或凭据问题统一查问题解决中心。

7.2 迁移与删除

迁移电脑

  1. 保存所有编辑，停止 Bridge、同步和 SVN 操作。
  2. 完整复制本地数据目录，保留配置、Workcopy、SVN 工作副本及本地修改。
  3. 在新电脑安装对应系统的应用与扩展，执行“设置工作空间”并选择复制后的数据目录。
  4. 重新配置新系统的数据库与 SVN 凭据，运行环境检查并核对目标工作区。

删除产品或项目

  1. 右键目标 PRD/PRJ，选择“删除产品或项目”。
  2. 检查预览中的配置、专属目录和 SVN checkout；项目文档有保留需要时先备份。
  3. 确认后执行删除，目标目录进入系统废纸篓。检查其他工作区仍在。

整理本地索引空间

  1. 在目标工作区完成保存，等待正在执行的索引操作结束。确认使用的是当前 GuthonCodeTool 后端。
  2. 用当前后端入口执行 index-compact --home <本地数据目录> --workspace <workspaceKey>。预期返回空间预览，尚未执行整理。
  3. 确认目标和可用磁盘空间后，在同一命令末尾增加 --apply。等待返回成功，并比较结果中的整理前后大小；索引不一定每次都能缩小。
  4. 重新搜索一个已知对象，确认仍能打开源码。整理不会替代源码更新，也不会清理 Git 历史或 SVN 缓存。

适用于 DATABASE 和 SVN 的已存在本地索引。命令参数、正文格式和限制见索引存储与空间整理。

7.3 遇到问题

在问题解决中心按系统、源码模式或错误原文搜索。先查看“输出 → GuthonCodeTool / Guthon Bridge”的首条失败信息，再按对应问答处理；需要求助时使用页面提供的脱敏模板。

7.4 首次使用检查

  • 应用可启动，Nexus 可读取所选本地数据目录，环境检查没有阻断错误。
  • 实际要用的产品或项目已配置；DATABASE 同步成功，或 SVN 检出与索引就绪。无需为检查而创建另一种模式的样例项目。
  • 需要团队治理时，目标 var/ 治理状态为 ready；需要 Hook 时已在新任务中验证其运行。
  • 需要 Bridge 时，扩展已加载、服务已配对，实际页面能使用对应能力。
  • 需要 MCP 时，客户端已连接，能以明确工作区查询目标源码。
