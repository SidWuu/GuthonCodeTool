macOS M1 及后续型号与 Windows 的 Nexus 操作相同。GuthonCodeTool 本身不要求克隆源码、安装 Python、安装 Node.js 或创建虚拟环境。

1. 安装

1.1 准备与下载

Windows 的 GuthonCodeSetup 下载清单与首次配置统一见 Windows 安装步骤第一章：一键安装配置。使用统一安装器的用户先完成该页向导；本章后续步骤用于 macOS 或手动安装。

下载前确认：

  • 手动安装需准备 VS Code 或 CodeBuddy，以及对应系统的应用；需要网页辅助时再准备 Chrome。
  • 使用 guthon-team 治理时，另需内网 Git 个人账号和团队 Marketplace 权限，详见第 3 章。
  • 接入源码时准备谷神平台账号；使用数据库诊断时另准备明确的数据库目标和只读连接。

打开 GitHub Releases 或 Gitee Releases ，在同一个版本下载：

  • macOS M1 及后续型号：单文件 GuthonCodeTool
  • Windows x64：GuthonCodeTool-windows-x64.exe
  • VS Code 双模式扩展 Guthon Nexus：guthon-nexus-vscode.vsix
  • Chrome 扩展 Guthon Bridge：GuthonCodeTool-chrome.zip
  • 按需使用数据库开发/测试库验证时，下载 guthon-testing.zip 并按 Skill 说明安装。
  • 团队规范与开发门禁由独立的团队 Marketplace 分发 guthon-guard，不在 GuthonCodeTool Release 中。

将应用和 VSIX 放在同一个上级目录，在其中自建开发目录。首次就在 VS Code 打开开发目录。初始化后，配置保存在其上一级。图文步骤见Windows 安装步骤。

text 
GuthonWork/
├── GuthonCodeTool              # macOS 单文件，Windows 放 GuthonCodeTool-windows-x64.exe
├── guthon-nexus-vscode.vsix     # 从 VSIX 安装时选择
├── config/                     # 初始化后生成
└── 研发源码/                    # 第一次就用 VS Code 打开这里，也可命名为 var

1.2 安装应用

macOS

  1. 确认 Mac 为 M1 或后续型号：可在“关于本机”中查看。
  2. 将下载的单文件 GuthonCodeTool 放到开发目录的上一级。
  3. 在当前开发目录点击“初始化此文件夹”，Nexus 会在上一级自动识别 GuthonCodeTool。
  4. 如果启动文件没有执行权限，在终端执行：
bash
chmod +x "/你的数据目录/GuthonCodeTool"

若系统阻止运行，请先确认文件来自本项目 Release，再打开“系统设置 → 隐私与安全性”，对被阻止的 GuthonCodeTool 选择“仍要打开”。

Windows

  1. 把 GuthonCodeTool-windows-x64.exe 放到工作区根目录，例如 D:\Develop\GuthonWork\。
  2. 不要放进经常清理的“下载”或临时目录。
  3. 若 SmartScreen 拦截，先确认文件来自本项目 Release，再选择“更多信息 → 仍要运行”。

1.3 安装 Nexus

  1. 打开 VS Code 的“扩展”面板。
  2. 点击右上角 ...，选择“从 VSIX 安装...”。
  3. 选择 guthon-nexus-vscode.vsix。
  4. 安装后执行“Developer: Reload Window”或重新启动 VS Code。
  5. 确认左侧活动栏出现“Guthon Nexus”图标。
  6. 使用旧版 Nexus 的用户可先从 VSIX 安装同版新扩展，再选用单文件后端。

1.4 设置工作空间

首次接入 API 时，在放置后端的上一级数据目录下，新建一个开发目录。目录可叫 var，也可用自己的名称。用 VS Code 或 CodeBuddy 直接打开这个开发目录，在 Nexus 点击“初始化此文件夹”。初始化需要 Git，会把当前打开的目录建为 Git 根，并在它的上一级生成配置。

  1. 已连接的窗口仍可用“设置/切换工作空间”更换目录。“刷新当前状态”会重新读取已连接的目录。
  2. 从当前开发目录初始化时，卡片会列出开发目录及其上一级数据目录。接入已有 API 空间时，通过“连接已有数据目录”选择包含 config/ 的上一级目录。每个数据目录绑定一个开发根，已有绑定继续使用原路径。
  3. 点击“初始化此文件夹”后，Nexus 自动检查上一级的 GuthonCodeTool 或 Windows EXE，检查通过即进入初始化确认。上一级找不到可用的运行文件时，会让你选择后端所在的运行目录，数据仍写入开发目录的上一级。已有工作区可从“项目总览 → … → 工具设置”手动更换运行入口。初始化取消时保留原设置，成功后才保存当前工作区的关联。
  4. 确认信任当前目录并连接公司网络。按提示输入团队提供的 Git 克隆地址。首次访问按内网 Git 接入步骤开通权限。等待 Nexus 显示“工作区已初始化，团队规则和开发门禁已同步”。此时即可在根目录查看 AGENTS.md、rules/ 和 tools/guthon-lint。
  5. 初始化后留在当前开发目录，点击“立即添加”，或在“项目总览”点击“添加项目”。日常继续打开这个目录。

切换到另一个文件夹时，Nexus 会核对当前文件夹与全局数据目录的归属。当前窗口若明确连接另一个位置的数据目录，该连接保存在这个窗口的工作区设置中。

普通用户使用“发行模式”；需要源码开发或 Python 调试时，按运行模式说明选择对应入口。在另一 IDE 中接入同一 API 数据时，选择相同的本地数据目录并读取已有工作区即可。

新配置的工作区列表为空是正常状态。继续添加项目，选择其同步方式并完成连接设置。全新空间会创建 rules/；已初始化空间缺少该目录时，重跑 setup 保留其原 docs/ 规范布局。

2. Nexus

2.1 添加项目

  1. 用 VS Code 或 CodeBuddy 打开已初始化的开发目录。在 Nexus 的“项目总览”点击“添加项目”，输入项目名称。
  2. 选择 API、SVN 或 DATABASE 后登记项目。项目目录会创建在当前开发根的 workspace/ 下，原有项目继续使用各自的目录。新项目推荐 API。取消选择时不会创建项目。旧版 API 后端仅显示 API，仍需确认选择；采用旧版分类登记的后端还会询问项目或产品类型。
  3. 点击新项目行。在 API 项目卡片配置平台地址并登录，按需输入验证码，然后选择全部或指定子系统并更新源码。SVN 和 DATABASE 项目也在当前项目卡片填写连接地址、用户名和密码。登录后选择同步范围，再手动点击“更新源码”。SVN 和 DATABASE 的操作见当前项目卡片。

API 拉取后可在项目的 checkout 编辑源码。Codex 可打开项目目录并读取开发根的 AGENTS.md。详细能力与范围见API 接入参考。

项目设置

三种同步方式均从“当前项目 → … → 项目设置”展开原生子菜单，可直接选择“配置源码连接”“同步范围”或“查看项目配置”。API 项目还可配置数据库查询与验证及官方参考资料。首次选择范围后，点击“更新源码”开始拉取并建立索引；取消选择不会保存。新目录使用 guthon.json。旧配置不自动转换。已有 SVN/DATABASE 项目可在总览选中后按当前模式操作。需要升级配置时，先预览并核对项目，再按配置参考离线执行。配置升级后重新打开同一数据目录，检查项目名称、同步方式和路径。

在当前项目卡片，SVN 模式填写授权仓库地址、用户名和密码。DATABASE 模式填写 MySQL 或 PostgreSQL 地址、只读用户名和密码。点击“登录”，验证成功后卡片显示“同步范围”和“更新源码”。已有连接可从“项目设置 → 配置源码连接”修改。新数据目录已准备 DATABASE 默认字段映射。连接标准谷神主库后，勾选子系统并保存范围。使用自定义主库表结构时，在“项目设置 → 查看项目配置”中核对字段映射。SVN 在“同步范围”按数据源名称勾选。关联子系统随数据源一起签出，例如“贸易系统”包括国内贸易与国际贸易。“公共源码”和“开发建议”可单独勾选。保存后点击“更新源码”。

选择 AI 任务目标

在 Nexus 按名称或稳定 key 切换当前窗口工作区，用于项目卡片、源码树和源码管理。AI 源码任务另外按名称或 key 明确目标，候选不唯一时先选择；Nexus 的窗口选择不自动替代 AI 会话绑定。CodeBuddy 保持打开 var 根，Codex 可打开具体工作区目录。

API 项目范围

选择子系统后，会自动纳入它们关联的数据源及其中的共享过程、表和视图；不再单独选择共享数据源。

2.2 工作区管理

先在“项目总览”选中项目，再从“当前项目 → …”打开项目目录、查看源码或配置 MCP。操作记录、索引管理和环境检查位于当前项目卡片。右键项目可选择“删除工作区”。保存该项目的文件和页面草稿后，核对确认框中的目录。确认后项目目录会移入系统废纸篓，随后移除登记。删除的是当前项目时，「当前项目」和「项目源码」会清空，可再从项目总览选择项目。配置异常时点击对应项目，在当前项目卡片点击“检查配置文件”。

选错同步方式时，从“当前项目 → … → 项目设置”选择“修改同步方式”，选定新方式并确认。尚无源码、索引或操作记录的项目可修改同步方式，即使已登录或已选同步范围。切换后按新方式核对连接和同步范围。已有本地源码的 SVN 或 DATABASE 项目可从同一入口切换到 API 并重新拉取。

当前项目卡片

项目行显示“配置异常”时，点击该行查看原因，再点击“检查配置文件”；修复后使用项目总览的刷新按钮重新读取。整份配置不可用时先处理显示的全局错误。选中 SVN/DATABASE 项目后先核对同步方式和项目目录。SVN 项目用“更新源码”检出或更新授权范围，进度显示在“输出 → GuthonCodeTool”。新登记项目的源码位于项目目录的 checkout/。用“本地修改”查看差异。清单模式能从“提交 SVN”勾选文件，审阅后确认，再到“操作记录”核对回执。DATABASE 项目用“更新源码”更新 readonly 及结构资料。执行时会打开 GuthonCodeTool 输出，显示主库连接、读取范围、源码处理和各项导出进度。单击“项目源码”的页面名称打开本地页面编辑器，点击左侧箭头展开脚本、SQL、字段和按钮。DATABASE 页面和过程函数从工作副本优先读取。首次保存会在 source/workcopy/ 建立与 source/readonly/ 对应的工作副本，之后更新同一副本。搜索结果可直接打开源码。已有导出资料尚未显示时，点击源码树中的“重建本地索引”提示。右键页面或过程函数可打开工作副本或直接比较差异。生成交付材料时使用卡片的“查看工作副本”。SVN 已同步 public 时，可展开“单据类型”和“下拉组件”查看条目。过程函数有继承时可在编辑器查看展开后的产品源码，或右键“查看继承源码”核对项目和产品两层。能力边界见项目操作参考。

在 CodeBuddy 打开 var 根，Nexus 从上到下显示“项目总览”“当前项目”和“项目源码”。在总览点击项目名称，卡片和源码树随之切换；点击“搜索项目”可按名称、别名或 key 筛选，清空搜索恢复全部项目。筛选不切换当前目标，切换项目也不会关闭已有标签页或把未保存内容改到另一个项目。源码 API 要求谷神平台主版本至少 2.0.0，日期版本不早于 202611101305；若提示版本不支持，先核对平台版本并联系平台维护人员。未登录时，在卡片中填写谷神开发平台地址、账号和密码；需要保存密码时勾选“保存密码”，再点击“登录”。如提示验证码，填写显示的验证码后重新登录。

登录后卡片显示项目、版本、地址和用户，以及子系统范围、源码数和修改数。平台会话过期时，工具会尝试恢复登录并继续只读查询；恢复失败后不再重复自动尝试，请在卡片重新登录。升级后旧系统钥匙串中的 API 登录不会自动读取或迁移，需要手动登录一次并勾选“保存密码”。未勾选“保存密码”且后端已经重启时，也需要重新登录。需要退出当前项目时，先保存并关闭该项目打开的在线页面编辑器，再从“当前项目 → … → 项目设置”选择“退出登录”；卡片回到登录状态，保存的 API 登录信息和运行会话被清除，本地源码和编辑器保留。保存方式及限制见API 接入参考。点击“同步范围”或进入“项目设置 → 同步范围”选择子系统。三种同步方式都在保存后等待点击“更新源码”。缩小范围时，该按钮同时清理退出范围的同步副本并更新源码树。API 或 SVN 提示退出范围存在本地修改时，先上传、提交、导出或撤销相应修改，再点击“更新源码”。DATABASE 的 Workcopy 保留。API 需要上传时先保存并核对修改，点击“上传代码”并审阅确认。三种同步方式的卡片下方都显示同步范围、源码数量和修改状态，并提供“搜索源码”“本地修改”“操作记录”“同步范围”“索引管理”“环境检查”六个按钮。需要重新解析本地源码时，点击卡片上的“索引管理”并选择重建索引。项目源码树显示“索引不完整”时，右键可选择“重建索引”重新解析全部本地源码，或选择“修复索引”只重试有诊断的索引项。左键查看诊断。修改尚未核对时会显示“修改待检查”。本地修改与冲突在源代码管理中查看；“索引管理”可查看当前索引状态或诊断；操作记录中可选择源码或数据库排查记录。三个面板都使用 IDE 原生标题栏。VS Code 和 CodeBuddy 折叠面板时会隐藏标题栏按钮，展开后可继续使用。在“项目总览 → …”中展开“工具设置”或“检查更新”。要切换下载渠道，在“检查更新”中点击“选择更新来源”。“当前项目 → … → 源码工具”按同步方式显示资料同步或 SVN 查询操作。源码树在卡片下方使用剩余空间；已有窗口保留过大的项目面板时，可向上拖动两个视图之间的分隔线。源代码管理栏使用“更新”和“上传”图标，悬停可查看操作说明。

3. guthon-team

3.1 安装治理插件

Nexus 初始化会同步工作区规则和本地开发门禁。需要在 Agent 执行工具或结束轮次时自动检查，再安装 guthon-guard 并完成 Hook 信任。

第一次连接内网 Git

  1. 连接公司内网或 VPN，确认终端中可以运行 git --version 和 python3 --version。
  2. 查看本机是否已有 SSH 公钥。macOS/Linux 执行 ls ~/.ssh/*.pub；Windows PowerShell 执行 Get-ChildItem $env:USERPROFILE\.ssh\*.pub。
  3. 如果没有公钥，在终端执行 ssh-keygen -t ed25519 并按提示保存。如果默认文件已经存在，不要覆盖仍在使用的密钥。
  4. 复制对应 .pub 文件的完整内容。macOS/Linux 可执行 cat ~/.ssh/id_ed25519.pub；Windows PowerShell 可执行 Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub。实际文件名不同时按真实路径调整。没有 .pub 后缀的私钥必须只保存在本机，不能上传或发送。
  5. 使用自己的账号登录团队内部发布的 <内网 Git Web 地址>，进入“用户设置 → SSH / GPG 公钥”，点击“增加密钥”，填写设备标题并粘贴公钥。
  6. 执行下面的只读命令。首次出现主机指纹时，先与团队公布的指纹核对；无法核对时不要直接确认。
bash
git ls-remote "<团队 Marketplace SSH 地址>" HEAD

看到一行提交哈希和 HEAD 表示连接成功。若提示 Permission denied (publickey)，先检查公钥是否添加到了当前登录的个人账号；公钥正确但仍无权访问时，再联系管理员检查账号或仓库权限。

Codex 安装

  1. 在终端添加团队 Marketplace。添加市场与安装插件是两个独立步骤，两条命令都要执行：
bash
codex plugin marketplace add "<团队 Marketplace SSH 地址>" --ref main
  1. 安装团队治理插件：
bash
codex plugin add guthon-guard@guthon-team
  1. 如果提示已存在同名 Marketplace，先确认现有来源是否正确。只有确认是旧来源或错误来源时，才移除后重新添加；不要直接覆盖未知配置。
bash
codex plugin marketplace remove guthon-team
codex plugin marketplace add "<团队 Marketplace SSH 地址>" --ref main
codex plugin add guthon-guard@guthon-team

CodeBuddy 安装

CodeBuddy IDE：在插件管理入口添加团队 Marketplace 并安装 guthon-guard@guthon-team。安装或更新后，从命令面板执行“开发人员: 重新加载窗口”，再新建对话。

CodeBuddy Code（命令行）：在 CLI 的交互输入框中依次执行以下命令。IDE 的普通聊天输入不执行这些 CLI 命令：

text
/plugin marketplace add <团队 Marketplace SSH 地址>
/plugin install guthon-guard@guthon-team --scope user
/reload-plugins

如果只希望当前项目使用，可将 --scope user 改为 --scope project。市场添加成功但插件未安装时，规范和 Hook 仍不会生效。

3.2 信任 Hook

  1. 重新打开使用的客户端，进入其插件或 Hook 的审阅与信任入口；Codex 和 CodeBuddy Code CLI 可在交互输入框使用 /hooks。CodeBuddy IDE 按宿主提供的入口操作。
  2. 找到 guthon-guard 提供的 Hook，展开查看实际命令和插件来源。
  3. 确认来源属于团队 Marketplace 后，将该 Hook 设为信任。
  4. 关闭当前任务，再从目标 var/ 或业务子目录打开新任务，才能触发受信任的 SessionStart。

插件已安装、插件已启用、Hook 已信任、Hook 已实际执行是四个不同状态。必须完成后续工作区状态检查，不能只看到插件名称就认为治理已经生效。

3.3 初始化并检查

  1. 确认 GuthonCodeTool 已设置本地数据目录，并且其中已经存在 var/。不要仅为安装治理而执行 git init。
  2. CodeBuddy 打开 <本地数据目录>/var；Codex 可打开具体项目目录，新项目位于 var/workspace/<项目目录>。读取开发根的规则并核对目标。
  3. 确认 Nexus 已提示同步成功，或按手动与无 Hook 安装补齐现有工作空间的规范。启用了 Agent Hook 时，可在新任务中单独确认其运行。

治理初始化通过后，检查根 AGENTS.md、选定规范目录、.guthon 配置、API 索引及本地 Linter。已有根 rules/ 时使用它，否则沿用根 docs/，团队插件不创建 rules/；人工文件冲突会停止更新。只有 var/ 本身是 Git 根且没有冲突的 Git Hook 配置时，才安装 Git pre-commit。初始化如更新了规则入口，再新建一次对话并核对客户端实际加载的规则；已有 CODEBUDDY.md 时保留人工内容，检查其是否遮蔽了根 AGENTS.md。

检查治理状态

  1. 已安装插件时，可以在新任务中输入以下提示词检查插件所带的规范和门禁：
text
使用 $guthon-bootstrap 检查当前工作区治理状态，只查看，不修改

预期看到 STATUS state=ready。当前 Codex 使用 Skill，不要输入 /guthon-guard:guthon-init；该命令不会在 Codex 注册。CodeBuddy 可在输入框执行 /guthon-guard:guthon-init status。

  1. 如果 var/ 使用 Git，在 var/ 或其子目录的终端检查 Git Hook；非 Git 工作区跳过本步：
bash
git config --get core.hooksPath

预期输出 .githooks。如果输出其他路径，不要覆盖；这说明工作区已经使用其他 Hook，需要由维护人员确认整合方式。

  1. 需要手工确认本地 Linter 入口时，在 var/ 根查看帮助；macOS/Linux 使用下列入口，Windows PowerShell 使用 .\tools\guthon-lint.cmd --help：
bash
tools/guthon-lint --help

帮助输出仅确认入口可用。实际源码检查按所选规范根中的“谷神源码写入门禁”执行：API 受控保存后核对回读与具体内容；普通文件的 Git 变更集合检查使用其适用范围。治理状态 ready、入口可运行和源码内容检查通过分别确认。

  1. 如果初始化更新了 AGENTS.md，再打开一次新任务，确保 Codex 从启动阶段加载最新版规则。

3.4 手动与无 Hook 安装

要更新当前工作空间的规则和开发门禁，在“项目总览 → … → 工具设置”点击“团队规则同步”。若提示输入仓库地址，请填写团队提供的 Git 克隆地址。等待 Nexus 提示“团队规则和开发门禁已同步”。如提示需要 Git 认证，选择“在终端认证并同步”，按 Git 提示输入凭据。终端显示 "governance": "ready" 即完成。已有团队 SSH 地址时，可选择“更换仓库地址”直接重试。首次初始化若通过终端完成，回到 Nexus 连接该数据目录。

也可运行 GuthonCodeTool 的 setup --home "<本地数据目录>" --team-source "<团队内网 Git 地址>" 重新同步。看到 "governance": "ready" 后，检查开发根规则和 Linter 入口。

Hook 未信任、宿主不支持 SessionStart 或自动识别失败时，在目标 var/ 工作区或其子目录打开 Codex，先预览计划：

text
使用 $guthon-bootstrap 初始化当前 Guthon 工作区，先执行 dry-run，只展示计划

确认目标 var/ 和文件清单正确、没有冲突后，再输入：

text
使用 $guthon-bootstrap 初始化当前 Guthon 工作区

只安装 AGENTS、规范、API 索引和 Linter，不配置 Git pre-commit 时，在请求中增加 --no-git-hook；非 Git 工作区必须使用这一模式。遇到 CONFLICT 时先逐个检查冲突文件，不要直接使用 --force；确需替换时，安装器会先将旧文件备份到 .guthon/backups/bootstrap-<时间戳>/。

没有 Marketplace 或 Hook 的宿主，应使用团队随 guthon-guard 发布物提供的自包含安装器，不要为此克隆完整团队仓库。安装器的 --workspace 必须明确指向 var/；如果它位于 Git 仓库中，则还必须是该 Git 根：

bash
python3 guthon-guard/scripts/guthon_workspace.py init --workspace "/本地数据目录/var"

# 只安装基础能力，不配置 Git pre-commit
python3 guthon-guard/scripts/guthon_workspace.py init --workspace "/本地数据目录/var" --no-git-hook

安装后重新打开任务并检查状态。规范、Linter、Hook 与 Git 检查的职责见团队治理说明；安装冲突或 Hook 未运行时查团队规范问题解答。

4. Bridge 网页辅助

4.1 安装 Chrome 扩展

需要网页辅助时加载 GuthonBridge 扩展；Windows 首次加载见安装步骤。API 源码核心操作不要求浏览器扩展。

4.2 启动与配对

  1. 更换本地数据目录前，在持有旧 Bridge 服务的 Nexus 窗口点击“项目总览 → … → 停止浏览器增强”，等待停止；同一端口不能同时监听两套数据目录。端口仍被占用时，按端口占用问答核对原窗口和进程。
  2. 在新 API 空间的 Nexus 中点击“项目总览 → … → 启动浏览器增强”（命令面板名称为“Guthon Nexus: 启动 Guthon Bridge”），等待启动成功，再点击“复制配对令牌”。
  3. 在 Chrome 扩展弹窗的配对设置中填写与新 Nexus 相同的端口、粘贴新令牌，点击“保存并连接”。确认显示“Bridge 配对成功”；默认导出目录应属于新的本地数据目录，若使用自定义导出目录则核对已配置的位置。
  4. 更新或重新加载 Chrome 扩展后，先保存平台编辑再刷新平台页面；执行一次所需的只读定位，核对返回工作区与对象。

4.3 使用网页辅助

在受支持页面使用字段复制、列表滚动、标签排序及对象定位；选择当前 PAGE 或过程函数后可发送到 Nexus。定向刷新需要唯一对象，表、视图和系统脚本每次选择一个。单据类型源码不通过 API 定向刷新；独立只读导出另按数据库目标使用。

标签排序

拖动平台标签可调整已支持标签栏的顺序；上层按平台地址保存，下层只在当前页面会话保留。

5. API MCP（按需）

5.1 准备索引

先配置目标 API 项目、选择范围并拉取源码，确认该工作区索引可用。结果只覆盖已拉取范围。

5.2 配置客户端

CodeBuddy、Trae、VS Code：在新 var/ 根打开的 Nexus 窗口中，先选中目标项目，再从“当前项目 → … → 配置 MCP”选择客户端及能力范围，查看配置差异后确认合并。向导按当前打开目录分别写入 .mcp.json、.trae/mcp.json 或 .vscode/mcp.json，保留其他服务及注释，并备份已有文件；它只更新本工具的 guthon-api 条目，不自动停用旧 SVN 服务。

Codex 的 MCP 配置与切换

当前 Nexus 向导不提供 Codex 选项，CodeBuddy 的 .mcp.json 不能代替 Codex 原生 MCP 配置。在终端先用 codex mcp get guthon-api 核对已有条目。确认要切换该条目后，以新的后端入口和数据目录注册；下面是发行应用的只读接入示例：

text
codex mcp add guthon-api -- "<API 后端启动文件绝对路径>" mcp --home "<当前项目所在的本地数据目录>" -- --stdio --read-only
codex mcp get guthon-api

替换尖括号占位符后执行。该命令写入当前 Codex 用户的全局 MCP 配置，同名 add 会更新该条目，使用这份配置的任务会受影响；先核对要切换的服务，保留其他仍在使用的服务。macOS 使用应用目录中的实际启动文件，Windows 使用 EXE。开发模式和 pyz 调试模式需要完整的 Python 与入口文件组合，例如：

text
codex mcp add guthon-api -- "<Python 绝对路径>" "<guthon_tool.py 或 pyz 绝对路径>" mcp --home "<当前项目所在的本地数据目录>" -- --stdio --read-only

日后需要受控修改或平台操作时，先确认授权与所需能力，再调整只读配置；本地保存和平台上传分别确认。

重连并确认切换结果

CodeBuddy IDE 的项目 MCP 还需审批：从命令面板打开“腾讯云代码助手 CodeBuddy: MCP 市场”，在“我的 MCP”中找到项目 guthon-api。如显示“待审批”，先核对来源为新 var 的 .mcp.json，命令及 --home 属于新 API 入口和目录；隔离测试可选“仅本次允许”，正式环境按团队策略审查信任范围。确认该条目显示工具数量后，再新建对话执行一次实际回读。不要批准与本次切换无关的其他服务。

保存配置后按客户端支持的方式重连 MCP，必要时新建任务或重启客户端。先确认发现的是 guthon-api 的 API 工具，再明确指定新工作区 key 读取一个已拉取对象，核对内容和目录。仍在使用的旧服务保留，只停用当前客户端中已经失效的旧 SVN 接线；保留其他 MCP 服务配置。

向导的“后端探测发现工具”独立于客户端的项目 MCP 审批状态。工具发现、本地源码读取和在线只读查询是不同检查。在线查询还需对应项目的 Nexus 窗口保持打开且已登录；仅发现工具不表示平台连接通过，本地源码读取也不要求平台登录。

5.3 查询与受控修改

使用明确 workspaceKey 和对象路径查询源码、调用方或 PAGE 字段。修改单个文件时先获取租约并预览候选，确认后写入并回读；跨文件修改时让 AI 先汇总各文件的修改并预览，核对全部对象后再应用，检查每项结果。需要上传时另行执行。响应未知先查询原操作，不重复提交。工具名与参数见API MCP 参考。

6. 日常工作流

6.1 拉取、修改与上传

  1. 打开目标项目窗口，登录并确认子系统范围及自动关联的数据源。
  2. 拉取或定向刷新，检查冲突；打开源码并保存编辑器中的修改。
  3. 打开上传审阅清单，按类型、名称和路径勾选本次文件；点击每项右侧的差异按钮核对，再确认上传。完成后核对每项回执及平台回读；遇到部分完成或未知结果先检查原记录。
  4. 按业务要求在平台进行最终提交、编译和运行验证；上传回读不代替这些步骤。

平台表或视图的结构同步会执行 DDL，需要明确确认并独立核验数据库结果。

需要更新部分源码时，右键“项目源码”的分类、目录或对象，选择“同步此节点源码”。逻辑分块同步其对应源码文件。结构化 PAGE 的悬停说明如果显示“批量下载 XML · 只读”，点击该页的“编辑页面”会为它加载原生模型；可右键“打开原始源码”查看批量下载的 XML。顶层“过程函数”分类右键可切换“列表平铺”和“树形结构”；数据源、过程包和函数节点没有此切换。函数节点左侧显示业务名称，右侧较小字号显示函数编码及可解析的签名，确认启用返回值时显示返回表达式，例如 [return $result]；无法可靠确定表达式时显示 [return 无]；() 表示确认无参数，(无) 表示无法可靠确定参数。格式及来源见过程函数展示说明。页面或过程函数右键选择“查看使用位置”可打开已索引的引用。新建函数从目标过程包右键进入，核对名称和选项后确认创建。

更新或上传期间打开“输出”，选择“GuthonCodeTool”，查看实际执行步骤和耗时；结果未知时从操作记录核对原编号。

过滤和定位源码

点击源码树标题栏的过滤按钮，输入名称、编码或相对路径；匹配项及父目录会保留。清除过滤后恢复完整目录，过滤不改变拉取范围或上传集合。源码树右键可复制文件名、绝对路径、相对路径，或在系统文件管理器显示所属物理文件；原生资源管理器同步显示本地修改、冲突和名称提示。

在过程函数或服务组件原文的 @inherit() 上悬停可查看说明，按 Ctrl/Cmd 点击打开只读产品源码。继承已展开的代码标签提供“打开只读产品源码”入口；本地函数声明和调用可悬停查看紧邻注释。全局事务过程调用也支持定义跳转。

编辑 PAGE

  1. 在源码树右键目标页面，选择“编辑页面”；也可从资源管理器右键“用本地页面编辑器打开”，或在“重新打开方式”选择谷神本地页面编辑器。两种入口使用同一份页面草稿。已同步源码可离线编辑，无需登录平台。
  2. 编辑字段或代码，按需撤销、恢复和比较，然后保存并确认源代码管理中的本地差异。
  3. 需要使用官方在线设计器时，登录当前 API 项目并点击“在线编辑器”。如有未保存草稿，须先成功保存到本地；保存失败时处理提示后再打开。无需下载、导入或配置设计器资源缓存。
  4. 本地或在线编辑器的保存都只写入本地；需要提交到平台时，确认保存完成且没有后续修改，关闭在线编辑器，再使用“上传代码”，核对回读结果并到平台验证。

如提示源码已变化，先保留当前编辑并比较原文件。服务组件或不支持设计的页面使用源码入口；能力与限制见PAGE 编辑参考。

编辑视图 SQL

在当前项目源码树中打开视图，直接编辑 SQL 并保存；保存结果写回同一份视图源码。需要查看完整定义时使用“原始源码”入口。上传后若平台格式化或补充字段，核对更新后的本地差异；同步数据库结构仍需单独执行并确认。

源码树按页面、过程函数、表、视图、系统脚本、模块参数及已同步的单据类型、下拉组件和开发参考分类，再使用系统名称、菜单及数据源组织，可直接打开页面、过程函数和视图。仅含元数据的 PAGE 或没有 SQL 节点的视图默认展示原文；需要编辑原始定义时，右键选择“打开原始源码”。身份冲突或继承原文保持只读。

编辑、预览和上传模块参数

在“源码工具”选择“同步模块参数”，或从模块参数分类右键同步，先取得所选子系统的参数清单；按子系统展开后点击参数，联网加载该条详情并打开 data JSON 编辑器。可按编码或名称查找条目；参数内容以已加载的详情为准。需要查看模板和其他元数据时，右键打开原始源码，完整原文保持只读。

  1. 在 data 编辑器修改所需参数；模板和对象身份不在编辑范围内。
  2. 从参数右键选择“预览模块参数差异”，核对平台基线与当前输入；按 Ctrl+S（macOS 为 ⌘S）仅保存到本地，完成后检查源代码管理差异。
  3. 需要同步到平台时，右键选择“预览并上传模块参数”，或使用上传代码入口选择模块参数范围。核对已打开的目标、差异及是否需要签出，再点击“确认上传”；关闭或取消提示不会上传。
  4. 查看上传回读结果。需要时工具会普通签出，但不强制覆盖他人的签出、不自动签入。结果未知时从操作记录核对原编号，不直接重试；平台最终签入仍在原生平台完成。

平台参数或模板已变化、存在未保存输入、他人签出或旧操作待核对时，先保留本地输入并按提示处理。差异较长被截断时，应通过参数差异预览或源代码管理核对完整内容。详细边界见模块参数参考。

展开单据类型的数据源或下拉组件列表，点击条目可查看原文对应行；搜索可使用编码、名称和关联表。需要更新时，在条目或相应分组上选择“更新指定 API 源码”，完成后重新查看结果。导出时右键对应分类、数据源或对象；导出源码说明从源码视图标题菜单进入。单据类型完整定义导出需要数据库连接。选择开发参考分类的右键入口，再选择 API、页面结构或事件分组，查看当前项目的说明与示例；属性说明可在属性标签上悬停查看。资料缺失时先从“项目设置 → 配置官方参考资料”启用，再从“源码工具”选择“同步官方参考资料”；不同的本地内容会保留，处理方式见参考资料问答。

保存页面修改

页面编辑器保存到本地后，检查源代码管理差异；结构化页面的上传使用原生源码并独立回读，源码条目悬停可查看来源。原文来源待核验时先刷新并审阅差异；尚无原生源码版本的页面先在平台初始化，再重新同步。未保存代码或外部修改冲突应先保留并处理。需要直接整理字段或按钮集合时，使用“浏览 PAGE 代码节点”中的集合 JSON 编辑入口。项目过程函数展开继承源码时会在保存前核对父层；父层变化后重新展开。

检查在线编辑器连接

打开在线编辑器时，确认已登录当前 API 项目并能连接其平台地址。连接或草稿保存问题见页面编辑器问答。

比较修改并到平台验收

在本地修改或上传审阅中打开 PAGE 差异；可读差异展示页面内容变化，若需要核对格式或键顺序，选择“查看原始源码对比”。区分平台基线与本地已保存内容，以及本地文件与窗口草稿；存在冲突先处理再继续上传。平台效果按实际页面和业务过程验证。

6.2 数据库诊断与测试

需要排查时选择明确工作区和开发或测试目标，核对身份、连接与只读权限，再按计划执行查询或导出结果。详见数据库诊断参考。

6.3 更新工作流

通过 Nexus 核对工具组件的下载、安装与生效状态。官方语言资源更新会在临时编辑器显示版本与兼容结果；它不安装官方扩展。团队治理按其插件市场流程更新。

7. 迁移与使用检查

7.1 系统支持

按实际发行构建选择受支持系统；浏览器增强与数据库驱动根据使用需要单独配置。

7.2 迁移与删除

清理 SVN 工作副本锁

源代码管理出现“SVN 工作副本锁”时，先等其他 SVN 操作结束，再点击对应锁提示。确认锁已清理并核对本地修改后再继续提交。需要检查远端更新时，仍会先显示范围并等待确认。

重新登记项目并迁移文档

  1. 备份前保存并核对旧项目的本地修改。API 按原流程上传并回读，SVN 按原流程提交并确认谷神平台生效，DATABASE 将 workcopy/ 的修改按原流程交付并回写谷神平台。
  2. 关闭原工作区的写入工具。在本地数据目录下创建 backup/，将原 var/ 的全部内容（包括隐藏目录）移入其中，保留空的 var/。要在同一本地数据目录从空登记开始，使用已有的空白统一配置，或先将仍在生效的旧 config/ 单独备份到 backup-config/，再初始化新工作区。配置位置见配置参考。
  3. 打开新 var/，重新添加项目并选择 API、SVN 或 DATABASE。连接原源码来源，选择同步范围，点击“更新源码”，再通过“索引管理 → 重建索引”确认源码树可用。
  4. 选中新项目，从“当前项目 → … → 从原目录迁移”选择 backup/workspace/ 下的对应原项目目录。迁移后检查新项目的 docs/，再让各 AI 工具打开新目录。

若目标已有同名不同内容，先比较备份和新项目中的文档，处理冲突后重试。更多规则见文档迁移参考。

将已有项目切换到 API 并重新拉取

  1. 先把需要保留的源码改动同步到谷神平台，并保存项目里仍打开的文件和页面草稿。
  2. 从“当前项目 → … → 项目设置 → 修改同步方式”选择 API。使用旧 YAML 的项目会先预览并备份升级登记。
  3. 核对提示中的本地清理目录和保留的文档路径，确认已同步后点击“已同步，确认切换”。项目保留原登记身份及文档。旧源码、索引与运行目录会被移出项目并送入废纸篓。
  4. 在 API 项目卡片重新登录和选择同步范围，手动点击“更新源码”拉取并建立新索引。

保留旧 SVN 工作副本与交付历史的迁移

  1. 更新 GuthonCodeTool 后端和 Nexus，按需更新 Bridge 和团队插件。继续打开原数据目录的 var/，从“项目总览”选中原项目并记下 workspaceKey。先保存草稿、处理冲突和未知操作，按原流程提交 SVN 并在谷神平台完成上传和最终提交。记录 revision、平台生效结果及对应对象。

  2. 若使用旧 YAML 或 API schema 2，先按配置升级说明离线发布 schema 3，确认原项目仍为 SVN。用同一后端执行 svn-api-migration --home "<toolHome>" --workspace "<workspaceKey>" -- preflight，处理报告中的阻断项。

  3. 向同一命令的 prepare 动作通过标准输入传入目标地址 serverUrl、平台生效依据 platformEvidence 和 login 对象。login 包含 userId、password 和需要时的 randCode。使用支持遮蔽密码的输入方式；查看 plan，核对 key、API 地址、系统和数据源、候选覆盖、新旧路径以及每个待人工核对的对象。发现缺项或冲突时，先修正来源并重新准备。

  4. 关闭相关 IDE 窗口、旧 ToolHost、Bridge 和 MCP 会话及其他写入入口。执行 apply --offline --confirm "<planId>"；标准输入再次提供 login，并以 manualReview 对象逐项提供待核对的 SVN 相对路径及核对依据。平台或本机材料变化时重新执行 prepare、审阅新的 planId。中断后先运行 status；有待恢复事务时，停用写入入口并执行 recover --offline --confirm "<transactionId>"。动作参数均放在 -- 后。

  5. 重新打开原 var/。在总览确认同一个项目已显示为 API，检查当前卡片和源码树，登录并回读一个已核对的对象。按需配置当前模式的 MCP或重新配对 Bridge。AI 会话重新选择目标并确认实际加载的团队规则；日常修改按API 工作流保存、审阅、上传和回读。旧 SVN 工作副本和操作记录可继续用于历史追溯。

完整输入、核对范围和恢复机制见SVN 切换参考。

移动本地数据目录或删除工作区

移动已有 API 环境时，分别保存项目源码、本地数据目录、API 基线及所需凭据迁移材料；不要将密码直接复制到公开目录。升级后如 AI 客户端仍保留失效的旧源码服务配置，先核对该客户端的实际配置再移除；安装器保留已有人工配置。删除工作区前先审阅范围与保留内容。

索引空间

索引是派生数据；整理前核对项目并保留源码和基线。

7.3 遇到问题

查看当前构建、首条错误及目标身份，在问题解决中心按关键词搜索。

7.4 首次使用检查

分别确认工具启动、项目登录、范围、拉取与索引、编辑上传回读以及平台业务结果；各项互不替代。
