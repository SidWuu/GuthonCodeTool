1. 安装

1.1 准备与下载

下载前确认：

  • 已安装 VS Code；需要网页辅助功能时同时准备 Chrome。
  • 已取得团队 Marketplace 访问权限。实际地址请向团队管理员获取。
  • DATABASE 用户已取得数据库只读账号。
  • SVN 用户已安装 SVN 1.10+，并取得账号和唯一根 checkout 配置。

SVN 首次没有地址配置时，可导入谷神平台提供的 svnCheckoutHere.sh 或 svnCheckoutHere.bat。Nexus 只解析配置，不执行脚本。

打开 GitHub Releases 或 Gitee Releases ，在同一个版本下载：

  • macOS M1 及后续型号：GuthonCodeTool-macos-arm64.zip
  • Windows x64：GuthonCodeTool-windows-x64.exe
  • VS Code 双模式扩展 Guthon Nexus：guthon-nexus-vscode.vsix
  • Chrome 扩展 Guthon Bridge：GuthonCodeTool-chrome.zip
  • 团队规范与开发门禁：通过团队 Marketplace 安装 guthon-guard；访问权限和 Marketplace 安装地址请向团队管理员获取。

建议固定两个目录位置：

text 
应用目录：只放 GuthonCodeTool 应用、Guthon Bridge、Guthon Nexus
本地数据目录：长期保存 config、var、源码、索引和 Workcopy

1.2 安装应用

macOS

  1. 确认 Mac 为 M1 或后续型号：可在“关于本机”中查看。
  2. 解压 GuthonCodeTool-macos-arm64.zip，将其中的 GuthonCodeTool 放入固定应用目录。
  3. 如果文件没有执行权限，在终端执行：
bash
chmod +x "/你的应用目录/GuthonCodeTool"

若系统阻止运行，请先确认文件来自本项目 Release，再打开“系统设置 → 隐私与安全性”，对被阻止的 GuthonCodeTool 选择“仍要打开”。

Windows

  1. 把 GuthonCodeTool-windows-x64.exe 放到固定目录，例如 D:\GuthonCodeTool\。
  2. 不要放进经常清理的“下载”或临时目录。
  3. 若 SmartScreen 拦截，先确认文件来自本项目 Release，再选择“更多信息 → 仍要运行”。

1.3 安装 Nexus

  1. 打开 VS Code 的“扩展”面板。
  2. 点击右上角 ...，选择“从 VSIX 安装...”。
  3. 选择 guthon-nexus-vscode.vsix。
  4. 安装后执行“Developer: Reload Window”或重新启动 VS Code。
  5. 确认左侧活动栏出现“Guthon Nexus”图标。

1.4 设置工作空间

  1. 点击 VS Code 左侧“Guthon Nexus”。
  2. 展开“工作区”，单击“设置工作空间”。
  3. 在确认框点击“执行”。
  4. 选择当前系统的 GuthonCodeTool 应用。
  5. 选择长期保存私有数据的本地数据目录；可以选择空目录。
  6. 等待输出面板显示 GuthonCodeTool 完成：setup。

设置后，入口会变为“切换工作空间”。普通用户保持“发行模式”即可；只有工具维护人员才需要使用“调试模式”。切换工作空间不会删除原目录。

设置工作空间会创建缺失的五个配置文件，不会覆盖已经存在的配置；首次创建的 datasource/products/projects 注册表为空。设置后点击“添加产品或项目”，后续开发新增项目也使用同一入口，不必重新初始化或切换数据目录。

text
<本地数据目录>/
├── config/
│   ├── datasource.yaml
│   ├── products.yaml
│   ├── projects.yaml
│   ├── source-tables.yaml
│   └── sync.yaml
└── var/  # 第一次同步或安装 guthon-team 后出现

2. Nexus

先创建产品或项目，再选择一条源码路线。DATABASE 与 SVN 的配置、同步和编辑方式不同，不要混用操作。

2.1 创建产品或项目

  1. 在 Nexus 点击“添加产品或项目”。
  2. 选择产品或项目，填写名称和稳定 ID。
  3. 选择源码来源：DATABASE 或 SVN。
  4. 向导创建工作区后，继续完成对应路线的配置。

项目是独立导出快照，不需要先选择产品。配置文件职责如下：

  • datasource.yaml：数据库连接。
  • products.yaml：产品、数据源和子系统映射。
  • projects.yaml：独立项目快照、数据源和子系统映射。
  • source-tables.yaml：公司提供的源码表语义配置。
  • sync.yaml：公共同步规则和 SVN 用户名。

2.2 DATABASE 路线

  1. 确认工作区显示“源码来源：DATABASE”。
  2. 在 datasource.yaml 填写只读数据库连接。
  3. 在 products.yaml 或 projects.yaml 填写 datasource、system_id 和 data_source_id。
  4. 保存配置，刷新 Nexus。
  5. 点击“同步工作区全部资料”。
  6. 等待源码、表结构、单据类型、系统脚本和视图全部完成。
  7. 后续只在 source/workcopy 开发；source/readonly 用于比较。

系统 ID 和数据源 ID 必须由配置管理人员提供。不要猜测，也不要复制其他项目的值。需要排查开发库或测试库时，在“配置资料 → 配置数据库排查”添加专用只读连接；快速查询只允许单条 SELECT。

2.3 SVN 路线

  1. 确认工作区显示“源码来源：SVN”。
  2. 点击“设置工作区 SVN 登录”，先保存公共用户名。
  3. 点击“导入/粘贴 SVN checkout 配置”。选择公司提供的脚本，或粘贴唯一根地址/checkout 命令。
  4. 保存并关闭编辑器，让 Nexus 解析地址。脚本只用于提取配置，不会执行。
  5. 点击“编辑 SVN 地址配置”，确认只有一个 svn.url。
  6. 再次打开“设置工作区 SVN 登录”，输入一次密码。
  7. 点击“检出/更新完整 SVN 仓库”，核对根地址后执行。
  8. 完成后从“谷神源码”打开 PAGE、过程函数或系统脚本。
i

SVN 默认完整检出 svn.url，systems.include.mappings 只用于身份和业务分组，不过滤目录。

用户名保存在 sync.yaml；密码由 SVN 凭据缓存或系统钥匙串管理，不写入 YAML。

2.4 驾驶舱与工作区管理

  • “工作区驾驶舱”集中显示索引、同步状态、SVN working copy、本地变更和最近一次 SVN 提交。
  • “搜索工作区完整索引”用于查找源码、调用、条件、赋值、异常和表读写事实。
  • 切换 DATABASE/SVN 只影响当前工作区，不影响其他产品或项目。
  • 删除工作区时，右键 PRD/PRJ 选择“删除产品或项目”，先核对预览范围，再确认移入废纸篓。

3. guthon-team

3.1 安装治理插件

团队治理分成两层：本机安装 Marketplace、guthon-guard 插件和生命周期 Hook；工作区安装 AGENTS.md、规范、API 索引、Linter 与可选的 Git pre-commit。两层需要分别安装和检查。当前流程不需要克隆完整的 guthon-team 仓库，也不要求 GuthonCodeTool 的 var/ 必须由本地 Git 管理。

第一次连接内网 Git

  1. 连接公司内网或 VPN，确认终端中可以运行 git --version 和 python3 --version。
  2. 如果从未访问过内网 Git，先生成或找到本机 SSH 公钥，将公钥交给内网 Git 管理员授权。私钥只保存在本机，不能发给任何人。
  3. 向管理员获取团队 Marketplace SSH 地址，再执行下面的只读命令。首次出现主机指纹时，先与管理员提供的指纹核对；无法核对时不要直接确认。
bash
git ls-remote "<团队 Marketplace SSH 地址>" HEAD

看到一行提交哈希和 HEAD 表示连接成功。若提示 Permission denied (publickey)，说明 SSH 公钥尚未授权；先联系管理员，不要反复安装插件。

Codex 安装

  1. 在终端添加团队 Marketplace。添加市场与安装插件是两个独立步骤，两条命令都要执行：
bash
codex plugin marketplace add "<团队 Marketplace SSH 地址>" --ref main
  1. 安装团队治理插件：
bash
codex plugin add guthon-guard@guthon-team
  1. 如果提示已存在同名 Marketplace，先确认现有来源是否正确。只有确认是旧来源或错误来源时，才移除后重新添加；不要直接覆盖未知配置。
bash
codex plugin marketplace remove guthon-team
codex plugin marketplace add "<团队 Marketplace SSH 地址>" --ref main
codex plugin add guthon-guard@guthon-team

CodeBuddy 安装

在 CodeBuddy 的对话输入框中依次执行；这些是 CodeBuddy 命令，不是在系统终端中执行：

text
/plugin marketplace add <团队 Marketplace SSH 地址>
/plugin install guthon-guard@guthon-team --scope user
/reload-plugins

如果只希望当前项目使用，可将 --scope user 改为 --scope project。市场添加成功但插件未安装时，规范和 Hook 仍不会生效。

3.2 信任 Hook

  1. 重新打开 Codex 或 CodeBuddy，在输入框中输入 /hooks。
  2. 找到 guthon-guard 提供的 Hook，展开查看实际命令和插件来源。
  3. 确认来源属于团队 Marketplace 后，将该 Hook 设为信任。
  4. 关闭当前任务，再从目标 var/ 或业务子目录打开新任务，才能触发受信任的 SessionStart。

插件已安装、插件已启用、Hook 已信任、Hook 已实际执行是四个不同状态。必须完成后续工作区状态检查，不能只看到插件名称就认为治理已经生效。

3.3 初始化并检查

  1. 确认 GuthonCodeTool 已设置本地数据目录，并且其中已经存在 var/。不要仅为安装治理而执行 git init。
  2. 从 <本地数据目录>/var 或其任意业务子目录打开一个新的 Codex 或 CodeBuddy 任务，例如某个 var/workspace/PRD ... 目录。
  3. 等待 SessionStart 完成。受信任的 Hook 会根据 GuthonCodeTool 标识向上定位 var/ 并进行幂等初始化；普通目录和普通 Git 仓库不会被写入 Guthon 治理文件。

自动初始化总会安装项目 AGENTS.md 和团队规范、.guthon 配置与版本锁、API 索引、工作区本地 Linter、tools/guthon-lint。只有 var/ 本身是 Git 根时，才额外安装 Git pre-commit 并设置 core.hooksPath=.githooks。

检查治理状态

  1. 在新任务中输入以下提示词：
text
使用 $guthon-bootstrap 检查当前工作区治理状态，只查看，不修改

预期看到 STATUS state=ready。当前 Codex 使用 Skill，不要输入 /guthon-guard:guthon-init；该命令不会在 Codex 注册。CodeBuddy 可在输入框执行 /guthon-guard:guthon-init status。

  1. 如果 var/ 使用 Git，在 var/ 或其子目录的终端检查 Git Hook；非 Git 工作区跳过本步：
bash
git config --get core.hooksPath

预期输出 .githooks。如果输出其他路径，不要覆盖；这说明工作区已经使用其他 Hook，需要由维护人员确认整合方式。

  1. Git 工作区可从实际 PRD 或 PRJ 工作目录执行变更范围检查：
bash
tools/guthon-lint --changed --write-target

非 Git 工作区不能使用 --changed 或 --staged 自动取得文件列表，应把本次修改的文件逐个传入，例如 tools/guthon-lint "workspace/PRD 期现产品/目标文件.vm"。

  1. 如果初始化更新了 AGENTS.md，再打开一次新任务，确保 Codex 从启动阶段加载最新版规则。

3.4 手动与无 Hook 安装

Hook 未信任、宿主不支持 SessionStart 或自动识别失败时，在目标 var/ 工作区或其子目录打开 Codex，先预览计划：

text
使用 $guthon-bootstrap 初始化当前 Guthon 工作区，先执行 dry-run，只展示计划

确认目标 var/ 和文件清单正确、没有冲突后，再输入：

text
使用 $guthon-bootstrap 初始化当前 Guthon 工作区

只安装 AGENTS、规范、API 索引和 Linter，不配置 Git pre-commit 时，在请求中增加 --no-git-hook；非 Git 工作区必须使用这一模式。遇到 CONFLICT 时先逐个检查冲突文件，不要直接使用 --force；确需替换时，安装器会先将旧文件备份到 .guthon/backups/bootstrap-<时间戳>/。

没有 Marketplace 或 Hook 的宿主，应使用团队随 guthon-guard 发布物提供的自包含安装器，不要为此克隆完整团队仓库。安装器的 --workspace 必须明确指向 var/；如果它位于 Git 仓库中，则还必须是该 Git 根：

bash
python3 guthon-guard/scripts/guthon_workspace.py init --workspace "/本地数据目录/var"

# 只安装基础能力，不配置 Git pre-commit
python3 guthon-guard/scripts/guthon_workspace.py init --workspace "/本地数据目录/var" --no-git-hook

相较只把规范文件交给 AI 阅读，guthon-team 还提供：

  • 机器可执行规则：guthon-lint 检查受保护路径、Velocity 结构、变量冲突、错误赋值、API 合法性、页面重复保存和 SQL 兼容性，不依赖 AI 是否记住全文。
  • 覆盖开发生命周期：支持的 Agent 可在写入前、写入后和任务结束时触发 Hook；Git pre-commit 检查暂存内容，业务仓库还可接入 CI。
  • 版本与防漂移：规范版本、逐文件哈希和锁文件可审计；更新时只升级未被人工修改的受管文件，发现冲突会停止覆盖。
  • 统一 API 事实：根据私有谷神 API 文档生成索引，阻止 AI 按普通 Java、JavaScript 或 SQL 经验猜测平台接口。
  • 精准启用：只有同时存在 .guthon/config.json 和 tools/guthon-lint 的谷神工作区才启用，不干扰普通项目。

安装完成后，以下规范仍保持原来的工作区路径，但由 guthon-team 统一写入和更新：

4. Bridge

只使用 VS Code 同步和导出功能时可以跳过本章。需要从谷神网页拉取当前对象、复制字段或快捷跳转时才需要 Bridge。

4.1 安装 Chrome 扩展

  1. 解压 GuthonCodeTool-chrome.zip 到固定目录。
  2. 按内部环境修改 extension/host-config.js，不要扩大到无关地址。
  3. 打开 chrome://extensions，开启“开发者模式”。
  4. 点击“加载已解压的扩展程序”，选择解压目录中的 extension。
  5. 把 Guthon Bridge 固定到 Chrome 工具栏。

4.2 启动与验证

  1. 打开 VS Code 左侧“Guthon Nexus”面板。
  2. 展开项目顶部的“工作区驾驶舱”，查看索引、同步状态、SVN working copy、本地变更和最近一次 SVN 提交；点击状态行可直接进入对应操作。
  3. 单击“启动 Guthon Bridge”。Nexus 自动使用初始化时选择的应用和本地数据目录。
  4. 面板显示 Bridge“运行中”后即可使用；单击“停止 Guthon Bridge”可关闭服务。

普通用户不需要安装 Node.js 或打开终端。若 Bridge 无法使用，先点击“停止 Guthon Bridge”，再重新启动；仍失败时查看“输出 → Guthon Bridge”中的第一条错误。

5. 日常工作流

每次开发先确认目标 PRD/PRJ 和源码来源。DATABASE 与 SVN 按下面各自的流程执行。

5.1 DATABASE 工作流

  1. 在“项目”树选择目标 PRD 或 PRJ。
  2. 点击“同步工作区全部资料”。
  3. 确认同步没有 FAIL，再从 Workcopy 开始开发。
  4. 需要网页辅助时启动 Bridge，从谷神页面拉取目标对象。
  5. 只修改 Workcopy；不要修改 readonly。
  6. 完成后点击“检查或打包 Workcopy”，查看 diff.md。
  7. 将确认后的内容复制回谷神平台，完成平台测试和提交。

5.2 SVN 工作流

开始开发

  1. 点击“检出/更新完整 SVN 仓库”。
  2. 等待更新和索引完成；不要重复点击正在执行的操作。
  3. 从“谷神源码”打开 PAGE、过程函数或系统脚本。

修改与检查

  1. 修改后按 Ctrl+S（macOS 为 Cmd+S）保存到本地。
  2. 在“谷神源码”树查看带 M 的文件。
  3. 在“源代码管理”点击文件，查看“SVN BASE ↔ 工作副本”差异。
  4. 旧编辑器提示冲突时，重新打开文件；不要强制覆盖。

提交或更新

  1. 先执行“检查远端变更”。
  2. 提交全部范围：使用工作区根节点的“提交 Nexus 修改”。
  3. 提交子系统：使用对应中文分组的提交按钮。
  4. 提交文件：选择一个或多个文件，再执行“提交所选 Nexus 修改”。
  5. 看到 SVN revision 后，到谷神平台完成最终提交和运行验证。

发生冲突

  1. 文本冲突：点击“打开 SVN 三方合并”。
  2. 保存合并结果，再点击“标记 SVN 冲突为已解决”。
  3. 属性冲突、树冲突、新增或删除：停止提交，交由维护人员处理。
  4. 在“工作区驾驶舱”查看最近一次 SVN 提交回执。
!

Ctrl+S/Cmd+S 只保存到本地；冲突必须先完成三方合并并显式标记已解决，不能直接强制提交。SVN 提交成功也不等于谷神平台已最终提交。

定位源码与只读排查

  • 使用“搜索工作区完整索引”查找源码、调用、条件、赋值、异常和表读写。
  • 选择搜索结果后，可打开源码或复制精简/详细 AI 上下文。
  • 排查数据库前先在“配置资料 → 配置数据库排查”选择明确环境。
  • 快速查询只用于只读证据；功能验收仍需正式测试流程。

5.3 更新工作流

更新 GuthonCodeTool

  1. 确认没有同步、SVN 或 Bridge 操作正在执行。
  2. 在“运行模式”选择 GitHub 或 Gitee 更新源。
  3. 点击“检查更新”，确认版本后执行更新。
  4. 更新异常时点击“回退到上一版本”。
  5. VSIX 或 Chrome 扩展有变化时，从同一 Release 重新安装。

更新 guthon-team

Codex 在终端执行：

  1. 执行 codex plugin marketplace upgrade guthon-team。
  2. 执行 codex plugin add guthon-guard@guthon-team。
  3. 从目标 var/ 或业务子目录打开新任务。
  4. 运行 $guthon-bootstrap status，确认状态为 ready。
  5. 如果 AGENTS.md 有变化，再打开一次新任务。

CodeBuddy 在对话输入框执行 /plugin marketplace update guthon-team、/plugin update guthon-guard@guthon-team --scope user 和 /reload-plugins，然后从目标 var/ 或业务子目录打开新任务。若客户端不支持更新命令，可在插件管理界面按 3.1 节重新安装；不要删除工作区中的规范文件。

6. 其他

6.1 系统差异

macOS

  • 当前支持 M1 及后续型号，Intel Mac 不支持。
  • 应用没有执行权限：执行 chmod +x 后重新选择应用。
  • Gatekeeper 阻止：确认下载来源后，在“隐私与安全性”中选择“仍要打开”。
  • 终端设置的数据库环境变量未被 VS Code 读取：从同一终端启动 VS Code，或按公司方式配置用户环境后重启 VS Code。

Windows

  • 当前只提供 Windows x64 EXE。
  • SmartScreen 阻止：确认下载来源后使用“更多信息 → 仍要运行”。
  • 目录链接失败：开启 Windows 开发人员模式，或由管理员完成首次同步。
  • 路径过长：使用 D:\GuthonCodeToolData 等短路径，并按公司策略启用长路径支持。
  • 终端环境变量未生效：关闭并重新打开 VS Code 和 PowerShell。

6.2 迁移与删除

迁移电脑

  1. 停止 Bridge、同步和 SVN 操作。
  2. 安全复制整个本地数据目录。
  3. 在新电脑安装同一版本的应用、Nexus 和 Bridge。
  4. 执行“设置工作空间”，选择复制后的本地数据目录。
  5. 运行“检查本地环境”，再分别验证一个 DATABASE 和 SVN 工作区。

删除产品或项目

  1. 右键目标 PRD/PRJ，选择“删除产品或项目”。
  2. 核对配置、独占数据源、数据库排查条目、工作区目录和 SVN checkout。
  3. 确认无误后执行删除。目标目录会进入系统废纸篓。
  4. 确认其他工作区和共享配置仍然存在。

升级或迁移时不要删除本地数据目录。删除 guthon-team 工作区治理文件需要按锁文件逐项核验，不要直接删除整个 docs/、tools/、.guthon/ 或 .githooks/。

6.3 常见问题

更多 macOS、Windows、DATABASE、SVN、Nexus 与 Bridge 部署和环境问题，请进入 GuthonCodeTool 问题解决中心，可按系统、源码模式和错误原文搜索。

左侧没有“Guthon Nexus”图标

确认 VSIX 已安装并启用，执行“Developer: Reload Window”；仍未出现时卸载旧版本后重新安装当前 Release 的 VSIX。

点击功能后提示启动失败

重新执行“设置/切换工作空间”，选择未改名、未移动且属于当前系统的应用。macOS 同时检查执行权限。

项目树没有显示某个产品或项目

打开 products.yaml 或 projects.yaml，检查 ID、名称和 datasource 是否填写正确，保存后点击 Nexus 刷新。

Bridge 显示无法连接

  1. 确认 Guthon Nexus 面板显示 Bridge“运行中”。
  2. 停止后重新启动 Bridge，并在“输出 → Guthon Bridge”查看第一条错误。
  3. 若错误包含 EADDRINUSE，关闭其他终端或旧版工具中仍在运行的 Bridge，再从 Nexus 启动。
  4. 重新加载 Chrome 扩展并刷新谷神页面。

Workcopy 与 readonly 不一致

先打开 diff.md 确认需要保留的内容。不确定时不要覆盖，请联系负责人处理。

SVN SCM 显示“外部修改”

点击“管理本地源码变更”查看差异，再选择保存或撤销。文本冲突使用文件行的三方合并和“标记为已解决”；如果显示属性冲突、树冲突、新增或删除，不要强制操作，请联系负责人处理。
