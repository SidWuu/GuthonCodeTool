i

macOS 与 Windows 的 VS Code 操作、配置结构和日常工作流相同；只有应用文件名和系统安全提示不同。

普通使用不需要克隆仓库、安装 Python、安装 Node.js 或创建虚拟环境。

1. 准备与下载

开始前准备 VS Code、Chrome、产品/项目配置和公司提供的 AI 规范文件。DATABASE 模式需要数据库只读连接；SVN 模式需要 SVN 1.10+ 客户端、谷神平台下载的 svnCheckoutHere.sh、相应权限和工作空间共享 SVN 凭据，日常无需手工配置仓库根地址；旧 .bat 签出脚本仍兼容。

打开 GitHub Releases 或 Gitee Releases ，在同一个版本下载：

  • macOS Apple Silicon：GuthonCodeTool-macos-arm64.zip
  • Windows x64：GuthonCodeTool-windows-x64.exe
  • VS Code 扩展 Guthon Nexus：GuthonCodeTool-vscode.vsix
  • Chrome 扩展 Guthon Bridge：GuthonCodeTool-chrome.zip
  • 内部配置文件和 AI 规范：从公司内部文档入口获取。

建议固定两个目录位置：

text 
应用目录：只放 GuthonCodeTool 应用、Guthon Bridge、Guthon Nexus
本地数据目录：长期保存 config、var、源码、索引和 Workcopy

2. 安装应用和 VS Code 扩展

2.1 macOS

  1. 确认 Mac 为 Apple 芯片：菜单“关于本机”中的芯片应为 M1、M2、M3、M4 或后续型号。
  2. 解压 GuthonCodeTool-macos-arm64.zip，将其中的 GuthonCodeTool 放入固定应用目录。
  3. 如果文件没有执行权限，在终端执行：
bash
chmod +x "/你的应用目录/GuthonCodeTool"

若系统阻止运行，请先确认文件来自本项目 Release，再打开“系统设置 → 隐私与安全性”，对被阻止的 GuthonCodeTool 选择“仍要打开”。

2.2 Windows

  1. 把 GuthonCodeTool-windows-x64.exe 放到固定目录，例如 D:\GuthonCodeTool\。
  2. 不要放进经常清理的“下载”或临时目录。
  3. 若 SmartScreen 拦截，先确认文件来自本项目 Release，再选择“更多信息 → 仍要运行”。

2.3 安装 VSIX

  1. 打开 VS Code 的“扩展”面板。
  2. 点击右上角 ...，选择“从 VSIX 安装...”。
  3. 选择 GuthonCodeTool-vscode.vsix。
  4. 安装后执行“Developer: Reload Window”或重新启动 VS Code。
  5. 确认左侧活动栏出现“Guthon Nexus”图标。

3. 设置工作空间

  1. 点击 VS Code 左侧“Guthon Nexus”。
  2. 展开“工作区”，单击“设置工作空间”。
  3. 在确认框点击“执行”。
  4. 选择当前系统的 GuthonCodeTool 应用。
  5. 选择长期保存私有数据的本地数据目录；可以选择空目录。
  6. 等待输出面板显示 GuthonCodeTool 完成：setup。

工作空间已设置后，该入口自动改为“切换工作空间”。确认后选择新的本地数据目录，工具会在新目录创建缺失配置；取消确认或目录选择时继续使用原工作空间。切换不会删除、迁移或修改旧工作空间。

普通用户保持“工作区 → 运行模式：发行模式”。需要随时修改 Python 脚本的维护者可单击该项切换为“调试模式”，首次选择 GuthonCodeTool 源码仓库根目录；仓库必须存在 .venv 和 scripts/guthon_tool.py。之后 Nexus 面板操作和 Bridge 拉取都会直接运行最新源码，无需重新构建应用。切回发行模式不会改变本地数据目录。

调试模式统一从 scripts/guthon_tool.py 进入；双模式共享实现位于 scripts/common/，数据库实现位于 scripts/providers/database/，SVN 实现位于 scripts/providers/svn/。不要直接调用旧的 scripts 根目录导出或拉取脚本路径。

设置工作空间会创建缺失的五个配置模板，不会覆盖已经存在的配置。完成后目录为：

text
<本地数据目录>/
├── config/
│   ├── datasource.yaml
│   ├── products.yaml
│   ├── projects.yaml
│   ├── source-tables.yaml
│   └── sync.yaml
└── var/  # 第一次同步或放入 AI 规范后出现

4. 填写配置和放置 AI 规范

在“Guthon Nexus → 工作区 → 配置文件”中单击文件名即可编辑。优先使用公司提供的真实配置；不要把数据库密码、源码或配置提交到公开仓库。

  • datasource.yaml：数据库连接。配置引用环境变量时，必须在启动 VS Code 前设置对应变量，并重启 VS Code。
  • products.yaml：产品 ID、名称、datasource、子系统别名和可选页面来源；不配置源码模式。
  • projects.yaml：项目 ID、名称、datasource、继承产品、子系统别名和可选页面来源；不配置源码模式。
  • source-tables.yaml：PAGE、过程函数和系统脚本的语义字段映射，通常直接使用公司提供版本；真实表名和字段名只保存在本机配置中。
  • sync.yaml：全局同步窗口、未签入源码用户白名单和自动暂存规则，不设置当前或默认工作区。

Nexus 同时展示全部产品和项目。每个产品或项目节点单独设置“源码来源：DATABASE/SVN”，结果保存在该工程 context/source-mode.json；未设置时默认 DATABASE。选择 SVN 后，把谷神平台下载的 svnCheckoutHere.sh 放入该工程的 context/。Nexus 的“从签出脚本检出/更新 SVN”会先显示精确地址数量及增删改统计，确认后生成同目录 authorized-scope.json 并检出或更新。工具只解析脚本，不执行脚本；脚本中的全部仓库使用同一份工作区认证，用户名、密码和原检出绝对路径不会写入清单、日志或公开配置。

text
<本地数据目录>/var/workspace/<PRD或PRJ 工程>/context/svnCheckoutHere.sh
        ↓ Nexus 预览并确认
<本地数据目录>/var/workspace/<PRD或PRJ 工程>/context/authorized-scope.json
        ↓ 受控检出/更新
<本地数据目录>/var/checkout/<配置ID>/...
yaml
products:
  <产品ID>:
    name: <产品名称>
    datasource: <数据源键>
	    systems:
	      include:
	        mappings:
	          demo.system:
	            system_id: SYS-DEMO
	            data_source_id: "0000"
	    page_origins: []

mappings 的键就是系统 alias，每项只保留一对一的 system_id、data_source_id。SVN 用它筛选签出脚本；DATABASE 仍按 alias 查询，并把结果缓存在本机 system-data.json。产品和项目必须分别配置自己的映射，项目的数据源 ID 不得直接复用产品值。

将内部 AI 规范保持原目录层级复制到本地数据目录，至少包括：

text
<本地数据目录>/var/AGENTS.md
<本地数据目录>/var/docs/GUSHEN_DEVELOPMENT_BASELINE.md
<本地数据目录>/var/docs/谷神模块开发规范.md
<本地数据目录>/var/docs/谷神方言API/custom.md
<本地数据目录>/var/docs/谷神方言API/java.md
<本地数据目录>/var/docs/谷神方言API/javascript.md
<本地数据目录>/var/docs/谷神方言API/sql.md

5. 首次初始化和同步

  1. 确认产品、项目各自的数据源和子系统范围正确。
  2. 点击“维护 → 检查本地环境”，确认输出没有 FAIL。
  3. 展开“项目”，确认产品显示为 PRD、项目显示为 PRJ。
  4. 在每个产品或项目节点选择“源码来源：DATABASE / SVN”；DATABASE 节点点击“同步工作区全部资料”，SVN 节点点击“从签出脚本检出/更新 SVN”。
  5. 数据库模式检查源码、表结构、单据类型、系统脚本和视图五步；SVN 模式检查 checkout 范围与本地索引结果。

数据库模式按五步计算状态；SVN 从工作区签出脚本派生脱敏授权清单，按 systems/<SYSTEM_ID>、datasources/<DATA_SOURCE_ID> 等精确 URL 检出多个 working copy 并建立索引；页面与过程函数目录名称分别来自 pages/index.md、procedures/index.md。后续同一入口用同一份认证更新全部授权范围；普通“扫描/重建本地 SVN 索引”不会联网更新。

DATABASE 日常只修改 source/workcopy。SVN 不生成额外代码副本：资源管理器保留 var/checkout/<配置 ID> 原始目录供查看，日常从“谷神源码”编辑并回写同一原文件；直接编辑原文件会被标记为外部修改并交给变更管理器进行安全检查。

6. 安装和启动 Bridge

只使用 VS Code 同步和导出功能时可以跳过本章。需要从谷神网页拉取当前对象、复制字段或快捷跳转时才需要 Bridge。

6.1 加载 Chrome 扩展

  1. 解压 GuthonCodeTool-chrome.zip 到固定目录。
  2. 按内部环境修改 extension/host-config.js，不要扩大到无关地址。
  3. 打开 chrome://extensions，开启“开发者模式”。
  4. 点击“加载已解压的扩展程序”，选择解压目录中的 extension。
  5. 把 Guthon Bridge 固定到 Chrome 工具栏。

6.2 启动本地服务

  1. 打开 VS Code 左侧“Guthon Nexus”面板。
  2. 单击“启动 Guthon Bridge”。Nexus 自动使用初始化时选择的应用和本地数据目录。
  3. 面板显示“运行中 · 127.0.0.1:17361”后即可使用；单击“停止 Guthon Bridge”可关闭服务。

Bridge 服务已经包含在 VSIX 中，由 Guthon Nexus 使用 VS Code 自带的 Node 运行时启动。普通用户无需安装 Node.js、设置环境变量或保持终端窗口运行。Bridge 会按请求中的 workspaceKey 或页面身份匹配产品、项目；多个候选时 Chrome 会要求本次选择。也可以打开 http://127.0.0.1:17361/health，看到 {"ok":true} 即表示服务正常。

数据库工作区继续显示网页源码拉取和 metadata 导出。SVN 工作区隐藏这些旧入口，服务端也拒绝旧版扩展的直接调用；请在 Nexus 中执行 checkout 初始化/更新、虚拟编辑和 SCM 操作。Bridge 继续保留页面身份路由、复制字段和字段平移等能力。

升级到该方式后，不要再同时从终端执行旧的 npm run start:bridge。如果输出出现 EADDRINUSE 127.0.0.1:17361，说明已有 Bridge 占用端口；先关闭原终端中的服务，再回到 Guthon Nexus 启动。

7. 日常工作流

数据库模式

text
在“项目”树选择数据库 PRD 或 PRJ
        ↓
同步该工作区全部资料
        ↓
启动 Bridge，从谷神页面拉取目标 Workcopy
        ↓
VS Code / AI 只分析和修改 Workcopy
        ↓
“检查或打包 Workcopy”生成状态和差异
        ↓
人工复制回谷神平台并测试、提交、签入
        ↓
再次拉取，确认 readonly 与 Workcopy 无差异

SVN 模式

text
将谷神下载的 svnCheckoutHere.sh 放入工程 context/
        ↓
在目标产品或项目节点选择“源码来源：SVN”并点击“从签出脚本检出/更新 SVN”
        ↓
Nexus 把授权清单中的多个 working copy 聚合为“谷神源码”和一个 SCM 项目
        ↓
打开 PAGE 脚本/SQL/字段或过程函数虚拟文档，Ctrl+S 回写原 checkout
        ↓
在 SCM 用原生双栏视图比较只读 SVN BASE 与当前源码，并查看历史；可全部或逐文件提交 Nexus 修改、更新远程变更
        ↓
勾选同一 working copy 中的部分物理文件，点击“保存到谷神”
        ↓
确认 SVN revision 与“待平台提交”，再在谷神平台最终提交
  1. 开始开发前，从“项目”树确定目标产品或项目。
  2. DATABASE 执行“同步工作区全部资料”并确认五步状态；SVN 执行“从签出脚本检出/更新 SVN”并确认授权范围和索引状态。
  3. DATABASE 可继续在谷神页面使用 Bridge 拉取 Workcopy；SVN 从“谷神源码”进入，不再通过 Bridge 拉取。
  4. 使用 VS Code 源代码管理查看项目级变更；底层多个 working copy 会按实际文件身份路由。
  5. var Git 只管理配置、上下文、索引资料和 DATABASE 工作区；根级 var/checkout/ 已被 Git 忽略，SVN 源码差异、更新、放弃和提交只在 Nexus SCM 中处理，禁止使用 git add -f 纳入 checkout。
  6. “谷神源码”树从本地 SVN 索引快速加载，只在展开单个 PAGE 时解析其分块；刷新树不会隐式扫描整个 checkout。
  7. PAGE 和系统脚本的 $.<中文子系统名> 只用作中文分组；PAGE 与过程函数的目录、菜单/过程包和叶子严格按各自 index.md 的出现顺序展示，未编入索引的对象排在后面；系统脚本、表和视图保留原源码目录层级。
  8. PAGE 的前端事件、字段、SQL 和 GSS 后端事件可按分块打开并保存；.gss 使用独立 Guthon GSS 语言，在 Java 语法上补充 Velocity/GSS 指令和变量高亮并保留 Nexus 补全/跳转，兼容保留的 .vm 仍使用 Java。GSS 服务组件的自动生成身份头不可修改。
  9. 选中“谷神源码”模块或其方法、字段、SQL、事件等任意子节点后点击顶部“跳转”，均可在资源管理器中显示所属模块的物理源码。
  10. 打开 SVN 虚拟分块或 checkout 物理文件后点击顶部“定位”，Nexus 会自动展开父级并选中对应源码节点；定位 PAGE 分块只解析目标页面。
  11. “谷神源码”视图顶部另提供展开所选、收缩所选、搜索和刷新；搜索按钮直接显示 VS Code 原生树搜索框，默认按模糊过滤当前缓存节点，不重新扫描 checkout。长名称超过视图宽度时可使用底部水平滚动条。
  12. SVN 虚拟文档支持调用索引的转到定义和查找引用；动态调用仍需人工确认。
  13. Ctrl+S 只写回目标文件并更新其索引；同一虚拟文档可连续修改和保存，真实外部变化仍会触发比较/覆盖保护。
  14. SCM 变更名称来自本地 SQLite 索引和 index.md 业务目录；点击 PAGE 变更默认打开脚本、SQL、字段的可读双栏差异，右键仍可查看精确原始 JSON。左侧是内存中的只读 SVN BASE，右侧是当前 working copy，不生成 BASE 临时文件。
  15. SCM 云图标显式检查远端并显示独立“远程变更”组；普通本地刷新不联网。更新遇到 SVN incomplete 或 working-copy 管理锁时仅执行标准 svn cleanup 后复检，不删除未跟踪文件或还原本地修改。
  16. SCM 顶部以及“Nexus 修改”“远程变更”分组提供全部提交/更新，每个 Nexus 修改和远程变更行提供单文件提交/更新。单文件更新仅作用于授权清单解析出的精确物理路径；该文件同时有本地修改时，必须确认使用 SVN 原生合并，Nexus 不自动解决冲突。
  17. “管理本地源码变更”同时列出 Nexus 编辑和安全的外部已跟踪文本修改；可查看差异、多选或全选保存和撤销。冲突、新增、删除、未跟踪和属性变化会明确阻断。
  18. 撤销按本地 SVN BASE 回退已选择文件，不要求 working copy 与远端最新 revision 一致；“保存到谷神”仍会执行远端过期检查。
  19. 完成本地验证后保存到谷神；看到 revision 后仍需在谷神平台完成最终提交。

sync.yaml 的 rules.pull_diff_check 缺省为 true：直接比较 readonly 与 workcopy，存在差异时保留 workcopy 并生成差异报告。设为 false 时直接覆盖 readonly/workcopy。

DATABASE 不自动回写平台。SVN 的 Ctrl+S 只写本地 checkout；“管理本地源码变更”支持类 Git 差异、多选/全选保存和撤销。“保存到谷神”是 SVN 模式固定能力，跨 working copy 时分组执行 svn commit，仍不等于谷神平台最终提交。

8. 系统差异和解决步骤

macOS

  • 当前只提供 Apple Silicon 应用，Intel Mac 暂不支持。
  • 应用没有执行权限：执行 chmod +x 后重新选择应用。
  • Gatekeeper 阻止：确认下载来源后，在“隐私与安全性”中选择“仍要打开”。
  • 终端设置的数据库环境变量未被 VS Code 读取：从同一终端启动 VS Code，或按公司方式配置用户环境后重启 VS Code。

Windows

  • 当前只提供 Windows x64 EXE。
  • SmartScreen 阻止：确认下载来源后使用“更多信息 → 仍要运行”。
  • 目录链接失败：开启 Windows 开发人员模式，或由管理员完成首次同步。
  • 路径过长：使用 D:\GuthonCodeToolData 等短路径，并按公司策略启用长路径支持。
  • 终端环境变量未生效：关闭并重新打开 VS Code 和 PowerShell。

9. 升级和迁移

  1. 从最新 Release 下载当前系统应用、VSIX 和 GuthonBridge。
  2. 关闭正在运行的同步任务和 Bridge。
  3. 用新应用替换旧应用；路径不变时 VS Code 无需重新初始化。
  4. 从 VSIX 重新安装扩展，并重新加载 VS Code。
  5. 替换 Bridge 前备份自己的 extension/host-config.js，然后重新加载 Chrome 扩展。
  6. 运行“检查本地环境”，再选择一个产品和一个项目分别执行完整同步。

升级时不要删除本地数据目录。配置、AI 规范、readonly、Workcopy、SQLite 和日志都保存在该目录，与应用版本分离。

迁移电脑时，应安全复制整个本地数据目录，再在新电脑执行一次“设置工作空间”选择新应用和该目录；数据库凭据和系统环境变量需按公司要求重新配置。

10. 常见问题与验收

左侧没有“Guthon Nexus”图标

确认 VSIX 已安装并启用，执行“Developer: Reload Window”；仍未出现时卸载旧版本后重新安装当前 Release 的 VSIX。

点击功能后提示启动失败

重新执行“设置/切换工作空间”，选择未改名、未移动且属于当前系统的应用。macOS 同时检查执行权限。

项目树没有显示某个产品或项目

检查 products.yaml 或 projects.yaml 的键、名称和 datasource，然后刷新 Nexus。每个节点独立绑定 workspaceKey，不会共享默认工作区。

Bridge 显示无法连接

  1. 确认 Guthon Nexus 面板显示 Bridge“运行中”。
  2. 访问 http://127.0.0.1:17361/health。
  3. 停止后重新启动 Bridge，并在“输出 → Guthon Bridge”查看第一条错误。
  4. 若错误包含 EADDRINUSE，关闭其他终端或旧版工具中占用 17361 的 Bridge，再从 Nexus 启动。
  5. 重新加载 Chrome 扩展并刷新谷神页面。

Workcopy 与 readonly 不一致

查看 diff.md 确认需要保留的内容。工具将 readonly 与 workcopy 的任何差异都视为需要保留；需要接受 readonly 覆盖时，将 pull_diff_check 设为 false 后重新拉取。

SVN SCM 显示“外部修改”

这表示 checkout 原文件在 Nexus 编辑会话外发生变化。先在“管理本地源码变更”中审阅 diff；安全的已跟踪文本修改可以继续选择保存或撤销。冲突、新增、删除、未跟踪和属性变化不会被自动接管，必须先在物理 working copy 中处理。
