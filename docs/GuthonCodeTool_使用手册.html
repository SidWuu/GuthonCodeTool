1. 安装

1.1 准备与下载

下载前确认：

  • 已安装 VS Code；需要网页辅助功能时同时准备 Chrome。
  • 已取得内网 Git 个人账号，并能登录团队内部发布的 <内网 Git Web 地址>；管理员已为账号授予团队仓库权限。
  • DATABASE 用户已取得数据库只读账号。
  • SVN 用户已安装 SVN 1.10+，并取得账号和唯一根 checkout 配置。

SVN 首次没有地址配置时，可导入谷神平台提供的 svnCheckoutHere.sh 或 svnCheckoutHere.bat。Nexus 只解析配置，不执行脚本。

打开 GitHub Releases 或 Gitee Releases ，在同一个版本下载：

  • macOS M1 及后续型号：GuthonCodeTool-macos-arm64.zip
  • Windows x64：GuthonCodeTool-windows-x64.exe
  • VS Code 双模式扩展 Guthon Nexus：guthon-nexus-vscode.vsix
  • Chrome 扩展 Guthon Bridge：GuthonCodeTool-chrome.zip
  • 团队规范与开发门禁：成员使用自己的内网 Git 账号和 SSH 公钥，通过团队 Marketplace 安装 guthon-guard。

建议固定两个目录位置：

text 
应用目录：只放 GuthonCodeTool 应用、Guthon Bridge、Guthon Nexus
本地数据目录：长期保存 config、var、源码、索引和 Workcopy

1.2 安装应用

macOS

  1. 确认 Mac 为 M1 或后续型号：可在“关于本机”中查看。
  2. 解压 GuthonCodeTool-macos-arm64.zip，将其中的 GuthonCodeTool 放入固定应用目录。
  3. 如果文件没有执行权限，在终端执行：
bash
chmod +x "/你的应用目录/GuthonCodeTool"

若系统阻止运行，请先确认文件来自本项目 Release，再打开“系统设置 → 隐私与安全性”，对被阻止的 GuthonCodeTool 选择“仍要打开”。

Windows

  1. 把 GuthonCodeTool-windows-x64.exe 放到固定目录，例如 D:\GuthonCodeTool\。
  2. 不要放进经常清理的“下载”或临时目录。
  3. 若 SmartScreen 拦截，先确认文件来自本项目 Release，再选择“更多信息 → 仍要运行”。

1.3 安装 Nexus

  1. 打开 VS Code 的“扩展”面板。
  2. 点击右上角 ...，选择“从 VSIX 安装...”。
  3. 选择 guthon-nexus-vscode.vsix。
  4. 安装后执行“Developer: Reload Window”或重新启动 VS Code。
  5. 确认左侧活动栏出现“Guthon Nexus”图标。

1.4 设置工作空间

  1. 点击 VS Code 左侧“Guthon Nexus”。
  2. 展开“工作区”，单击“设置工作空间”。
  3. 在确认框点击“执行”。
  4. 选择当前系统的 GuthonCodeTool 应用。
  5. 选择长期保存私有数据的本地数据目录；可以选择空目录。
  6. 等待输出面板显示 GuthonCodeTool 完成：setup。

设置后，入口会变为“切换工作空间”。普通用户保持“发行模式”即可；维护者可选“开发模式”（仓库源码与 .venv），已有 Python 3.12+ 的开发人员可选“调试模式”（Release 的 .pyz 与校验文件）。调试模式会检查脚本、依赖、自检和 ToolHost 协议；隔离 Python 运行环境的一键下载尚未交付。切换工作空间不会删除原目录。

Nexus 和 Bridge 各自复用一个常驻 ToolHost。普通“刷新 Guthon Nexus”只更新工作区列表和界面，不扫描全部 SVN working copy；需要检查本地变更时使用“刷新 SVN 变更”，需要访问远端时使用“检查 SVN 远程变更”。

设置工作空间会创建缺失的五个配置文件，不会覆盖已经存在的配置；首次创建的 datasource/products/projects 注册表为空。设置后点击“添加产品或项目”，后续开发新增项目也使用同一入口，不必重新初始化或切换数据目录。

text
<本地数据目录>/
├── config/
│   ├── datasource.yaml
│   ├── products.yaml
│   ├── projects.yaml
│   ├── source-tables.yaml
│   └── sync.yaml
└── var/  # 第一次同步或安装 guthon-team 后出现

2. Nexus

先创建产品或项目，再选择一条源码路线。DATABASE 与 SVN 的配置、同步和编辑方式不同，不要混用操作。

2.1 创建产品或项目

  1. 在 Nexus 点击“添加产品或项目”。
  2. 选择产品或项目，填写名称和稳定 ID。
  3. 选择源码来源：DATABASE 或 SVN。
  4. 向导创建工作区后，继续完成对应路线的配置。

项目是独立导出快照，不需要先选择产品。配置文件职责如下：

  • datasource.yaml：数据库连接。
  • products.yaml：产品、数据源和子系统映射。
  • projects.yaml：独立项目快照、数据源和子系统映射。
  • source-tables.yaml：公司提供的源码表语义配置。
  • sync.yaml：公共同步规则和 SVN 用户名。

2.2 DATABASE 路线

  1. 确认工作区显示“源码来源：DATABASE”。
  2. 在 datasource.yaml 填写只读数据库连接。
  3. 在 products.yaml 或 projects.yaml 填写 datasource、system_id 和 data_source_id。
  4. 保存配置，刷新 Nexus。
  5. 点击“同步工作区全部资料”。
  6. 等待源码、表结构、单据类型、系统脚本和视图全部完成。
  7. 后续只在 source/workcopy 开发；source/readonly 用于比较。

系统 ID 和数据源 ID 必须由配置管理人员提供。不要猜测，也不要复制其他项目的值。需要排查开发库或测试库时，在“配置资料 → 配置数据库排查”添加专用只读连接；快速查询只允许单条 SELECT。

2.3 SVN 路线

  1. 确认工作区显示“源码来源：SVN”。
  2. 点击“设置工作区 SVN 登录”，先保存公共用户名。
  3. 点击“导入/粘贴 SVN checkout 配置”。选择公司提供的脚本，或粘贴唯一根地址/checkout 命令。
  4. 保存并关闭编辑器，让 Nexus 解析地址。脚本只用于提取配置，不会执行。
  5. 点击“编辑 SVN 地址配置”，确认只有一个 svn.url。
  6. 再次打开“设置工作区 SVN 登录”，输入一次密码。
  7. 点击“检出/更新完整 SVN 仓库”，核对根地址后执行。
  8. 完成后从“谷神源码”打开 PAGE、过程函数或系统脚本。
i

SVN 默认完整检出 svn.url，systems.include.mappings 只用于身份和业务分组，不过滤目录。

用户名保存在 sync.yaml；密码由 SVN 凭据缓存或系统钥匙串管理，不写入 YAML。

2.4 驾驶舱与工作区管理

  • “工作区驾驶舱”集中显示索引、同步状态、SVN working copy、本地变更和最近一次 SVN 提交。
  • “搜索工作区完整索引”用于查找源码、调用、条件、赋值、异常和表读写事实。
  • 切换 DATABASE/SVN 只影响当前工作区，不影响其他产品或项目。
  • 删除工作区时，右键 PRD/PRJ 选择“删除产品或项目”，先核对预览范围，再确认移入废纸篓。

3. guthon-team

3.1 安装治理插件

团队治理分成两层：本机安装 Marketplace、guthon-guard 插件和生命周期 Hook；工作区安装 AGENTS.md、规范、API 索引、Linter 与可选的 Git pre-commit。两层需要分别安装和检查。当前流程不需要克隆完整的 guthon-team 仓库，也不要求 GuthonCodeTool 的 var/ 必须由本地 Git 管理。

第一次连接内网 Git

  1. 连接公司内网或 VPN，确认终端中可以运行 git --version 和 python3 --version。
  2. 查看本机是否已有 SSH 公钥。macOS/Linux 执行 ls ~/.ssh/*.pub；Windows PowerShell 执行 Get-ChildItem $env:USERPROFILE\.ssh\*.pub。
  3. 如果没有公钥，在终端执行 ssh-keygen -t ed25519 并按提示保存。如果默认文件已经存在，不要覆盖仍在使用的密钥。
  4. 复制对应 .pub 文件的完整内容。macOS/Linux 可执行 cat ~/.ssh/id_ed25519.pub；Windows PowerShell 可执行 Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub。实际文件名不同时按真实路径调整。没有 .pub 后缀的私钥必须只保存在本机，不能上传或发送。
  5. 使用自己的账号登录团队内部发布的 <内网 Git Web 地址>，进入“用户设置 → SSH / GPG 公钥”，点击“增加密钥”，填写设备标题并粘贴公钥。
  6. 执行下面的只读命令。首次出现主机指纹时，先与团队公布的指纹核对；无法核对时不要直接确认。
bash
git ls-remote "<团队 Marketplace SSH 地址>" HEAD

看到一行提交哈希和 HEAD 表示连接成功。若提示 Permission denied (publickey)，先检查公钥是否添加到了当前登录的个人账号；公钥正确但仍无权访问时，再联系管理员检查账号或仓库权限。

Codex 安装

  1. 在终端添加团队 Marketplace。添加市场与安装插件是两个独立步骤，两条命令都要执行：
bash
codex plugin marketplace add "<团队 Marketplace SSH 地址>" --ref main
  1. 安装团队治理插件：
bash
codex plugin add guthon-guard@guthon-team
  1. 如果提示已存在同名 Marketplace，先确认现有来源是否正确。只有确认是旧来源或错误来源时，才移除后重新添加；不要直接覆盖未知配置。
bash
codex plugin marketplace remove guthon-team
codex plugin marketplace add "<团队 Marketplace SSH 地址>" --ref main
codex plugin add guthon-guard@guthon-team

CodeBuddy 安装

在 CodeBuddy 的对话输入框中依次执行；这些是 CodeBuddy 命令，不是在系统终端中执行：

text
/plugin marketplace add <团队 Marketplace SSH 地址>
/plugin install guthon-guard@guthon-team --scope user
/reload-plugins

如果只希望当前项目使用，可将 --scope user 改为 --scope project。市场添加成功但插件未安装时，规范和 Hook 仍不会生效。

3.2 信任 Hook

  1. 重新打开 Codex 或 CodeBuddy，在输入框中输入 /hooks。
  2. 找到 guthon-guard 提供的 Hook，展开查看实际命令和插件来源。
  3. 确认来源属于团队 Marketplace 后，将该 Hook 设为信任。
  4. 关闭当前任务，再从目标 var/ 或业务子目录打开新任务，才能触发受信任的 SessionStart。

插件已安装、插件已启用、Hook 已信任、Hook 已实际执行是四个不同状态。必须完成后续工作区状态检查，不能只看到插件名称就认为治理已经生效。

3.3 初始化并检查

  1. 确认 GuthonCodeTool 已设置本地数据目录，并且其中已经存在 var/。不要仅为安装治理而执行 git init。
  2. 从 <本地数据目录>/var 或其任意业务子目录打开一个新的 Codex 或 CodeBuddy 任务，例如某个 var/workspace/PRD ... 目录。
  3. 等待 SessionStart 完成。受信任的 Hook 会根据 GuthonCodeTool 标识向上定位 var/ 并进行幂等初始化；普通目录和普通 Git 仓库不会被写入 Guthon 治理文件。

自动初始化总会安装项目 AGENTS.md 和团队规范、.guthon 配置与版本锁、API 索引、工作区本地 Linter、tools/guthon-lint。只有 var/ 本身是 Git 根时，才额外安装 Git pre-commit 并设置 core.hooksPath=.githooks。

检查治理状态

  1. 在新任务中输入以下提示词：
text
使用 $guthon-bootstrap 检查当前工作区治理状态，只查看，不修改

预期看到 STATUS state=ready。当前 Codex 使用 Skill，不要输入 /guthon-guard:guthon-init；该命令不会在 Codex 注册。CodeBuddy 可在输入框执行 /guthon-guard:guthon-init status。

  1. 如果 var/ 使用 Git，在 var/ 或其子目录的终端检查 Git Hook；非 Git 工作区跳过本步：
bash
git config --get core.hooksPath

预期输出 .githooks。如果输出其他路径，不要覆盖；这说明工作区已经使用其他 Hook，需要由维护人员确认整合方式。

  1. Git 工作区可从实际 PRD 或 PRJ 工作目录执行变更范围检查：
bash
tools/guthon-lint --changed --write-target

非 Git 工作区不能使用 --changed 或 --staged 自动取得文件列表，应把本次修改的文件逐个传入，例如 tools/guthon-lint "workspace/PRD 期现产品/目标文件.vm"。

  1. 如果初始化更新了 AGENTS.md，再打开一次新任务，确保 Codex 从启动阶段加载最新版规则。

3.4 手动与无 Hook 安装

Hook 未信任、宿主不支持 SessionStart 或自动识别失败时，在目标 var/ 工作区或其子目录打开 Codex，先预览计划：

text
使用 $guthon-bootstrap 初始化当前 Guthon 工作区，先执行 dry-run，只展示计划

确认目标 var/ 和文件清单正确、没有冲突后，再输入：

text
使用 $guthon-bootstrap 初始化当前 Guthon 工作区

只安装 AGENTS、规范、API 索引和 Linter，不配置 Git pre-commit 时，在请求中增加 --no-git-hook；非 Git 工作区必须使用这一模式。遇到 CONFLICT 时先逐个检查冲突文件，不要直接使用 --force；确需替换时，安装器会先将旧文件备份到 .guthon/backups/bootstrap-<时间戳>/。

没有 Marketplace 或 Hook 的宿主，应使用团队随 guthon-guard 发布物提供的自包含安装器，不要为此克隆完整团队仓库。安装器的 --workspace 必须明确指向 var/；如果它位于 Git 仓库中，则还必须是该 Git 根：

bash
python3 guthon-guard/scripts/guthon_workspace.py init --workspace "/本地数据目录/var"

# 只安装基础能力，不配置 Git pre-commit
python3 guthon-guard/scripts/guthon_workspace.py init --workspace "/本地数据目录/var" --no-git-hook

相较只把规范文件交给 AI 阅读，guthon-team 还提供：

  • 机器可执行规则：guthon-lint 检查受保护路径、Velocity 结构、变量冲突、错误赋值、API 合法性、页面重复保存和 SQL 兼容性，不依赖 AI 是否记住全文。
  • 覆盖开发生命周期：支持的 Agent 可在写入前、写入后和任务结束时触发 Hook；Git pre-commit 检查暂存内容，业务仓库还可接入 CI。
  • 版本与防漂移：规范版本、逐文件哈希和锁文件可审计；更新时只升级未被人工修改的受管文件，发现冲突会停止覆盖。
  • 统一 API 事实：根据私有谷神 API 文档生成索引，阻止 AI 按普通 Java、JavaScript 或 SQL 经验猜测平台接口。
  • 精准启用：只有同时存在 .guthon/config.json 和 tools/guthon-lint 的谷神工作区才启用，不干扰普通项目。

安装完成后，以下规范仍保持原来的工作区路径，但由 guthon-team 统一写入和更新：

4. Bridge

只使用 VS Code 同步和导出功能时可以跳过本章。需要从谷神网页拉取当前对象、复制字段或快捷跳转时才需要 Bridge。

4.1 安装 Chrome 扩展

  1. 解压 GuthonCodeTool-chrome.zip 到固定目录。
  2. 按内部环境修改 extension/host-config.js，不要扩大到无关地址。
  3. 打开 chrome://extensions，开启“开发者模式”。
  4. 点击“加载已解压的扩展程序”，选择解压目录中的 extension。
  5. 把 Guthon Bridge 固定到 Chrome 工具栏。

4.2 启动与验证

  1. 打开 VS Code 左侧“Guthon Nexus”面板。
  2. 展开项目顶部的“工作区驾驶舱”，查看索引、同步状态、SVN working copy、本地变更和最近一次 SVN 提交；点击状态行可直接进入对应操作。
  3. 单击“启动 Guthon Bridge”。Nexus 自动使用初始化时选择的应用和本地数据目录。
  4. 面板显示 Bridge“运行中”后即可使用；单击“停止 Guthon Bridge”可关闭服务。

普通用户不需要安装 Node.js 或打开终端。若 Bridge 无法使用，先点击“停止 Guthon Bridge”，再重新启动；仍失败时查看“输出 → Guthon Bridge”中的第一条错误。

5. SVN MCP

SVN MCP 与 Nexus、Bridge 并列，是供支持 MCP 的 AI 客户端快捷查询和受控修改源码的本地服务。它由客户端单独启动一个 stdio 进程，不依赖 Chrome，也不会自动改写客户端配置。当前只面向已配置的 SVN manifest 工作区；默认提供 14 个只读工具和 13 个 PAGE/过程函数编辑与恢复工具，复用 Nexus/CLI 的授权范围和 context/index.db，不另建索引，也不提交 SVN。

stdio 握手支持 MCP 2025-03-26、2025-06-18 与 2025-11-25。客户端应核对服务端协商返回的版本；本入口不支持新版无握手生命周期，也不会把未知版本原样回显为“已支持”。

5.1 准备索引

  1. 先按 2.3 节在 Nexus 创建 SVN 工作区，完成授权根检出与索引；记下配置中的完整 workspaceKey，例如 products.<id>，不要用显示名或 PRD 目录名代替。
  2. 确认当前应用或开发版包含 mcp --stdio 入口。旧发行包不会因更新手册而自动获得 MCP。
  3. 客户端连接后，PAGE 操作先调用 get_index_status，过程函数操作先调用 get_source_index_status。目标索引为 READY 才继续；REBUILD_REQUIRED 需显式重建。若为 PARTIAL 且 projectionGapCount>0，表示部分 JSON PAGE 有源码片段但缺少语义节点；可对明确目标执行 svn reindex-file --path，缺口较多时重建整个工作区索引。刷新会更新该工作区的 context/index.db，不会修改 SVN 源码或提交 SVN。过程函数对象索引就绪不要求 PAGE 语义投影同时就绪。
text
/应用目录/GuthonCodeTool reindex --home /本地数据目录 --workspace products.<id>

若只有明确目标缺口，也可用 /应用目录/GuthonCodeTool svn --home /本地数据目录 --workspace products.<id> -- reindex-file --path <索引返回的 sourcePath> 做单文件刷新；sourcePath 必须来自已核对的索引身份或错误提示，不猜物理路径。上行是 macOS 发行应用示意；Windows 把命令换成已安装的 GuthonCodeTool-windows-x64.exe 并使用本机绝对路径。只有状态提示需要刷新时才运行，不把 MCP 查询当成自动迁移入口。

5.2 配置客户端

在支持 stdio MCP 的 Harness 中新增一个独立服务，命令和每个参数分别填写；使用真实的绝对路径，不要把 ~、$GUTHON_HOME 或整条 Shell 命令作为可执行文件。以下示例选用发行应用；如果路径包含空格，在配置中仍把可执行文件作为一个 command 值，不自行拆分。

Codex（桌面应用、CLI、IDE 扩展）

编辑个人 ~/.codex/config.toml，在已有内容后添加下列服务表，不要覆盖原有配置。Codex 的桌面应用、CLI 和 IDE 扩展共用此配置；也可放在可信任项目的 .codex/config.toml，但包含个人本地路径的配置通常更适合放在个人文件中。配置格式以 Codex 官方 MCP 文档为准。

toml
[mcp_servers."guthon-svn"]
command = "/应用目录/GuthonCodeTool"
args = ["mcp", "--stdio", "--home", "/本地数据目录"]

也可以只用 Codex CLI 添加一次（与手工编辑 TOML 二选一，避免重复配置）：

bash
codex mcp add guthon-svn -- /应用目录/GuthonCodeTool mcp --stdio --home /本地数据目录
codex mcp list

命令行示例假设替换后的绝对路径不含空格；含空格时分别给可执行文件路径和数据目录路径加引号。codex mcp list 用于核对注册项；随后新开 Codex 任务，确认工具列表中出现 guthon-svn，再调用 get_runtime_status 和目标工作区的索引状态工具。列表中存在注册项不等于 MCP 进程已正常启动或索引已经 READY。原有 guthon-page 只是客户端别名，若仍指向同一可执行入口可继续使用；迁移时先删除或停用旧注册项，再新增 guthon-svn，避免同一服务重复启动，勿覆盖其他 MCP 服务。

ZCode

打开“设置 → MCP 服务器 → 新建 MCP 服务器”，作用域选“用户”（本机各工作区共用）或“工作区”，名称填 guthon-svn、类型选 stdio（本地命令），命令填应用绝对路径，参数依次填 mcp、--stdio、--home、本地数据目录绝对路径；添加后确认已启用。若已按上面步骤配置 Codex，可在同一页面点“导入”，从 Codex CLI 配置中只勾选 guthon-svn 导入，不必重复手填。详见 ZCode 官方 MCP 文档。

手工配置 ZCode 时，用户级原生文件为 ~/.zcode/cli/config.json、工作区级为 <项目根>/.zcode/config.json，服务放在 mcp.servers；也可在“完整配置”模式粘贴下方 mcpServers JSON。但同一作用域内一旦原生 .zcode 配置已有 MCP 服务，.agents/mcp.json 不再合并加载，不要把两处各写一半。个人绝对路径建议保存在用户级配置，避免提交到项目仓库。

CodeBuddy（IDE / CodeBuddy Code）

在 CodeBuddy IDE 侧栏打开“CodeBuddy Settings → MCP → Add MCP”，把下列配置加入 JSON 文件，保存后在服务旁点击“Try to Run”检查状态；随后在 Craft Agent 中提出 PAGE 或过程函数查询/修改任务。CodeBuddy Code CLI 可将同一配置保存到个人 ~/.codebuddy/.mcp.json，或仅对某项目放在 <项目根>/.mcp.json；已有文件时合并 mcpServers 对象，不覆盖其他服务。项目级 MCP 首次连接可能要求用户批准。参见 CodeBuddy IDE MCP 文档与 CodeBuddy Code MCP 文档。

json
{
  "mcpServers": {
    "guthon-svn": {
      "type": "stdio",
      "command": "/应用目录/GuthonCodeTool",
      "args": ["mcp", "--stdio", "--home", "/本地数据目录"]
    }
  }
}

CodeBuddy Code CLI 也可只执行一次下列命令代替手工编辑 JSON；codebuddy mcp list 核对已注册服务，在交互任务中用 /mcp 查看连接诊断：

bash
codebuddy mcp add --scope user guthon-svn -- /应用目录/GuthonCodeTool mcp --stdio --home /本地数据目录
codebuddy mcp list

以上命令行示例同样要求替换真实绝对路径；路径含空格时分别加引号。其他支持 stdio MCP 的 Harness 可按自身官方配置入口复用 command 与 args，不能假设都接受 CodeBuddy 的 mcpServers JSON 或 CLI 命令。

Windows 把 command 指向应用 EXE、--home 后的参数指向本地数据目录；JSON 中的反斜杠要写成双反斜杠，TOML 中可使用正斜杠或正确转义的反斜杠。维护者使用源码开发版时，把 command 换为仓库 .venv 中 Python 的绝对路径，并在 args 最前面加上 /源码仓库/scripts/guthon_tool.py。需要强制只读时，在 --stdio 后加 --read-only，客户端便只发现 14 个查询工具。MCP 服务和 Nexus 可共用同一 toolHome，但客户端连接与工具调用路由须在对应客户端或 guthon-team 中另行配置；安装 GuthonCodeTool 本身不会让 AI 自动调用。

在 AI 任务中调用

连接成功后，向 Harness 明确目标和使用方式。例如：“请使用 guthon-svn MCP，在 workspaceKey=products.<id> 中查询某 PAGE 的脚本/SQL 或某过程函数；先检查对应索引状态和精确身份，再读取当前源码并给出证据。修改时先预览，再以唯一幂等键写入本地 SVN working copy，查询 operation 状态并审阅 SVN diff；不要提交 SVN。”

AI 是否主动选用 MCP 取决于 Harness 的工具发现、审批设置和任务/项目规则。将 PAGE、过程函数查询与受控修改的路由写入团队规则（如 guthon-team），可提高主动选用率；规则仍须要求显式 workspaceKey、身份核对及修改前后检查，不能以“已安装 MCP”代替这些步骤。若工具未出现，Codex 先查 codex mcp list，ZCode 查“设置 → MCP 服务器”的启用状态，CodeBuddy IDE 用“Try to Run”、CodeBuddy Code 用 /mcp 查诊断；再检查路径、作用域/项目信任和进程启动错误，不要直接重建索引。

5.3 查询与排错

  1. 重启或重载 MCP 客户端，确认发现 guthon-svn 及默认 27 个工具。先调用 get_runtime_status，再以明确 workspaceKey 调用 PAGE 的 get_index_status 或过程函数的 get_source_index_status。
  2. 用 search_sources 搜索 PAGE 名称或 ID，并设 sourceType=page、较小的 limit。从结果复制真实 sourceNamespace、sourceId 和 funId；同名对象不猜第一个。
  3. 以完整身份调用 list_page_nodes 或 list_page_fields；从目录选择稳定的 semanticNodeId/semanticFieldId，再用 read_page_nodes/get_page_field 定点读取。若改用 jsonPointer，同时传目录返回的 indexedSourceHash。
  4. 需要局部证据时调用 get_source_context 或 list_page_field_relations；check_page_field_references 只提示显式和未解析引用风险，不能证明字段可安全删除。
json
{"name":"get_index_status","arguments":{"workspaceKey":"products.<id>"}}
{"name":"search_sources","arguments":{"workspaceKey":"products.<id>","sourceType":"page","keyword":"页面名或 PAGE ID","limit":20}}
{"name":"list_page_nodes","arguments":{"workspaceKey":"products.<id>","sourceNamespace":"从搜索结果复制","sourceId":"从搜索结果复制","funId":"从搜索结果复制","limit":20}}

过程函数先以 sourceType=procedure 调用 search_sources，复制结果中的完整 sourceNamespace、sourceId、funId 和 workingCopyId，再用 read_procedure 按 offset/maxChars 有界读取；如需调用方证据，用 list_procedure_callers。同名或多 working copy 不猜第一个；调用方索引无法区分同别名目标时会拒绝归因。

以上是依次调用的工具名与参数示意，不是直接粘贴到普通终端的命令。MISSING 表示先完成目标 SVN 工作区索引，PARTIAL 表示存在陈旧来源或 projectionGapCount 缺口；不要把非 READY 当作空结果。缺口 PAGE 的定向查询会返回 INDEX_STALE 和精确 sourcePath 刷新提示。结果含 nextCursor 时才继续翻页；CURSOR_STALE 要从第一页重查，SOURCE_STALE/INDEX_STALE 要先核对授权源码和目标工作区索引，不能沿用旧 Pointer。MCP 查询不代替 Nexus 的 SVN 差异审阅、平台运行或业务验收。

5.4 受控修改 PAGE 节点

默认 MCP 允许 AI 对已授权 SVN working copy 中的稳定脚本/SQL 字符串节点发起本地修改；同一字段集合内的单字段新增/拷贝见 5.6。任意 PAGE JSON 属性、字段集合整体替换及反射组不能经当前 MCP 写入。操作前应确认目标 workspaceKey、PAGE 身份、当前文件差异和工作区 edit 能力；仅仅发现写入工具不代表某个对象已获写入许可。

  1. 从 list_page_nodes 的结果选定 identityStability=STABLE 且 nodeType=SCRIPT 或 SQL 的目标，调用 open_page_node_edit 获取绑定当前源码与授权状态的短期 editToken。
  2. 用 preview_page_nodes 提交 editToken 和新 content，检查候选 hash、变更摘要和错误；预览不落盘，也不保证后续写入时源码仍未变化。
  3. 确认修改后用同一批 token 和内容调用 update_page_nodes，提供调用方生成并保存的唯一 idempotencyKey（8–128 个无空格的可打印 ASCII 字符）。多个节点必须属于同一份 PAGE，服务会重新预检并一次写入本地文件。
  4. 保存返回的 operationId。响应丢失时先用 get_page_operation 按原 idempotencyKey 查询，不要换 key 盲目重试；后置索引或 diff 核验未完成时按 operationId 调用 resume_page_operation。
  5. 最后在 Nexus 的 SCM 中人工审阅 SVN diff，并按项目流程验证；MCP 不执行 SVN commit，也不把本地写入当作谷神平台提交或运行成功。

5.5 受控修改过程函数

过程函数写入只针对完整身份确定且获授权的 SVN working copy 物理文件。调用 open_procedure_edit 获取短期 editToken，以 preview_procedure 提交完整 content 或精确 replacements 检查候选 hash（预览不落盘），再以同一 token、候选和唯一 idempotencyKey 调用 update_procedure。响应丢失时用 get_procedure_operation 按原 key 查询；后置索引或 SVN diff 核验未完成时，用返回的 operationId 调用 resume_procedure_operation。最后人工审阅目标文件 diff；不可将本地写入等同平台运行成功，也不可通过 MCP 提交 SVN。

!

写入依赖编辑租约、源码/索引 hash、授权范围和 SVN 状态的再次核对。真实 MCP 客户端、已安装 VSIX、Windows 与强杀故障矩阵尚未完成验收；出现未完成或外部改动时先查看 operation 状态和实际 diff，不强行覆盖。字段删除、移动与反射组写入仍未开放。

5.6 新增与拷贝 PAGE 字段

仅支持一份 PAGE 中同一个已识别 UI 字段集合的单字段新增或拷贝；不支持跨 PAGE、跨区域/集合、反射组、删除或移动。先用 list_page_fields 获取字段的 collectionPointer、semanticFieldId 和 indexedSourceHash；空集合可从 list_page_nodes 的 FIELD_COLLECTION 节点取 Pointer。目标必须属于表单、查询、主表或明细表组件，且当前索引与源码一致。

  1. 调用 open_page_field_insert，传完整 PAGE 身份、collectionPointer、indexedSourceHash 和 action=add 或 copy。新增时传完整 field 对象（至少有 fieldId、type）；拷贝时传同集合来源的稳定 sourceSemanticFieldId、新的 newFieldId，可选 newLabel。可用 afterSemanticFieldId 指定同集合插入锚点，否则追加。服务始终生成字段自身的新 id；若候选带 guid 键则重生成，否则保持无 guid，不会把缺失值当成重复身份。返回固定候选和短期 editToken；不要自行改写 token 内的候选。
  2. 调用 preview_page_field_insert 核对候选 hash、字段编码和插入位置。预览不落盘，且不是正式写入的并发保证。
  3. 确认后以同一 editToken 和唯一 idempotencyKey 调用 insert_page_field。响应丢失先用共享的 get_page_operation 按原 key 查询；后置索引或 SVN diff 核验未完成时用 resume_page_operation，不要换 key 再插一次。
  4. 人工审阅目标 PAGE 的 SVN diff，确认字段配置、顺序、引用与平台行为；MCP 不执行 SVN commit。

本阶段拒绝字段编码重复、来源身份不稳定、双重编码 PAGE、疑似反射或未解析字段引用。复制仅重置字段对象自身的身份，不改嵌套配置中的 ID，也不自动修正脚本和关联关系。新增/拷贝已在临时 SVN 夹具及真实工作副本完成本地验证；真实测试改动已受控撤销且未提交 SVN。已安装包、Windows、平台运行与业务行为仍需单独验收。

6. 日常工作流

每次开发先确认目标 PRD/PRJ 和源码来源。DATABASE 与 SVN 按下面各自的流程执行。

6.1 DATABASE 工作流

  1. 在“项目”树选择目标 PRD 或 PRJ。
  2. 点击“同步工作区全部资料”。
  3. 确认同步没有 FAIL，再从 Workcopy 开始开发。
  4. 需要网页辅助时启动 Bridge，从谷神页面拉取目标对象。
  5. 只修改 Workcopy；不要修改 readonly。
  6. 完成后点击“检查或打包 Workcopy”，查看 diff.md。
  7. 将确认后的内容复制回谷神平台，完成平台测试和提交。

6.2 SVN 工作流

开始开发

  1. 点击“检出/更新完整 SVN 仓库”。
  2. 等待更新和索引完成；不要重复点击正在执行的操作。
  3. 从“谷神源码”打开 PAGE、过程函数或系统脚本。过程函数调用可用 Cmd 点击或“转到定义”打开目标函数，@子方法(...) 可跳到当前文件的 #function 声明；从调用处打开的目标也可用源码树的定位按钮反向定位。

修改与检查

  1. 修改后按 Ctrl+S（macOS 为 Cmd+S）保存到本地。
  2. 在“谷神源码”树查看带 M 的文件。
  3. 在“源代码管理”点击文件，查看“SVN BASE ↔ 工作副本”差异。
  4. 旧编辑器提示冲突时，重新打开文件；不要强制覆盖。

提交或更新

  1. 先执行“检查远端变更”。
  2. 提交全部范围：使用工作区根节点的“提交 Nexus 修改”。
  3. 提交子系统：使用对应中文分组的提交按钮。
  4. 提交文件：选择一个或多个文件，再执行“提交所选 Nexus 修改”。
  5. 看到 SVN revision 后，到谷神平台完成最终提交和运行验证。

发生冲突

  1. 文本冲突：点击“打开 SVN 三方合并”。
  2. 保存合并结果，再点击“标记 SVN 冲突为已解决”。
  3. 属性冲突、树冲突、新增或删除：停止提交，交由维护人员处理。
  4. 在“工作区驾驶舱”查看最近一次 SVN 提交回执。
!

Ctrl+S/Cmd+S 只保存到本地；冲突必须先完成三方合并并显式标记已解决，不能直接强制提交。SVN 提交成功也不等于谷神平台已最终提交。

定位源码与只读排查

  • 使用“搜索工作区完整索引”查找源码、调用、条件、赋值、异常和表读写。
  • 选择搜索结果后，可打开源码或复制精简/详细 AI 上下文。
  • 需要 AI 直接定位 SVN PAGE 节点、过程函数、界面字段和引用证据，或受控修改 PAGE 脚本/SQL 节点与过程函数时，按第 5 章配置 SVN MCP；PAGE 查询层也供 CLI svn page-query 和 Nexus 后端复用。Nexus 的 SVN 源码树可对 PAGE JSON 执行“浏览 PAGE 语义节点”，按页选择并源码复核后打开现有虚拟文档。
  • 排查数据库前先在“配置资料 → 配置数据库排查”选择明确环境。
  • 快速查询只用于只读证据；功能验收仍需正式测试流程。

6.3 更新工作流

更新 GuthonCodeTool

  1. 确认没有同步、SVN 或 Bridge 操作正在执行。
  2. 在“运行模式”选择 GitHub 或 Gitee 更新源。
  3. 点击“检查更新”，确认版本后执行更新。
  4. 更新异常时点击“回退到上一版本”。
  5. VSIX 或 Chrome 扩展有变化时，从同一 Release 重新安装。

更新 guthon-team

Codex 在终端执行：

  1. 执行 codex plugin marketplace upgrade guthon-team。
  2. 执行 codex plugin add guthon-guard@guthon-team。
  3. 从目标 var/ 或业务子目录打开新任务。
  4. 运行 $guthon-bootstrap status，确认状态为 ready。
  5. 如果 AGENTS.md 有变化，再打开一次新任务。

CodeBuddy 在对话输入框执行 /plugin marketplace update guthon-team、/plugin update guthon-guard@guthon-team --scope user 和 /reload-plugins，然后从目标 var/ 或业务子目录打开新任务。若客户端不支持更新命令，可在插件管理界面按 3.1 节重新安装；不要删除工作区中的规范文件。

7. 其他

7.1 系统差异

macOS

  • 当前支持 M1 及后续型号，Intel Mac 不支持。
  • 应用没有执行权限：执行 chmod +x 后重新选择应用。
  • Gatekeeper 阻止：确认下载来源后，在“隐私与安全性”中选择“仍要打开”。
  • 终端设置的数据库环境变量未被 VS Code 读取：从同一终端启动 VS Code，或按公司方式配置用户环境后重启 VS Code。

Windows

  • 当前只提供 Windows x64 EXE。
  • SmartScreen 阻止：确认下载来源后使用“更多信息 → 仍要运行”。
  • 目录链接失败：开启 Windows 开发人员模式，或由管理员完成首次同步。
  • 路径过长：使用 D:\GuthonCodeToolData 等短路径，并按公司策略启用长路径支持。
  • 终端环境变量未生效：关闭并重新打开 VS Code 和 PowerShell。

7.2 迁移与删除

迁移电脑

  1. 停止 Bridge、同步和 SVN 操作。
  2. 安全复制整个本地数据目录。
  3. 在新电脑安装同一版本的应用、Nexus 和 Bridge。
  4. 执行“设置工作空间”，选择复制后的本地数据目录。
  5. 运行“检查本地环境”，再分别验证一个 DATABASE 和 SVN 工作区。

删除产品或项目

  1. 右键目标 PRD/PRJ，选择“删除产品或项目”。
  2. 核对配置、独占数据源、数据库排查条目、工作区目录和 SVN checkout。
  3. 确认无误后执行删除。目标目录会进入系统废纸篓。
  4. 确认其他工作区和共享配置仍然存在。

升级或迁移时不要删除本地数据目录。删除 guthon-team 工作区治理文件需要按锁文件逐项核验，不要直接删除整个 docs/、tools/、.guthon/ 或 .githooks/。

7.3 常见问题

更多 macOS、Windows、DATABASE、SVN、Nexus 与 Bridge 部署和环境问题，请进入 GuthonCodeTool 问题解决中心，可按系统、源码模式和错误原文搜索。

左侧没有“Guthon Nexus”图标

确认 VSIX 已安装并启用，执行“Developer: Reload Window”；仍未出现时卸载旧版本后重新安装当前 Release 的 VSIX。

点击功能后提示启动失败

重新执行“设置/切换工作空间”，选择未改名、未移动且属于当前系统的应用。macOS 同时检查执行权限。

项目树没有显示某个产品或项目

打开 products.yaml 或 projects.yaml，检查 ID、名称和 datasource 是否填写正确，保存后点击 Nexus 刷新。

Bridge 显示无法连接

  1. 确认 Guthon Nexus 面板显示 Bridge“运行中”。
  2. 停止后重新启动 Bridge，并在“输出 → Guthon Bridge”查看第一条错误。
  3. 若错误包含 EADDRINUSE，关闭其他终端或旧版工具中仍在运行的 Bridge，再从 Nexus 启动。
  4. 重新加载 Chrome 扩展并刷新谷神页面。

Workcopy 与 readonly 不一致

先打开 diff.md 确认需要保留的内容。不确定时不要覆盖，请联系负责人处理。

SVN SCM 显示“外部修改”

点击“管理本地源码变更”查看差异，再选择保存或撤销。文本冲突使用文件行的三方合并和“标记为已解决”；如果显示属性冲突、树冲突、新增或删除，不要强制操作，请联系负责人处理。
