# 谷神数据库测试工作流开发补充方案

日期：2026-09-07

状态：首版 A/B 工作流已实施；尚未连接真实数据库或执行真实平台验证。

关联：[谷神需求开发与数据库测试工作流设计](谷神需求开发与数据库测试工作流设计.md)。保留原文；本补充方案是本次新增数据库测试能力的实施依据。

## 1. 范围与明确决策

用户已确认开发工作流存在。本次在其开发结果之后接入数据库测试，复用需求理解、源码定位、代码修改、发布和失败修正流程，不重新建设这些步骤。

首版选择 **DBX MCP + 专用只读数据库账号 + 显式测试目标映射 + 用例/报告模板**。AI 调用当前环境实际提供的 DBX 工具，核验数据库并执行只读检查。需要平台业务验证时，由现有流程完成发布和触发，数据库测试步骤负责前置条件及结果断言。

后续确有自动写入测试需求时，再增加 **Guthon CLI + PyMySQL** 执行器，提供参数绑定、同连接事务和清理；首版不建设通用 workflow CLI，也不实现 DBX 凭据导出或数据库连接管理界面。

现有开发工作流的具体存放位置和扩展接口尚未在本任务中核验。Sol 实施时应先定位实际入口，复用其任务标识和产物目录，不根据本方案自行新建另一套开发流程。

## 2. 数据库连接方式

### 2.1 真实连接由 DBX 管理

主机、端口、数据库、账号、密码及连接选项保存在 DBX。工作流只保存 connection ID 和环境映射，不读取、复制或输出密码。

优先使用已有专用只读连接。没有连接时，由用户在 DBX 完成配置；如用户明确授权工具创建连接，需在当时核验工具契约和凭据输入方式。不得从 SVN 脚本、日志或其他项目配置中寻找凭据。

连接可用还依赖运行 DBX 的机器具备内网/VPN、网络路由及必要的 TLS 配置。工作流记录连接失败类型和修复提示，不自动修改网络配置或关闭证书校验。

只读账号应仅拥有所需业务库表的查询权限，不具备写入、文件操作或执行有副作用函数的权限。提示词要求“只读”不能替代数据库授权；若账号权限无法确认，记录该限制，不承诺执行器已强制只读。

### 2.2 工作区与测试连接显式映射

建议私有配置采用 `<descriptor.home>/config/database-testing.yaml`；若现有流程已有合适配置入口，直接并入其扩展区。以下字段是拟新增设计，不代表当前程序已支持：

```yaml
schemaVersion: 1
databaseTests:
  projects.demo:
    targets:
      - id: trade-dev
        systemId: SYS-DEMO
        dataSourceId: DS-DEMO
        connectionId: "<DBX connection ID>"
        database: demo_trade
        environment: dev
        access: read-only
        expectedIdentityRef: demo-trade-dev
        allowedTables: [DEMO_ORDER, DEMO_ORDER_DETAIL]
        tenantScope: demo-tenant
```

映射使用现有环境命名 `dev` / `test`。`expectedIdentityRef` 指向私有环境核验资料，包含预期端点、库及项目可用的环境身份依据。`tenantScope` 须映射到实际业务字段或平台上下文，不能把示例字符串直接用于真实 SQL。

公开仓库只保存脱敏模板；真实映射、连接 ID、用例参数和查询结果留在私有目录。DBX 连接 ID 在不同机器上可能不同，每台机器分别绑定，不跨机器假设一致。

### 2.3 选择与核验顺序

1. 接收已有流程解析出的显式 workspaceKey，以及本次修改对象的系统、数据源和数据路由证据。
2. 按工作区、对象路由和用例输入匹配唯一 target。动态路由无法确定、映射缺失或多个候选时，停止依赖该目标的查询并说明缺项。
3. `dbx_list_connections` 核对 connection ID、数据库类型、端点和默认库；不把全部连接详情写入公开报告。
4. 使用明确 connection ID 和 database 读取结构及必要身份信息，核对实际库、环境、租户范围与代码字段。
5. 核验通过后，将目标摘要绑定本次 runId。连接映射、源码或环境变化后重新核验。

源码 datasource 不必然是业务数据库连接；禁止从目录 PRD/PRJ、连接名称含“开发”、同名表或上次连接结果推断目标。跨库或多数据源函数要逐个声明目标和执行步骤，不默认跨库访问已授权。

SVN 始终承担源码读取和受控编辑职责。现行私有工作区规则禁止因缺少数据自动连接数据库，实施时应在对应授权下补充“显式数据库测试目标”能力规则；未完成衔接前，不能用本设计直接绕过限制或切换 provider。

## 3. 使用工具及边界

| 工具 | 使用阶段 | 注意事项 |
|---|---|---|
| `dbx_list_connections` | 目标发现和映射核验 | 保存 ID；不按名称模糊选择 |
| `dbx_get_schema_context` | 获取少量相关表的字段上下文 | 仅请求本次涉及表 |
| `dbx_describe_table` | 核对具体表字段定义 | 具体参数以当时工具 schema 为准 |
| `dbx_execute_query` | 只读前置检查、聚合、结果断言 | 显式 connection ID/database；结果最多 100 行 |
| `dbx_open_session` | 需要会话变量等连续上下文时 | 不是每个用例必需；不能直接视为事务保证 |
| `dbx_close_session` | 会话结束时释放资源 | 关闭会话不等于已核验回滚 |

当前 DBX 工具契约支持有状态 session，空闲 30 分钟后可能过期；`execute_query` 未暴露驱动式参数绑定接口。首版以普通只读查询为主，不通过 DBX 自动执行 DML、DDL、存储过程或测试数据清理。

查询值须按实际数据库方言正确处理；不将自由文本直接插入 SQL，不允许参数承载 SQL 片段。无法可靠构造查询时，报告该用例受阻，或交给后续支持绑定参数的执行器。表名和库名只允许来自已核验结构与配置。

单条 SELECT 仍可能含副作用函数、跨库访问或锁等行为；首版只执行可确认安全且有明确过滤范围的查询，数据库最小权限承担最终限制。需要强制 SQL 策略、服务端超时、绑定参数或同一快照时，再由执行器提供机械约束，不能把 AI 检查写成已具备这些能力。

返回结果可能同时存在行截断和单元格截断。COUNT、金额汇总、唯一性与缺失记录检查优先使用返回少量标量的 SQL；完整明细集合断言需要证明没有截断，不能直接比较前 100 行后宣称全部通过。

工具不可用、连接失败或所需方言不支持时，保留用例和具体阻碍。不得静默切换到另一连接或从 DBX 导出凭据改用 CLI。

## 4. 与现有开发流程的输入输出

### 4.1 输入

最小输入：现有 taskId、workspaceKey、sourceMode、本次修改对象/差异及版本摘要、需求验收条件、业务触发入口、涉及表和路由证据。平台测试另需待测版本生效依据。

缺少动态路由等信息时，数据库测试步骤应返回具体待补项给原流程；不重复生成整份需求分析或重新定位所有源码。

### 4.2 用例

每个用例至少包含：

- caseId、requirementIds、关联源码位置及版本摘要。
- targetId、测试层级、租户/业务主键范围。
- 前置条件查询、执行动作、结果查询及独立预期值。
- 断言类型、必要的精度、超时/观察截止时间。
- 运行证据、失败原因；需要平台写入时补数据准备和清理责任。

预期值来自需求或独立计算，不用被测 SQL 的输出自动充当期望值。金额和数量按实际业务精度处理；空数据不自动等于成功。

### 4.3 执行步骤

```text
现有开发结果
  → 读取改动和验收条件
  → 生成数据库测试用例
  → 解析并核验 DBX 测试目标
  → 查询结构和前置数据
  → 只读查询验证／等待现有流程完成平台触发
  → 查询结果并执行断言
  → 返回报告或失败证据给现有开发流程
```

新增的输出建议为 `database-test-plan.json` 和 `database-test-report.md`，存放在现有任务私有产物目录。逐项记录 `PASS/FAIL/BLOCKED/SKIPPED`；报告必须关联 runId、源码版本、用例版本及测试目标摘要。修正代码后旧结果保留为历史，重新执行受影响用例。

## 5. 首版测试覆盖

### 5.1 SQL 与数据条件验证

使用 DBX 查询实际表结构、入口状态、过滤分支、聚合结果、重复记录或不变量。该层证明指定数据库和数据范围内的查询结果，不证明本地函数已运行。

谷神 GSS/Velocity 不是普通 SQL。不能通过简单替换平台表达式来模拟权限注入、临时表或事务逻辑。实际 SQL 无可靠来源时，使用平台执行后的结果断言，或明确缺少执行入口。

### 5.2 平台业务结果验证

对于保存、确认、取消、事件、调度等行为：

1. 现有流程核验本次修改已在正确开发平台生效，保存对象版本/回读和运行证据。
2. DBX 查询业务主键对应的前置状态。
3. 由现有页面/API/调度入口按已有授权触发，不由数据库测试步骤重建发布能力。
4. DBX 查询同一业务主键的最终状态、汇总及下游数据，关联实际运行记录。
5. 异步任务设置明确观察截止时间，每次读取需能看到新提交数据；超时不盲目重复触发。

平台测试可能持久化数据。数据准备、取消/删除及残留处理按现有流程和授权完成，首版 DBX 只读账号不承担清理写入。无可用测试数据或清理方案时，只完成可执行的只读验证，平台用例标记受阻。

## 6. 后续事务测试执行器

只有存在重复执行的写入验证、绑定参数或可靠事务控制需求时，才新增 `db-test` CLI。建议一个独立测试模块承担解析、执行、断言和报告，复用 `gusen_hub.py` 的工作区及数据源解析，不新建整套 workflow 引擎。

CLI 使用现有私有 datasource 配置和环境变量，通过 PyMySQL 连接；不直接使用 DBX connection ID，也不读取 DBX 密码。测试目标明确指定执行后端和 datasourceRef，切换后端需重新核验实际环境，禁止静默回退。

首版驱动实现限定 MySQL。事务测试必须保持同一连接，使用参数绑定，限制表/主键和影响行数，排除非事务表、隐式提交及外部副作用；失败回滚后核验残留。平台进程看不到另一未提交事务的夹具，平台测试不能承诺由 CLI 事务统一回滚。

现有 `run_source_diagnosis.py` 是仅允许特定 test 数据源的只读诊断器，保留其环境与 provider 限制；不得为了新增能力直接放宽旧 `diagnose`。只复用语义一致的现有实现，避免复制整份脚本后改条件。

## 10. 首版运行形态与责任划分

首版由已有 AI 工作流调用 DBX MCP；普通 Python 脚本不能直接调用只在 AI 会话中暴露的 `tools.mcp__dbx__...`。Sol 不应在 CLI 中硬编码这些工具名并假设它们可运行。

| 组件 | 首版承担的职责 |
|---|---|
| 现有开发工作流 | 提供需求、修改对象、版本和运行证据；接收失败反馈 |
| 数据库测试工作流指令 | 根据证据生成用例，顺序调用 DBX，识别不完整结果和业务失败 |
| 本地确定性校验模块 | 校验配置和用例，计算受支持断言，生成报告；不负责连接 DBX |
| DBX MCP | 使用已配置连接执行结构查询和只读 SQL |
| 数据库账号 | 提供数据库层面的只读权限边界 |

优先复用已有模板加载、JSON 校验和报告代码。若没有可复用模块，可新增一个 `scripts/common/database_test_artifacts.py`，集中处理配置/用例校验、断言和报告；此路径为建议，实际落点以现有架构为准。无需为每个步骤拆一个类或新增通用调度器。

本地模块使用规范化结果文件作为输入。AI 必须保留工具原始证据引用，不手工补出缺失行或猜测截断标记；工具返回格式无法可靠识别时，标记 `RESULT_UNSUPPORTED`，禁止当作空结果处理。

如果现有工作流已有 MCP 编排 SDK，可复用其经过验证的调用能力；否则保持 AI 调用 DBX、本地模块处理产物的分工，不为首版另建 MCP 客户端和凭据服务。

## 11. 配置校验与首次配置体验

### 11.1 校验规则

- `schemaVersion` 首版仅接受 1；不认识的版本或安全相关字段报错，不静默忽略。
- `workspaceKey` 必须与现有流程解析结果完全一致；target ID 在该工作区内唯一。
- `connectionId`、`database`、`environment` 和环境身份资料必填；环境只允许 `dev/test`。
- 首版 `access` 仅接受 `read-only`，写入配置明确返回不支持。
- `allowedTables` 必须非空，使用明确表名；不支持 `*` 或跨库通配符。涉及视图时另核验其实际数据访问范围。
- 首版自动验证优先支持 MySQL 查询模板。DBX 支持某数据库类型不等于工作流已支持该方言；其他类型仅生成计划，直到具备对应身份查询、字面量处理及断言验证。
- `expectedIdentityRef` 必须能解析；环境身份缺失不得只依赖名称判断。代理/集群环境核验授权服务身份，不强求每次物理节点相同。
- 路由对象可能没有直接 systemId：必须使用调用链提供的明确数据源证据匹配，不自动将缺失字段解释为“任意系统”。

字段规范应写入配置 schema。公开示例包含占位值，校验器要拒绝将占位连接 ID 当成真实配置执行。

### 11.2 首次使用

1. 读取已有目标映射。映射已完整且工具核验通过，直接继续。
2. 未配置时，可列出当前任务相关的候选连接摘要供选择；不询问数据库密码。
3. 缺少的连接由用户在 DBX 配好；首次只补工作区到连接的映射、环境身份和业务数据范围。
4. 用户确认具体映射后，按授权保存到私有配置；后续复用，每次执行仍核验连接和目标身份。
5. 连接删除或 ID 变化时报 `CONNECTION_MISSING`。同名新连接不自动替换原 ID。

普通“测试一下”的请求不应触发全量连接枚举、重新配置或强制用户填整份表单；已知目标直接核验。

## 12. 用例契约与示例

以下为拟定 JSON 契约，表名、列名、主键和期望值均是通用演示。首版保留已具体化 SQL，不引入一个尚未实现的 SQL 模板语言；需要绑定参数的复杂输入交给后续 CLI。

```json
{
  "schemaVersion": 1,
  "taskId": "TASK-DEMO",
  "workspaceKey": "projects.demo",
  "sourceMode": "svn",
  "sourceDigest": "<本次相关源码摘要>",
  "cases": [
    {
      "caseId": "DB-001",
      "requirementIds": ["AC-01"],
      "targetId": "trade-dev",
      "level": "query",
      "sourceEvidence": ["<私有对象与代码位置引用>"],
      "preconditions": [
        {
          "id": "order-exists",
          "sql": "SELECT COUNT(*) AS total FROM DEMO_ORDER WHERE ID = 1001 AND TENANT_ID = 7",
          "assert": {"type": "scalar_equals", "column": "total", "expected": 1}
        }
      ],
      "checks": [
        {
          "id": "no-duplicate-detail",
          "sql": "SELECT COUNT(*) AS total FROM DEMO_ORDER_DETAIL WHERE ORDER_ID = 1001 AND TENANT_ID = 7",
          "assert": {"type": "scalar_equals", "column": "total", "expected": 2}
        }
      ],
      "expectedBasis": "验收样例明确包含两条有效明细",
      "cleanup": {"required": false, "reason": "本用例仅查询已有样例"}
    }
  ]
}
```

`level` 首版接受 `query` 或 `platform-result`。后者额外要求运行环境、版本依据、业务关联 ID 和触发证据引用，尚未获得这些证据时用例保持 `BLOCKED`。用例不能自行声明一个布尔值“已发布”替代证据。

源码摘要覆盖与用例相关的本次对象及必要依赖，不需要散列整个工作区。SVN 同时保留对象片段、物理文件 hash 和 BASE 等已有证据；不要为生成摘要绕过受控读写入口。

前置条件不满足表示样例不可执行，通常为 `BLOCKED/PRECONDITION_UNMET`，不是业务断言失败。如果“该记录必须存在”本身就是验收要求，应放在 checks，缺失时才记 FAIL。

### 12.1 首版断言集合

| 类型 | 语义与约束 |
|---|---|
| `scalar_equals` | 必须恰有一行且指定列存在；值按声明类型比较 |
| `decimal_equals` | 以十进制字符串和声明精度比较，容差来自业务要求 |
| `rows_empty` | 确认成功执行且返回零行；工具异常不能当零行 |
| `row_count_equals` | 只用于已证明未截断的结果；大量记录使用 COUNT 标量 |
| `keyed_rows_equals` | 指定唯一键，验证键不重复后比较集合；不依赖默认排序 |

NULL 与空串、零、缺失列分别处理。首版不支持任意 Python/JS 表达式断言；不认识的断言类型直接拒绝。对于顺序要求，SQL 必须有确定 ORDER BY，并在后续增加明确的有序断言类型，不能借集合比较声称排序通过。

## 13. DBX 调用顺序与结果规范化

常规查询不需要有状态 session，按下列依赖顺序执行：

1. 检查当前会话可调用的工具及其参数，不假设下一会话工具前缀不变。
2. 找到映射中的 connection ID，核验连接类型与端点。
3. 显式传 connection ID/database 获取相关 schema；执行该方言已核验的身份查询。
4. 校验用例引用的库、表和列。SQL 有无法确认的跨库、函数或副作用时不执行。
5. 顺序执行前置条件；不足时停止该用例，其他独立用例可继续。
6. query 用例执行 checks；platform-result 用例先取得现有流程的运行证据再执行 checks。
7. 将每次返回转成规范化结果，交给断言模块，再生成报告。

规范化结果至少包含 `runId/caseId/stepId/targetId/startedAt/finishedAt/status/columns/rows/truncation/rawEvidenceRef`。truncation 应区分 `none/rows/cell/unknown`；unknown 不能满足完整集合断言。

SQL 和结果的真实字段类型要保留。日期保留数据库及会话时区依据；金额不能先转浮点再比较。原始工具证据和规范化结果都留在私有路径，公开输出只给必要摘要。

不需要跨步骤一致性时，不开启长事务。若业务断言必须同一快照而 DBX 当前能力未经过验证，则该用例受阻并转执行器需求；不得用相邻两次独立查询冒充同一快照。

有状态 session 只用于已核验且确有必要的连续上下文；创建后在结束/失败时关闭。session 过期要重新核验上下文，不能自动重建临时表或重放未知写入。首版默认不创建临时表。

## 14. 失败、恢复与报告格式

### 14.1 错误分类

| errorCode | 处理 |
|---|---|
| `TOOL_UNAVAILABLE` | 保留计划，说明缺少的 DBX 能力 |
| `CONNECTION_MISSING` | 请求补连接映射，不按名称自动替换 |
| `BINDING_AMBIGUOUS` | 给出与本需求相关候选及歧义依据 |
| `ENVIRONMENT_MISMATCH` | 停止该目标所有用例，不切到其他库 |
| `SCHEMA_DRIFT` | 返回实际字段差异给开发流程，不自动改表 |
| `PRECONDITION_UNMET` | 标记样例不足，继续不依赖它的用例 |
| `RESULT_TRUNCATED` / `RESULT_UNSUPPORTED` | 缩小查询或改用聚合；不判完整结果通过 |
| `VERSION_UNVERIFIED` | 保留只读检查结果，阻止平台结果通过 |
| `ASSERTION_FAILED` | 保存预期、实际及证据，交回开发流程 |
| `QUERY_TIMEOUT` | 返回执行状态；确认前一查询终止后才考虑重试 |

首版没有可靠取消能力时，不自动重试超时查询，避免前一查询仍在数据库运行。纯连接建立失败可在连接条件恢复后重新开始；平台触发不由本步骤自动重试。

恢复时复核源码摘要、测试计划摘要、target 映射和平台版本。只有输入未变且证据仍有效的步骤可复用；新的 runId 关联旧报告，不覆盖历史结果。

### 14.2 报告必须回答的问题

```text
任务 / runId / workspaceKey：
源码摘要 / 测试计划摘要：
测试目标：脱敏环境、库及绑定 ID
目标核验：PASS / BLOCKED，依据引用

用例 | 验收条件 | query/platform-result | 状态 | 预期 | 实际 | 证据

平台版本与触发证据：有 / 无 / 不适用
未覆盖项与原因：
数据准备和清理结果：不适用 / 已完成 / 待处理
需要开发流程处理的问题：
```

整体通过要求所有必需用例 PASS，平台用例版本可核验，必要清理已完成。存在必需 SKIPPED/BLOCKED 时不得显示“全部测试通过”；允许明确“已执行的 3 项查询通过，2 项平台验证受阻”。

## 15. 实际开发清单与完成标准

Sol 开始时先产出一份简短接入清单：现有工作流入口路径、接收开发产物的位置、调用 DBX 的执行环境、私有配置根、报告根和生效规则。能从项目查出的信息自行核验，只有确实缺少时才询问。

实施内容限定为：

1. 给现有流程增加数据库测试入口和返回开发修正的分支。
2. 增加目标映射示例及 schema；真实映射不自动生成猜测值。
3. 增加用例/规范化结果 schema、有限断言和报告模板。
4. 增加 DBX 顺序调用说明、结果完整性检查、平台证据衔接。
5. 为确定性模块增加本地测试；准备一个不依赖真实私有数据的演示任务。
6. 有实际开发连接授权后，运行一个只读试点，再运行一个由现有流程触发的平台结果验证。

至少验证以下可观察结果：

| 测试输入 | 预期输出 |
|---|---|
| 两个 target 同时匹配 | BINDING_AMBIGUOUS；不执行业务查询 |
| 返回空结果但调用报错 | 工具/查询失败；rows_empty 不通过 |
| 100 行返回且完整性未知 | 集合断言受阻；COUNT 方案可单独验证 |
| 标量 NULL 与期望 0 | 断言失败，不隐式补零 |
| 金额字符串按业务精度相等 | decimal_equals 按精度通过，无浮点误差 |
| 两行具有同一声明唯一键 | keyed_rows_equals 失败 |
| 前置订单不存在 | PRECONDITION_UNMET；不触发平台业务 |
| 本地代码已变更但报告仍指旧摘要 | 旧结果过期，不计入本次通过 |
| 平台版本未知但结果碰巧正确 | VERSION_UNVERIFIED |
| 用户工作区存在无关修改 | 文件与暂存状态保持原状 |

模板和模块测试通过只表示工作流实现的相应逻辑通过。真实连接、账号只读约束、环境身份和平台入口必须分别验证；没有这些条件时交付可用设计/实现及阻碍，不声称完成真实业务闭环。
