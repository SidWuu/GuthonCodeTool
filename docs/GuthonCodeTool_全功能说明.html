1. 产品定位与设计原则

1.1 功能边界

GuthonCodeTool 把谷神平台的源码与元数据整理为按产品或项目隔离的本地工作区。开发人员可以同步 PAGE、过程函数、系统脚本及数据库元数据，也可以从已授权的 SVN 仓库检出源码；随后通过本地索引完成搜索、跳转、调用关系分析、差异审阅和受控修改。

工具负责工作区路由、源码同步、索引、受控编辑、差异与交付证据，以及 Nexus、Bridge 和 SVN MCP 所需的共享本地能力。
平台负责谷神页面中的编译、发布、运行和业务验证。这些结果按需要另行核验；源码交付以成功提交的 SVN revision 为准。
本地私有真实配置、凭据、源码、索引、日志和业务资料只保存在显式选择的本地数据目录中。

1.2 核心设计选择

设计原因
一个工作区只选择一个源码 provider
DATABASE 或 SVN。		防止同一对象同时出现两个事实来源，避免同步、编辑和交付时无法判断哪一份有效。
产品与项目使用稳定 workspaceKey
products.<id> 或 projects.<id>。		目录名、显示名和当前窗口都会变化；稳定键能让 CLI、Nexus、Bridge、MCP、数据库目标和索引指向同一边界。
工具源码与运行数据分离升级或切换开发/发行入口时不搬迁私有数据，也不会把业务源码和凭据误带入公开仓库。
DATABASE 与 SVN 使用不同写入模型数据库导出是快照，适合 readonly/workcopy；SVN checkout 本身已有版本基线，再复制一份会制造额外冲突。
AI 默认读取索引与有界证据减少扫描和上下文体积，同时保留路径、对象身份、调用位置和 hash，使结论可回到源码核验。
所有高风险操作显式触发源码覆盖、SVN 更新、提交、撤销和工具升级都会改变本地或远端状态，必须由开发人员明确选择范围。

2. 运行架构

2.1 组件职责

text
Guthon Nexus（VS Code） ──┐ 展示工作区、源码、索引与 SCM；管理 Bridge
Guthon Bridge（Chrome） ──┼─→ GuthonCodeTool（Python CLI 与共享实现）
AI 客户端 → SVN MCP ──────┘    ├─ 工作区解析、同步、索引、Workcopy
  独立 stdio 进程              ├─ DATABASE provider
                             └─ SVN provider → 授权 checkout + context/index.db
  • 统一 CLI：scripts/guthon_tool.py 负责编排命令；scripts/common/gusen_hub.py 复用工作区解析、同步状态、索引和 Workcopy 规则。
  • DATABASE provider：读取配置的数据源，导出源码及元数据，并提供受限的只读数据库排查。
  • SVN provider：管理根检出、授权清单、虚拟对象投影、文件写入、SCM、冲突和交付回执。
  • Nexus：只通过参数数组启动工具，不经过 Shell；因此路径、空格和 Windows/macOS 参数行为一致。
  • Bridge：由 Nexus 使用 VS Code 自带的 Node 运行环境启停，普通用户无需另装运行时。
  • SVN MCP：由已配置的 AI 客户端独立启动 stdio 服务；对显式 SVN 工作区调用共享 PAGE/过程函数查询与受控修改服务，默认暴露写入工具，但每次写入仍需授权和编辑租约。

2.2 目录与调用链

text
<toolHome>/
├── GuthonCodeTool/                 # 可公开、可替换的工具源码
├── config/                         # 真实运行配置
├── docs/private/                   # 本机私有资料
└── var/                            # 独立的私有工作区
    ├── AGENTS.md
    ├── tools/guthon-lint
    ├── nexus/{bridge,tool-runtime.json}
    ├── checkout/<配置 ID>/         # SVN working copy
    └── workspace/<工程>/
        ├── source/{readonly,workcopy}/  # 仅 DATABASE
        ├── database/                   # 仅 DATABASE
        └── context/{index.db,state.json,source-mode.json,logs}/

toolHome 只能由 --home、运行描述文件或对应环境变量显式提供。源码不能沿父目录猜测 config 或 var，因为这种猜测会让开发仓库、发行应用和用户数据相互污染。

Nexus 将当前应用入口、toolHome 和运行模式写入运行描述文件，Bridge 据此使用同一工作空间。MCP 客户端需单独配置可执行入口及显式 toolHome；它不会因 Nexus 切换模式而自动重写客户端配置。配置和工作区分别按请求加载，不使用全局“当前工作区”。

3. 工作区与配置

3.1 稳定身份与配置

  • datasource.yaml：数据源注册和 DATABASE 连接引用。
  • products.yaml：产品名称、稳定 ID、数据源、子系统范围和可选 SVN 根地址。
  • projects.yaml：项目快照的独立配置。项目与产品并列管理，不保存产品工作区引用。
  • source-tables.yaml：DATABASE 源码表及语义字段映射。
  • sync.yaml：公共同步规则、SVN 用户名、拉取校验和白名单；不保存默认工作区。
  • context/source-mode.json：当前工作区的 DATABASE/SVN 选择；缺失时采用 DATABASE。

所有调用方必须传递同一 workspaceKey。Bridge 在缺少该键时只能根据页面身份查找候选；如果存在多个匹配项，选择仅对当前请求有效，不写入全局状态。这样多个产品、项目和窗口可以同时工作而不串线。

3.2 创建、切换与删除

  1. 首次设置：setup 只创建缺失的公开模板和空注册表，不覆盖已有配置。
  2. 添加工作区：向导收集产品/项目、名称、稳定 ID 和源码模式，随后原子写入相关注册表。DATABASE 和 SVN 的连接细节在对应模块继续配置。
  3. 切换 toolHome：Nexus 先在候选目录执行设置与验证，通过后才保存新目录。失败或取消不会破坏当前可用配置。
  4. 切换源码模式：只更新目标工作区的 source-mode.json，不会影响其他工作区。
  5. 删除工作区：先显示目录、配置和独占资源的精确范围；确认后把工作区目录移入系统废纸篓，并只删除对应注册项和专属配置。

项目删除不会连带删除产品；共享数据源也不会因某个工作区删除而被误删。该设计把“身份”“物理目录”和“可共享资源”分别核对，避免用目录递归推断业务关系。

3.3 命令与运行描述

统一 CLI 覆盖以下功能族：

设置与路由setup、workspace-create/delete、workspaces、workspace-resolve、workspace-summary、source-mode、route。
同步与索引sync-source、sync-source-all、sync-all、pull、reindex、search、context-pack。
数据与源码元数据导出、数据库目标解析与只读查询、Workcopy 操作，以及完整的 svn 命令族。

workspace-resolve 可从当前工作目录返回唯一工作区、provider、索引就绪度和下一步建议，不读取源码正文。它用于让 Agent 先确定边界，再执行小范围检索；若路径无法唯一对应工作区则明确失败。

4. DATABASE 模式

4.1 源码与元数据同步

DATABASE provider 根据目标工作区的数据源、子系统范围和语义映射读取 PAGE、过程函数与系统脚本，生成结构化的 source/readonly。PAGE 保存原始 JSON，同时拆出 GSS、JavaScript、SQL、事件和组件脚本；过程函数按包与函数组织；项目快照内的继承关系只使用同一快照的数据，不跨到产品工作区。

元数据导出包含表结构、单据类型、系统脚本和视图。sync-all 固定执行“源码与索引 → 表结构 → 单据类型 → 系统脚本 → 视图”。任一步失败或执行期间配置摘要改变，后续步骤都会停止；只有全部成功才把工作区标记为 SYNCED。这样“同步完成”代表一个一致快照，而不是五个时间点不同的局部结果。

4.2 Workcopy 开发

  1. 从 readonly 创建目标对象的 Workcopy，并保存来源身份。
  2. 开发人员只修改 source/workcopy，readonly 始终表示最近一次数据库导出。
  3. workcopy status 汇总状态，diff 生成差异，package 生成可交付清单。
  4. 再次拉取时，默认直接比较新 readonly 与现有 workcopy；存在差异便保留 workcopy，防止覆盖开发修改。

rules.pull_diff_check 默认启用。只有显式关闭时才允许拉取覆盖 workcopy。自动 Git 暂存也只处理本次新生成且原本未跟踪的目标文件，不会暂存已有修改、其他工作区文件或被忽略内容。

采用双目录是因为数据库导出没有版本控制工作副本。readonly 提供可重建基线，workcopy 保留人工修改，两者的差异就是需要审阅和回填平台的内容。

4.3 只读数据库排查

工具可按工作区、开发/测试环境和私有目标配置解析数据库连接，并支持 MySQL、PostgreSQL 与 Oracle。密码写入系统凭据库，配置只保存连接引用；每个目标可限制可见 database、schema 和表。

  • database-probe：验证驱动、连接和只读能力。
  • database-describe：在白名单内读取表结构，避免猜测字段。
  • database-query-readonly：只接受单条 SELECT，限制返回行数并始终回滚事务。
  • 可选 DBX 连接只在配置了 connectionId 时使用；缺失绑定会明确报告，不自动猜测其他连接。

diagnose 还提供配置驱动的源码逻辑排查：它只允许显式标记为测试、启用只读诊断并声明数据库白名单的数据源，按模板逐步执行绑定参数的单条 SELECT，在首个不满足条件的位置停止并生成本地排查报告。该能力适合重复执行的固定检查链；临时问题则使用目标解析、结构描述和有界查询逐步取证。

数据库快速排查从当前工作区和开发/测试环境解析明确目标；未指定环境时使用配置中的诊断默认目标，而“测试一下”只是连接探测，不代表已切换到测试库。功能验收、回归和交付应使用正式测试目标与测试计划/结果证据，不能把一次只读查询当作完整验证。可选的 Guthon Testing Skill 提供该工作流指导，其安装与数据库连接配置是两个独立步骤。

这些限制使数据库能力适合诊断和验证，而不会把开发工具变成任意 SQL 执行器。查询命中只证明数据库证据，不等同于页面结果或已部署版本验证。

5. SVN 模式

5.1 检出与认证

每个 SVN 工作区配置一个仓库根地址，并完整检出为一个 repository-root。系统和数据源映射只负责对象身份、中文名称与业务分组，不裁剪检出目录。完整根检出保证跨子系统引用、公共源码和同名对象都有共同 revision 基线。

  • 可从文件选择或粘贴 checkout 内容导入根地址；工具只解析字面量地址，不执行脚本。
  • 变量、多个根地址或不安全的本地目标会被拒绝，避免把导入功能变成命令执行入口。
  • 公共用户名保存在同步配置；密码经标准输入交给 SVN 认证缓存或系统钥匙串，不进入 YAML、日志、命令参数或编辑会话。
  • 检出、更新、清理和重建索引都显示实际处理范围；同一工作区的重叠操作通过操作锁阻止。

5.2 业务目录与虚拟文档

SVN checkout 是唯一源码事实。工具从其中识别系统、数据源、PAGE、过程函数、系统脚本、表和视图，写入工作区独立 SQLite 索引。Nexus 的“谷神源码”树只读取索引；展开单个 PAGE 时才解析目标 JSON，因此大型仓库不会在每次展开树节点时全量扫描。

对象与展示编辑边界
PAGE：按索引中的模型、模块和页面顺序展示，内部固定分为 GSS、JavaScript、SQL、字段及服务事件。脚本与 SQL 以虚拟文档投影，可受控写回原始 JSON；字段用于定位和分析。
过程函数：按包名和函数名组织，支持复制稳定身份、跳转与调用位置。函数源码可以受控编辑，写回对应物理文件。
系统脚本：按业务子系统分组。可受控编辑和提交。
表与视图：作为结构和引用事实进入索引。只读展示，不通过虚拟文档改写定义。

5.3 受控编辑

打开可写虚拟文档时，后端创建独立编辑租约，记录 workspace、对象身份、授权相对路径、文件 hash、SVN BASE revision、JSON Pointer、编码、BOM 和换行风格。保存时按以下顺序处理：

  1. 重新核对工作区、provider、对象身份和路径，拒绝越出授权 checkout。
  2. 检查物理文件、当前片段、文件 hash 与 BASE 状态；缓存标签缺少会话或仍显示只读时，Nexus 先强制重新加载一次，再由后端作最终判定。
  3. 同一 PAGE 的其他片段发生变化但当前片段未变时，在最新 JSON 上安全重放；同一片段已经变化则拒绝旧租约覆盖。
  4. 保留编码、BOM、换行和文件权限，以最小范围原子替换，再按物理文件增量刷新索引。

svn read-batch 可以一次读取多个对象；write-batch 会先预检全部目标，拒绝同一物理文件出现两次，任一写入失败时恢复已写文件，全部成功后统一更新索引。短时读写使用带超时的跨进程锁，长操作使用工作区操作锁，解决 Nexus、CLI 和自动化同时访问同一 checkout 的竞争。

5.4 SCM、冲突与交付

  • 每个工作区注册一个 SCM provider；内部按中文业务子系统分组，同组可聚合数据源与多个系统 working copy，公共源码单独成组。
  • 本地差异比较 SVN BASE 与 working copy；远端差异比较 working copy 与 SVN HEAD。PAGE 默认显示脚本、SQL 和字段的可读差异，也可查看原始 JSON。
  • 支持全部、业务组、原生多选和单文件范围的提交或更新。提交前复核 selection token、文件 hash、当前 SVN 状态和目标文件远端变化，不使用 Git 暂存区。
  • 放弃修改只回退所选文件到 BASE；远端已有新 revision 不会阻止本地撤销，但提交仍会检查目标文件远端安全性。
  • 重叠文本冲突可用三方合并处理，保存并确认后才标记 resolved；新增、删除、未跟踪、属性和树冲突继续阻断。

跨 working copy 的提交按组依次执行，会产生多个 revision，不伪装成原子事务。每次成功提交都追加持久交付回执，记录交付编号、revision、文件和时间。目标文件成功提交并取得 revision，即视为本次源码交付成功；编译、发布和业务运行按需要另行验证。

6. 索引与 AI 上下文

6.1 工作区事实索引

每个工作区维护自己的 context/index.db，DATABASE 从 readonly 建索引，SVN 从授权 checkout 流式建索引。索引保存：

  • 源码对象身份、真实相对路径、物理 working copy、内容 hash 和对象定位信息。
  • 静态调用、低置信动态调用、调用位置和目标身份。
  • PAGE 片段、字段到表列、单据路由、表读写、条件、赋值和异常事实。
  • SVN PAGE 的可重建脚本、SQL、字段集合节点目录与界面字段目录，包含当前 JSON Pointer、局部语义身份、区域、解析版本与索引 generation；正文仍从授权 working copy 按需读取。无原生身份的数据源列不进入界面字段目录。
  • SVN 对象的 JSON Pointer、BASE 信息和支持增量刷新的文件关联。

同名对象用数据源、working copy 与业务身份组成键；PAGE ID 保持工作区全局身份。全量重建在单个事务内完成，失败会回滚并保留旧索引；虚拟保存、撤销和提交按文件增量更新，只有无法安全识别结构变化时才回退到全量扫描。

索引不保存第二份可编辑源码，也不建立源码全文倒排。这样避免索引成为隐蔽副本，并把结果始终锚定到可核验的真实文件。

SVN MCP、Nexus 和 CLI 使用同一份可重建索引，MCP 的独立入口、工具能力和开发边界见第 9 章。PAGE 语义投影与 SVN 对象目录分别报告就绪状态；旧索引需由目标工作区显式全量重建后才提供对应查询；索引 generation 变化会使旧分页游标失效。

6.2 检索与有界上下文

统一搜索search 同时查询源码身份和事实索引；结果可打开精确源码位置。
关系查询svn definition/callers/find/context 提供定义、引用、调用链和局部上下文。
事实解释svn facts/explain 返回写入位置、控制条件、表关系和有界调用者链。

context-pack 默认生成精简上下文，只保留少量直接关系、高价值事实、路径和短 hash；需要更多证据时再请求详细版本或 continuation token。该流程让 AI 先根据稳定身份和事实缩小范围，再读取准确片段，避免把整个业务仓库塞入上下文后凭相似名称猜测。

Markdown 源码索引和调用索引只在显式执行导出命令时生成，不属于 Nexus 日常运行链路。运行时以 SQLite 为事实来源，可以快速增量更新，也避免大量派生文件污染私有 Git。

7. Guthon Nexus

7.1 工作区驾驶舱

Guthon Nexus 是统一 VS Code 扩展，DATABASE 与 SVN 工作区同时出现在同一侧边栏。每个节点绑定自己的 workspaceKey，菜单由 CLI 返回的有效 capabilities 决定，因此没有配置的功能不会显示为可执行操作。

  • 配置或切换 toolHome、添加/删除产品和项目、切换源码来源、打开配置与目录。
  • 显示同步状态、索引就绪度、SVN working copy、本地/远端变更和最近交付回执。
  • 执行 DATABASE 同步、元数据导出、Workcopy 管理和只读数据库排查。
  • 执行 SVN 检出、更新、索引、业务目录浏览、虚拟编辑、差异、冲突处理和精确提交。
  • 搜索当前工作区完整索引，并复制精简或详细 AI 上下文。
  • 启动、停止和检查 Bridge；管理发行/调试运行模式。

“谷神源码”树支持展开、收缩、刷新、水平滚动、索引搜索、从树跳到资源管理器，以及从当前虚拟文档或物理文件反向定位树节点。路径跳转会核对 workspace、checkout 和 sourcePath，拒绝越界。

7.2 语言与导航

  • .gss 是独立 Guthon GSS 语言，在 Java 语法基础上注入 Velocity/GSS 指令和变量；兼容的 .vm 保持 Java 关联。
  • Java、JavaScript、SQL 提供谷神 API 补全与悬停说明；路由规则根据上下文选择 sqltools、sql 或 sqlh 等 API 族。
  • 过程函数调用可转到索引中的定义；过程函数内的 @子方法(...) 可转到当前源码的 #function 声明。定义跳转与“谷神源码”树使用同一虚拟文档，支持从编辑器定位树节点；索引对象也支持查找引用与调用位置。
  • SVN 虚拟 GSS 根据当前文档的 #function 声明补全 @ 调用，并提示重复的本地函数名；PAGE 字段集合分块先用当前有效 JSON 的 fieldId 补全 selectCodefieldId，再按精确 PAGE 身份和字面前缀查询其他集合的有界候选，标明来源；候选较多时继续输入前缀缩小范围。同一集合重复值会警告；兄弟分块有未保存修改时不引用其旧索引。这些提示不替代平台语法或业务校验。
  • 源码树中的 PAGE JSON 和过程函数提供“预览源码影响”及“浏览影响证据”。PAGE 展示索引中的表访问、显式字段关系与逻辑事实，可跳转到字段关系所属集合或表访问、逻辑事实的源码片段与索引行；过程函数展示静态调用边与动态调用线索，并可跳转到索引行。预览显示 PAGE 索引代次及源码哈希，结果按上限截取，索引文件身份不一致时拒绝归因。PAGE 字段关系只覆盖显式 selectBox 证据，不能用于自动删除判定。
  • PAGE 节点的“查找其他 PAGE 的字段”在同一工作区与命名空间内按 fieldId 字面前缀有界分页检索，返回 PAGE、工作副本、字段集合与表列 ID 来源；所有跨 PAGE 关系标为未验证，不自动补全或推断引用。命令面板和 Chrome Bridge 弹窗、页面左下角按钮共用本地精确定位：PAGE 只传完整 PAGE ID，过程函数只传包名与函数名；由用户明确选择 SVN 工作区，多份源码当次选择，再打开受控虚拟文档。浏览器入口要求已安装包含 URI 处理器的 VSIX，并在安装后重载 VS Code。
  • 补全索引、人工片段和路由规则分别维护，使自动生成 API 与项目特定规则可以独立更新。
  • SCM 使用 VS Code Quick Diff 以 SVN BASE 标出增删改，点击装饰即可内联查看。

跨对象定义与引用依赖工作区索引，不扫描所有文件；当前虚拟文档的本地函数与字段提示读取编辑器正文。过程函数调用按索引证据定位，遇到同名身份无法确认时仍须核对目标源码。

7.3 工具更新

运行模式节点默认折叠，显示当前入口路径和本地数据目录；发行应用版本、GitHub/Gitee 更新源、手动检查和回退也在此处，默认使用 Gitee。工具不会在启动时或后台定时联网，只有用户点击检查才访问所选来源。开发模式和调试模式的检查更新提示会分别说明源码/.venv 与 Release pyz/本地 Python。

  1. 下载候选发行物和校验文件。
  2. 验证 SHA-256，阻止损坏或被替换的文件。
  3. 在临时 toolHome 执行独立 self-test，避免候选版本污染真实配置。
  4. 安装到扩展全局存储的版本目录，通过后原子切换当前入口。
  5. 保留上一可用版本，发生问题时由用户手动回退。

开发模式使用源码仓库的 .venv 与 Python 入口；调试模式使用经 SHA-256 校验的 Release pyz 和本地 Python 3.12+；发行模式继续使用 macOS/Windows 可运行包。三种模式复用同一 ToolHost 协议，切换模式不改变 toolHome。当前调试模式需要本地 Python；隔离运行环境的一键下载资产尚未交付。

Nexus 和 Bridge 各自复用一个常驻 ToolHost。工作区列表在 Nexus 视图间共享，普通界面刷新不触发全部 SVN SCM 扫描；本地状态与远程检查由不同命令触发。日常 SCM 状态只使用必要的 svn info/status，更新和写回仍走完整安全检查。

8. Guthon Bridge

8.1 页面能力

Guthon Bridge 由 Chrome 扩展和 Nexus 管理的本地服务组成，把谷神在线开发页面的身份转换为 GuthonCodeTool 命令。当前页面能力包括：

页面左下角按钮组在开发页签就绪后先挂载，再异步确认页面桥接和工作区模式；页签变化会触发刷新，30 秒轮询作为兜底。

  • 在 DATABASE 工作区拉取 PAGE、过程函数和系统脚本。
  • 导出表结构、单据类型、视图和系统脚本元数据。
  • 在过程函数和模块后台脚本中识别静态过程方法，按住 Ctrl（macOS 为 Cmd）点击即可打开对应函数；也可查看索引识别的调用位置。
  • 根据页面所属模块路由到正确产品或项目。
  • 复制模式，以及字段复制、粘贴和平移等页面辅助。
  • 从模块开发页当前激活的 PAGE 或过程函数页签提取对象身份，弹窗和左下角按钮通过 VS Code URI 请求 Nexus 精确定位本地源码；Nexus 当次选择 SVN 工作区及多候选源码。
  • SVN MCP 的 PAGE 受控修改预检使用相同事实提取器比较候选源码与租约绑定快照，返回表访问、显式字段关系的有界增减及前后哈希；预检不写入源码。
  • 显示本地工具执行结果，并把具体同步工作交给统一 CLI。

SVN 工作区不提供网页源码拉取或数据库元数据导出。Bridge 的 PAGE 定位链接仅传递页面编码，不携带工作区、路径或写入命令；SVN 的检出、编辑、索引和提交只在 Nexus 内完成。

8.2 路由与安全边界

  • 请求携带 workspaceKey 时，Bridge 继续核对页面身份；缺失时根据页面来源、数据源和系统查找候选。
  • 存在多个候选时由用户为当前请求选择，不写入全局默认，也不影响其他页面。
  • 允许访问的页面范围由扩展的来源、域名后缀和路径规则限制。
  • 所有本地请求只在回环接口通信；文档和 UI 不需要暴露监听地址。
  • Nexus 把当前应用入口和 toolHome 传给 Bridge，用户无需手工配置环境变量或安装 Node.js。

Bridge 只提供页面增强和 DATABASE 拉取，不向平台自动写回源码，也不执行 SVN commit。该边界让在线页面、本地工作区和版本控制各自只有一个明确写入入口。

9. Guthon SVN MCP

SVN MCP 与 Nexus、Bridge 同属 GuthonCodeTool 的用户入口，但职责不同：Nexus 服务 VS Code 中的开发与 SVN SCM，Bridge 服务受限谷神网页，MCP 服务 AI 客户端对已授权 SVN PAGE 和过程函数的定位、证据读取和受控源码修改。MCP 是共享服务的协议适配，不建立第二套索引、授权清单或文件写回路径。推荐客户端别名为 guthon-svn；旧 guthon-page 别名仍可指向同一入口，迁移不应重复启动两个服务。

9.1 入口与能力

客户端以 mcp --stdio --home <toolHome> 启动独立进程；stdio 握手支持 MCP 2025-03-26、2025-06-18 与 2025-11-25；不支持无握手的新版协议，客户端须确认服务端返回的版本。--home 明确目标数据目录，每次工具调用再传 workspaceKey；PAGE 查询还需精确 sourceNamespace、sourceId，必要时带 funId；过程函数必须带完整 sourceNamespace + sourceId + funId + workingCopyId。运行入口可用发行应用、Release pyz 或源码开发环境，但客户端配置分别指向各自实际存在的可执行文件和绝对路径。

默认发现 28 个工具：15 个只读查询工具，以及 13 个编辑流程工具。加 --read-only 时只发现前 15 个；后 13 个中的“打开”和“预览”虽然不修改源码，也会随编辑流程一起隐藏。

9.2 共享索引与安全边界

  • MCP 只面向显式配置的 SVN manifest 工作区。PAGE 需完整页面身份；过程函数还必须带 workingCopyId。不能只凭显示名称或目录位置猜测。
  • context/index.db 保存可重建的 SVN 对象目录、PAGE 节点、界面字段和保守关系投影；PAGE JSON、过程函数、脚本与 SQL 正文仍以授权 working copy 为准。无原生身份的数据源列仍通过字段集合按需读取。对象目录就绪不依赖 PAGE 语义投影就绪。
  • 字段关系仅确认显式 selectCodefieldId 等有证据的子集，并保留未解析 otherSetFields 诊断。动态、继承与反射组引用尚未形成完整闭包，check_page_field_references 不能批准字段删除。
  • MCP 不自动安装到客户端，不修改既有 MCP 配置，也不决定 AI 何时调用。工具是否可见及是否主动调用取决于客户端连接和 guthon-team 的工具路由规则。

9.3 开发状态与验证

PAGE 提供 open_page_node_edit、preview_page_nodes、update_page_nodes、get_page_operation、resume_page_operation 五个工具，限定稳定的同页脚本/SQL 字符串节点；另提供 open_page_field_insert、preview_page_field_insert、insert_page_field，只允许同一已识别 UI 字段集合内的单字段新增或拷贝，并共用 PAGE operation 查询/恢复。过程函数提供 open_procedure_edit、preview_procedure、update_procedure、get_procedure_operation、resume_procedure_operation 五个工具，限定完整身份匹配的一份授权物理文件。工具可见不等于目标可写：编辑令牌绑定授权、会话和源码快照；预览不落盘，正式写入重新校验 edit 能力、当前源码、索引及 SVN 状态，再以 idempotencyKey 记录操作。只改本地 SVN working copy，后续记录索引与 diff 核验，不执行 SVN commit。跨 PAGE/集合拷贝、字段整体覆盖、任意 PAGE JSON 结构和反射组不能由当前 MCP 修改。

当前源码注册 28 个 MCP 工具，并提供本地协议、索引和受控写入测试。具体安装版本仍应在客户端核对握手、工具清单、目标索引和真实源码差异。历史真实工作副本验证或某次 projectionGapCount=0 不能代表其他工作区或新一次索引也就绪；PARTIAL、REBUILD_REQUIRED 与 INDEX_STALE 应按目标身份重新取证。完整字段关系、跨文件补偿/故障矩阵、字段删除/移动和反射组写入仍未交付；使用默认写入能力时应人工核对 SVN diff，不把工具响应当作平台运行证明。具体配置和调用顺序见使用手册第 5 章。

10. guthon-team 治理

10.1 安装与更新

团队治理通过团队 Marketplace 中的 guthon-guard 插件分发。插件在新任务的 SessionStart 阶段检查工作区并幂等初始化：已是当前版本时不重复写入，缺失或版本更新时补齐规范、Linter、API 索引和配置。支持 Hook 的客户端还需对插件 Hook 完成信任；不支持 Marketplace 或 Hook 的环境可使用同一发行物中的独立安装器。

治理安装面向业务 var 工作区，不写入 GuthonCodeTool 源码仓库。核心 AGENTS、规范正文和 guthon-lint 即使没有 Marketplace 或 Hook 也能使用，Hook 只负责自动选择检查时机。

10.2 规范门禁

规范层AGENTS 与权威标准说明业务语义、开发模式、方言 API 和允许的写入范围。
判定层guthon-lint 用稳定诊断码检查受保护路径、非法 API、Velocity 结构、赋值、重复保存和 SQL 兼容性。
时机层Agent Hook 在任务与工具生命周期检查，Git Hook 在提交前兜底；需要时可把同一 CLI 接入 CI。

版本清单和文件哈希用于判断规范是否完整、是否被本地修改以及升级是否安全。人工修改不会被静默覆盖；强制更新前先备份。私有 API 索引使工具能明确判断函数是否存在，避免用通用语言经验猜测谷神方言。

治理采用“语义规范 + 可执行 Linter + 生命周期 Hook + Git/CI 兜底”，因为提示词只能提醒，不能稳定证明每次修改都经过同一规则。Linter 通过只代表已覆盖的静态规则通过，不代表数据库、平台编译、SVN 或业务流程已经验证。

11. 构建、发布与验证

11.1 发行物

Python 应用使用 PyInstaller 单文件构建，并内置公开配置模板与版本信息。构建必须在目标系统执行，以生成 Windows x64 应用和 macOS ARM64 应用。发布流程同时完成：

  • 运行 Python、Nexus 与 Bridge 的相关测试。
  • 打包 Guthon Nexus VSIX 和 Guthon Bridge Chrome ZIP。
  • 打包公开的 guthon-testing Skill。
  • 为应用生成校验文件，并向 GitHub 与 Gitee Release 上传相同附件。

Release 不包含真实配置、凭据、业务源码、私有索引、日志或 guthon-team 内容。工具应用可以替换升级，用户的 toolHome 保持不动。

11.2 验证边界

验证证据能够证明的范围
Python、Nexus 或 Bridge 自动化测试源码级命令、路由和组件行为；不能证明已安装 VSIX、真实浏览器或远端服务。
MCP stdio 协议、临时打包及真实 SVN 验证初始化、28 工具发现、临时夹具与真实工作副本的 PAGE 节点/字段新增与拷贝/过程函数本地写入；测试改动已撤销，未提交 SVN。不能证明 AI 自动路由、已安装 VSIX、Windows 或平台运行。
打包应用 self-test发行物可启动、可解析内置资源并能在临时目录完成基础设置。
SQLite 索引与静态事实当前本地源码快照中的对象、关系和可识别规则；不能证明运行时分支一定执行。
数据库只读查询指定目标和时点的数据库记录；不能证明页面版本、缓存或业务流程结果。
SVN revision 与交付回执所列文件已经提交到对应 revision，本次源码交付成功；编译、发布和运行结果需分别取证。
guthon-lint 通过已实现的静态治理规则没有发现问题；不能替代平台或业务验证。

维护功能时先用 AI_CODE_INDEX.md 定位最小模块，再检查实际受影响的 CLI、配置、Nexus、Bridge、MCP、测试及三份 HTML 文档。删除或改名后全局搜索失效引用。文档至少执行 HTML 结构检查、定向敏感信息检查和 git diff --check；代码修改再按影响范围运行 Python、Nexus、Bridge、MCP、打包或真实环境验证。
