1. 定位与边界

GuthonCodeTool 把谷神平台中的 PAGE、过程函数、表结构、单据类型、视图和系统脚本整理到本地，形成可检索、可比较、可供 AI 分析的私有开发工作区。

  • 工具负责读取、整理、索引和生成安全工作副本。
  • 工具不会自动签出、保存、提交或签入谷神平台源码。
  • var/source/readonly 是上游镜像，禁止人工修改；开发只修改 var/source/workcopy。
  • 数据库连接、源码、业务文档和运行索引均为本地私有内容，不进入公开仓库或 Release。
  • Python 脚本继续作为开发与测试入口；普通用户只使用打包应用、VSIX 和 Bridge。

2. 整体架构

2.1 组件关系

text
VS Code 侧边栏 ──spawn──▶ GuthonCodeTool 应用
                                  │
Chrome 扩展 ──HTTP──▶ Bridge ─────┘
                                  │
                                  ▼
                          数据库 / 源码表
                                  │
                                  ▼
                readonly / workcopy / SQLite / logs
GuthonCodeTool 应用统一执行同步、导出、查询、排查和 Workcopy 操作。
VSCode扩展: Guthon Nexus提供侧边栏、配置编辑、代码补全、悬浮说明和本地源码跳转。
Chrome扩展: Guthon Bridge把谷神网页上下文转换为本地工具调用，并提供字段复制等页面能力。

2.2 运行链路

  1. VS Code 扩展保存应用路径和本地数据目录。
  2. 用户确认操作后，扩展使用 spawn 启动应用并传入 --home。
  3. 应用设置 GUTHON_HOME，所有配置和私有输出均相对于该目录解析。
  4. sync.ACTIVE 决定当前产品或项目、数据库连接、readonly 范围和 SQLite 索引。
  5. Bridge 使用同一应用和同一本地数据目录，因此网页拉取与 VS Code 同步共享状态。

3. 可执行应用

3.1 统一命令入口

scripts/guthon_tool.py 是打包应用入口。macOS 与 Windows 仅文件格式不同，命令和业务逻辑相同。

text
setup                 创建缺失配置，不覆盖已有文件
init                  初始化当前 ACTIVE 源码索引
sync-source           同步当前 ACTIVE 源码
sync-all              依次同步源码、表结构、单据类型、系统脚本和视图
reindex               从 readonly 重建调用索引
export-schema         导出表结构
export-bill-type      导出单据类型
export-system-script  导出系统脚本
export-view           导出视图
query / diagnose      查询局部上下文 / 执行只读排查
workcopy              查看状态、生成差异或交付物

3.2 打包方式

scripts/build_guthon_tool.py 使用 PyInstaller --onefile，内置配置模板和运行所需 Python 模块。构建必须在目标系统执行：Windows 生成 EXE，macOS 生成 ARM64 Mach-O。

  • Windows 发行物：GuthonCodeTool-windows-x64.exe。
  • macOS 发行物：GuthonCodeTool-macos-arm64.zip，当前只支持 Apple Silicon。
  • 应用本身不保存用户配置，升级时直接替换应用文件即可。

4. 配置与本地数据

4.1 配置职责

  • datasource.yaml：产品、项目和只读排查数据源；敏感值可引用环境变量。
  • products.yaml：产品名称、数据源和源码范围。
  • projects.yaml：项目名称、数据源和继承产品。
  • source-tables.yaml：PAGE 与过程函数表名、字段名映射。
  • sync.yaml：ACTIVE、子系统别名、未签入源码白名单和拉取规则。

setup 只补齐缺失文件，不覆盖用户配置。系统与数据源映射查询后缓存到 config/system-data.json。

4.2 目录契约

text
<本地数据目录>/
├── config/
│   ├── datasource.yaml
│   ├── products.yaml
│   ├── projects.yaml
│   ├── source-tables.yaml
│   └── sync.yaml
└── var/
    ├── AGENTS.md
    ├── docs/
    ├── source/readonly/
    ├── source/workcopy/
    ├── database/{schema,billtype,views}/
    ├── knowledge/
    └── runtime/{index,logs}/

5. 源码同步与索引

scripts/gusen_hub.py 是源码同步、目录写入、索引和 Workcopy 的共享实现。同步按 datasource 查询子系统，并使用 VERSION_MAC 优先判断变化；未变化时复用 readonly，变化时才重写源码和调用索引。

5.1 PAGE 导出

PAGE 保存到 {子系统}/page/{模型序号}_{模型}/{模块序号}_{模块}/{页面名 页面ID}。完整 JSON 写入 raw.json，页面脚本、SQL、事件和组件脚本拆入 scripts/。

  • 模型和模块序号补齐三位，并按父模型链还原目录。
  • 项目脚本的独立 @inherit(); 使用相应产品快照字段。
  • 空的服务组件 compScript 仍生成空 compScript.vm。

5.2 过程函数导出

过程函数保存到 {子系统}/procedure/{过程别名}/{函数名}/source.vm。项目继承标记使用配置映射的产品脚本；多个子系统共用数据源时只保存一份实体源码，其余目录使用链接。

5.3 调用索引

每个 ACTIVE 使用独立 SQLite：var/runtime/index/{products|projects}/<id>.db。索引记录源码对象、静态调用和低置信动态调用；AI 应通过 query 获取局部上下文，不应直接加载全量源码索引。

6. 平台元数据导出

  • 表结构：export_table_schema_sql.py 查询 gd_tables、gd_tables_field 和 gd_system。
  • 单据类型：export_bill_type_sql.py 查询 gd_bill_type 和 gd_system。
  • 视图：export_view_sql.py 读取 gdp_tables_views.VIEW_SQL。
  • 系统脚本：export_system_script_sql.py 读取 gd_system_script；项目继承时使用产品脚本，项目 JavaScript 覆盖代码追加在产品代码之后。

四类导出均复用 ACTIVE 的数据源与子系统范围。sync-all 固定按“源码 → 表结构 → 单据类型 → 系统脚本 → 视图”执行，任一步失败或 ACTIVE 中途变化即停止。

7. Workcopy 安全模型

  1. 从 readonly 创建 Workcopy，同时保存 .guthon-baseline 和 source-meta.json。
  2. 再次拉取时比较本地内容、原基线和最新上游。
  3. 本地修改已经回写上游时刷新基线；本地与上游分叉时返回冲突并拒绝覆盖。
  4. workcopy status 查看状态，diff 更新差异，package 生成交付清单。

pull_auto_add_git 只暂存本次新生成、未跟踪且未被忽略的文件，不暂存已有文件修改，也不强制添加忽略文件。

8. VSCode扩展: Guthon Nexus

扩展入口为 plugins/GuthonVSCodeExtension/gushen-vscode-completion/src/extension.js。

  • 全局保存 gushenCompletion.toolPath 和 gushenCompletion.toolHome。
  • 侧边栏所有执行型操作均先弹出确认；打开配置和目录保持单击。
  • 已初始化时再次执行“初始化工作区”会先确认是否切换；只有确认并选中新目录后才更新全局 toolHome，取消时保留原工作区。
  • 使用 spawn(toolPath, [command, "--home", toolHome])，不经过 Shell，因此 macOS 与 Windows 参数一致。
  • 提供 Java、JavaScript、SQL 方言补全、API 悬浮说明和过程函数转到定义。
  • 补全数据在 data/index.json，手工片段在 data/manual.json，路由规则在 rules.json。

9. Chrome扩展: Guthon Bridge

Bridge 由 Chrome 扩展和监听 127.0.0.1:17361 的本地服务组成。服务入口为 plugins/GuthonBridge/bridge/server.js，随 VSIX 打包并由 Guthon Nexus 使用 VS Code 自带的 Node 运行环境启停。

  • Nexus 直接把当前系统应用和本地数据目录传给 Bridge；用户不需要手工设置 GUTHON_TOOL_PATH 或 GUTHON_TOOL_HOME。
  • 页面提供过程函数/PAGE 拉取、表结构、单据类型、视图、系统脚本、复制模式和字段平移。
  • 允许访问的平台范围由 extension/host-config.js 的 CIDR、域名后缀和路径前缀控制。
  • Bridge 不提供平台回写接口；保存、签出、提交和签入仍由用户在谷神平台完成。

普通用户不需要单独安装 Node.js。GuthonCodeTool-chrome.zip 只负责安装 Chrome 扩展，本地服务由 Guthon Nexus 启动；命令行启动仅保留给仓库源码调试。

10. 发布、维护与验证

.github/workflows/release.yml 在 main 的工具、配置模板、插件或工作流变化后自动执行：

  1. 在 Windows 和 macOS 构建应用。
  2. 运行 VS Code 扩展与 Bridge 测试并打包 VSIX、Bridge ZIP。
  3. 生成中文说明并创建 GitHub Release。
  4. 使用仓库 Secret 和变量创建 Gitee Release、上传相同附件。
bash
python -m unittest discover -s tests
npm test  # plugins/GuthonVSCodeExtension/gushen-vscode-completion
npm test  # plugins/GuthonBridge
git diff --check

修改功能时应同步检查应用命令、VS Code 侧边栏、Bridge 路由、配置模板、README、知识库和使用手册。Release 只分发应用、VSIX 和 Bridge，不包含真实配置、AI 规范或私有 var/。
