一、一键安装配置

Windows 用户使用 GuthonCodeSetup 安装 GuthonCodeTool、GuthonNexus 和 GuthonBridge，并由向导接入内网 guthon-team 插件市场。个人登录、服务器信任与 Chrome 首次扩展加载需要本人确认，向导会提供操作入口。

推荐阅读路线：

v0.3.2 起使用 GuthonCodeSetup。完成本章安装及首次配置向导后，无需重复第二、三、五章的手动安装和工具初始化；这些章节用于单独安装或修复。第四章是后续在 GuthonNexus 接入业务工作区的参考，按工作需要使用。

个人账号登录、工作区／插件信任、内网仓库授权和 Chrome 首次扩展加载仍需按本章完成。之后阅读第六章日常使用，按第七章验收清单核对；遇到问题查第八章排障，维护操作查第九章。

1.1 从 GitHub Release 下载哪些文件

打开 GitHub Releases，进入同一个版本的 Assets（发行附件）。v0.3.2 及后续发行版下载下表文件；安装器会包含后端、Nexus、Bridge、独立 Python 和三个依赖安装程序。

文件是否需要用途
GuthonCodeSetup.exe必需统一 Windows x64 安装与首次配置入口。
GuthonCodeSetup.sha256必需同一发行版安装器的 SHA-256 校验文件。
guthon-testing.zip按需仅在需要独立安装数据库排查 Skill 的 Agent 中使用；按对应 Agent 的 Skill 安装方式配置。

使用统一安装器时，GuthonCodeTool-windows-x64.exe、guthon-nexus-vscode.vsix 和 GuthonCodeTool-chrome.zip 已包含在套件中。guthon-team 从团队内网 Git 插件市场获取，规范由实际 SessionStart 初始化和更新。

安装前核对下载文件

将安装器和同版校验文件放在同一目录，在 PowerShell 执行：

$expected = ((Get-Content .\GuthonCodeSetup.sha256 -Raw).Trim() -split '\s+')[0]
$actual = (Get-FileHash .\GuthonCodeSetup.exe -Algorithm SHA256).Hash
if ($actual.ToLower() -ne $expected.ToLower()) { throw '安装器校验不匹配，请重新下载' }

摘要匹配用于检查文件完整性；下载来源和正式发行签名仍需按团队分发说明核对。

手动安装或单独修复时下载哪些文件（可选）

仅在采用第二至第五章手动流程或单独修复组件时，在同一个 Release 下载以下文件：

  • GuthonCodeTool-windows-x64.exe：后端应用。
  • guthon-nexus-vscode.vsix：CodeBuddy 中的 Nexus 扩展。
  • GuthonCodeTool-chrome.zip：Chrome 的 Bridge 扩展。
  • GuthonCodeTool-checksums.txt、GuthonCodeTool-checksums.signature.json、GuthonCodeTool-release.json：同版摘要、签名和组件清单，供离线核验和更新流程使用。

需要独立数据库排查 Skill 时再取 guthon-testing.zip。CodeBuddy、Git、SVN 从各自官网安装；团队插件仍从内网市场安装。

1.2 运行安装器并打开安装助手

  1. 双击 GuthonCodeSetup.exe。选择用于配置、日志和后续工作数据的目录，通常使用默认值。公开包会询问团队提供的 guthon-team 内网 Git 克隆地址；可以填写或由团队通过 GUTHON_TEAM_MARKETPLACE_URL 预置。安装阶段不创建产品或项目。
  2. 安装器准备 CodeBuddy、Git、SVN、GuthonCodeTool 和 GuthonNexus。系统要求安装授权或重启时按提示完成；重启后重新运行同一个安装包。
  3. 双击桌面“开始 Guthon 开发”。首次在 CodeBuddy 登录个人账号，并信任当前工作区。
  4. CodeBuddy 会打开“Guthon 安装配置助手”，用于一次性确认工具、团队插件和 Chrome Bridge 环境。可以点击“继续下一步”。

检查标准：GuthonCodeTool 与 GuthonNexus 卡片显示通过。无需自己安装 Python 或配置系统环境变量。

1.3 安装内网 guthon-team

  1. 连接公司网络或团队提供的 VPN。点“打开内网 Git 网站”，填写团队网站地址并登录；没有账号或没有仓库权限时，先联系管理员开通。
  2. 如果市场使用 SSH 地址：点击“生成或复制 SSH 公钥”。向导保留已有密钥，只把公钥复制到剪贴板；到 Git 网站“用户设置 → SSH/GPG 公钥”新增并粘贴保存。私钥不上传、不发给别人。
  3. 点击“首次连接授权”。终端提示服务器指纹时，先与团队提供的指纹核对，再确认信任。HTTPS 来源按终端或 Git 凭据管理器提示登录，跳过 SSH 公钥步骤。
  4. 点击“检查内网仓库”。访问通过后点“打开插件市场”，从命令列表选择插件市场；也可从 CodeBuddy 的“插件 → 插件市场”进入。选择 guthon-team，安装 guthon-guard，并确认插件／Hook 信任提示。
  5. 点击“复制重载插件命令”，在 CodeBuddy 聊天输入框粘贴执行。随后开始一个新聊天，再回到向导点“检查 Hook 运行”。

检查标准：实际 SessionStart 在本次安装后运行，并成功初始化／检查工作区。安装器不携带规范；客户端市场取得插件后，由 SessionStart 使用插件载荷初始化和更新规范。

向导回执需要 guthon-guard 0.2.10 或更新版本。市场版本过旧时由维护者先更新内网插件。看到“已安装”不能代替运行回执，也不证明全部生命周期检查或业务运行已验收。

1.4 在现有 Chrome 加载 GuthonBridge

  1. 需要额外平台主机规则时可点“平台地址规则（按需）”；否则使用已配置的默认规则。此项不作为安装完成条件。
  2. 点“打开 Chrome 扩展管理”，打开后启用右上角“开发者模式”。
  3. 点向导“定位并复制扩展目录”。回到 Chrome 点击“加载已解压的扩展”，在文件夹选择器粘贴该目录并选择。
  4. 在 Chrome 工具栏的扩展按钮中打开 GuthonBridge；可以将它固定到工具栏。
  5. 回到向导点“复制配对令牌”。在 GuthonBridge 展开“本机 Bridge 配对”，粘贴令牌，点击“保存并连接”。令牌只用于你的本机，不发送给别人。
  6. 点“检查浏览器连接”。工具与插件环境检查通过后点“完成配置”；助手将提示后续在 CodeBuddy 使用 GuthonNexus，并关闭安装确认页面。

检查标准：本地 Bridge 服务运行，当前托管扩展发出了认证连接心跳。扩展文件存在、或浏览器显示“已加载”，都不能单独替代此项检查。

已有 Chrome 的首次加载需要本人操作；安装器不修改浏览器策略。已经加载后改变平台地址，需要到扩展管理页重新加载 GuthonBridge。后续版本通过 Nexus 更新固定托管目录。

1.5 完成安装，后续使用 GuthonNexus

GuthonCodeSetup 只负责从零安装必需工具、插件和基础环境。安装及一次性确认完成后，提示“后续打开 CodeBuddy，使用 GuthonNexus”。日常双击“开始 Guthon 开发”直接进入 CodeBuddy，安装助手不再弹出，已配置的 Bridge 服务自动启动。

产品／项目创建、SVN 业务账号、数据库连接、源码检出和索引建立属于后续 GuthonNexus 的业务使用，根据实际工作需要操作；它们不属于安装流程，也不作为安装完成条件。可按需查阅第四章。

1.6 自动安装失败时的手动恢复

现象处理
CodeBuddy / Git / SVN 自动安装失败安装结果页会提供官网链接。也可在安装目录的 prerequisites 子目录双击对应离线安装程序；完成后重新运行 GuthonCodeSetup。
找不到 SVN 命令TortoiseSVN 安装时选择 Command Line Client Tools。首次安装漏选时重新运行安装程序，选择修改功能。
内网仓库访问失败确认公司网络、账号仓库权限、公钥登记和首次服务器信任。到“首次连接授权”终端查看具体提示。
插件已安装但 Hook 仍待完成确认工作区与 Hook 信任，更新市场插件，重载插件并开始新聊天。当前市场需要包含支持向导回执的版本。
Chrome 无法加载扩展选择“定位并复制扩展目录”给出的完整目录，确认该目录直接包含 manifest.json。
Chrome 开发者模式被公司策略禁用由管理员按公司的扩展部署方式安装 GuthonBridge；向导不会绕过浏览器策略。安装后继续配对与连接检查。
配对后没有连接保持 CodeBuddy 窗口打开，重新复制本机令牌并保存连接；确认两边端口一致，然后再次检查。
发现人工配置冲突保留原文件，请维护者合并；不要直接删除配置或强制覆盖。

官网下载：CodeBuddy · Git · TortoiseSVN · Chrome

二、手动创建并信任工作区目录

本章为手动安装参考。已完成第一章工具及插件环境配置时可跳过；单独安装或修复时再使用。

1

新建目录并在 CodeBuddy 中信任 操作示例

  1. CodeBuddy 安装完成后，在文件资源管理器新建唯一根目录 D:\Develop\GuthonWork。
  2. 在 CodeBuddy 选择「文件 → 打开文件夹」，打开 D:\Develop\GuthonWork；出现工作区信任提示时确认信任该目录。
  3. 后续把发行版运行文件放在根目录，运行数据保存在根目录下的 var：D:\Develop\GuthonWork\GuthonCodeTool-windows-x64.exe、D:\Develop\GuthonWork\var。

三、手动安装并设置 Guthon Nexus

本章为手动安装参考。已完成第一章工具及插件环境配置时可跳过；单独安装或修复时再使用。

从 最新 Release 下载同版 GuthonCodeTool-windows-x64.exe 与 guthon-nexus-vscode.vsix，放入 D:\Develop\GuthonWork。工具首次配置后在该根目录生成 config 和 var。

3

图形界面安装 VSIX 操作示例

  1. 在 CodeBuddy 左侧点击「扩展」图标，点击扩展栏右上角 … → 从 VSIX 安装…。
  2. 选择 D:\Develop\GuthonWork\guthon-nexus-vscode.vsix。安装结束后在 CodeBuddy 扩展列表确认出现 Guthon Nexus，版本为 2.5.0。
  3. 如图标未立即出现，在 CodeBuddy 使用「开发人员: 重新加载窗口」或关闭后重新打开 CodeBuddy。
4

在 Nexus 中初始化数据目录 操作示例

  1. 点击 CodeBuddy 左侧 Guthon Nexus 图标。点击「设置工作区」或「初始化/配置」入口。
  2. 数据目录选择 D:\Develop\GuthonWork；运行程序选择 D:\Develop\GuthonWork\GuthonCodeTool-windows-x64.exe。
  3. 确认后观察 CodeBuddy 的「输出」面板，出现 GuthonCodeTool 完成: setup。Nexus 树显示「工作区 已配置」，切换工作区显示 GuthonWork。
  4. CodeBuddy 文件树应有 config\datasource.yaml、products.yaml、projects.yaml、source-tables.yaml、sync.yaml、database-testing.yaml。首次为空模板属正常，不代表业务源已连接。
5

注册真实产品或项目 按团队配置

  1. 在 Nexus「添加产品或项目」中填写名称；系统自动生成 ID，建议将其改为易读、稳定的 ID。工作区身份为 products.<id> 或 projects.<id>。
  2. 按团队提供的配置选择 DATABASE 或 SVN，并填写真实目标、只读账号或 checkout 信息。没有授权时保留空模板。示例产品 配置示例见下一节。
  3. 同步只更新目标工作区的 readonly、database 或 context；源码开发进入 Workcopy，SVN 走受控编辑入口。首次同步前核对 Nexus 显示的工作区身份与目标。

四、在 GuthonNexus 接入 SVN 业务工作区

本章属于安装完成后的 GuthonNexus 业务使用参考。根据工作需要创建并连接产品／项目；不属于 GuthonCodeSetup 的安装步骤，也不需要日常重复执行。

配置示例：产品名称与ID使用示例值；旧显式 scope 配置仍可读取。新安装按同一工作区的完整repository-root配置，扫描进度不等于业务范围数量，以当前授权清单与最终状态为准。

G1

创建产品身份 操作示例

  1. 在 CodeBuddy 左侧打开 Guthon Nexus，在「项目」旁点击 +，选择「产品」。
  2. 名称输入 示例产品；产品 ID 会自动生成，建议改为易读且稳定的 ID。本示例使用脱敏 ID demo-product，来源选择 SVN。
  3. 回到 Nexus 树，确认出现 PRD 示例产品 demo-product · SVN，并核对稳定工作区键 products.demo-product。
G2

设置 SVN 登录 操作示例

  1. 展开 示例产品，点击「设置工作区 SVN 登录」。
  2. 输入团队分配的 SVN 用户名。导入 checkout 配置后，再输入 SVN 密码完成认证；输出面板应显示 usernameConfigured: true。
  3. 输入 SVN 用户名、密码；Nexus 只保存用户名，密码由 SVN 保存。
G3

导入用户提供的 checkout 清单 操作示例

  1. 在 示例产品 下点击「导入/粘贴 SVN checkout 配置」，选择「粘贴一个或多个 SVN 地址/checkout 命令」。
  2. 在打开的 CodeBuddy 编辑器中，从第 2 行开始粘贴团队提供的完整 svn checkout 清单；保留各 URL 和本地子目录。保存并关闭编辑器，再选择「解析 SVN 地址」。解析只写配置，不会执行原始脚本。
  3. 点击「编辑 SVN 地址配置」检查 products.yaml：确认 svn.url 指向团队提供的产品根地址。新配置生成完整repository-root；旧显式scope仍可读取。业务映射可包括 skill、public、datasources/... 和 systems/...。
  4. 若提示 No executable SVN checkout commands，检查 https://、域名和 checkout 命令是否完整，再粘贴原始清单重新解析。
G4

检出并检查本地索引 核对最终状态

  1. 在 CodeBuddy 的 示例产品 Nexus 树点击「检出/更新完整 SVN 仓库」，先核对预览中的目标工作区、根地址和范围，再执行。新配置默认完整根检出，旧scope按显式清单处理。
  2. 完成 SVN 认证和检出后，在 Nexus 点击「扫描/重建本地 SVN 索引」。CodeBuddy 资源管理器显示 var\workspace\PRD 示例产品\context\checkout-scope.json、index.db；输出面板应显示索引任务的最终状态和错误摘要。扫描计数不能代替索引完成状态。
  3. 复核时展开示例产品的Nexus树，以当前授权清单返回的实际checkout路径、SVN版本与索引任务汇总为准；不要按业务映射或扫描进度猜测缺失对象。

五、手动安装 guthon-team 治理插件

本章为手动安装参考。已完成第一章工具及插件环境配置时可跳过；单独安装或修复时再使用。

这里的「插件」是 CodeBuddy Agent Marketplace 插件，和上节的 Nexus VSIX 属于两个界面。在插件市场中安装，无需手工克隆整个治理仓库。

6

一次性配置 Forgejo SSH 核对结果

  1. 在本机的 %USERPROFILE%\.ssh 下新建个人 SSH 密钥，并把公钥登记到自己的 Forgejo 账号。私钥只留在本机。
  2. 在文件资源管理器地址栏输入 %USERPROFILE%\.ssh；用记事本编辑名为 config 的文件，填入下面内容。若有其他 Host 配置，保留原内容；专用别名应放在 Host * 前。IdentityFile 替换为实际私钥路径。
Host guthon-git
  HostName <团队提供的 Forgejo 地址>
  User git
  Port 2222
  IdentityFile C:\Users\<Windows用户名>\.ssh\id_ed25519
  IdentitiesOnly yes

在 CodeBuddy 终端或 Git Bash 做两项只读验证；无需日常输入命令：

ssh -T guthon-git
git ls-remote git@guthon-git:guthonagentcrew/guthon-team.git HEAD

第一项应显示个人密钥已认证，第二项应返回团队仓库当前 HEAD 的提交哈希。

若电脑还没有 Git：图形向导安装步骤与截图
  1. 访问 Git for Windows 官方页下载安装程序，保存到本机。
  2. 双击安装程序，Windows UAC 确认发布者为 Johannes Schindelin 后继续；安装目录采用默认的 C:\Program Files\Git。
  3. 在「Choosing the default editor」选择 Notepad；PATH 选 Git from the command line and also from 3rd-party software，使 CodeBuddy 能找到 Git。
  4. HTTPS 后端保留 Windows Schannel；行尾选 Checkout as-is, commit Unix-style line endings；终端保留 MinTTY，pull 保留 Merge。Credential Helper 按实际认证方式选择。其余页面保持默认并完成安装。
  5. 重启 CodeBuddy 后在 CodeBuddy 内置终端或 Git Bash 运行 git --version。确认输出显示已安装的 Git 版本。

CodeBuddy 图形市场输入框需要 git@别名:组织/仓库.git 形式；Forgejo 使用 2222 端口，因此依赖上述个人 SSH 别名。

7

通过 CodeBuddy 市场添加团队插件源 操作示例

  1. 在 CodeBuddy 右侧 CodeBuddy 面板点击齿轮，选「插件 → 插件市场」。编辑区打开 CodeBuddy Market 标签。
  2. 点击市场页插件源列表旁的 +，在「添加插件源」输入 git@guthon-git:guthonagentcrew/guthon-team.git，核对字符和来源后提交。
  3. 新增 guthon-team 源后，选择该源，找到 guthon-guard，在 CodeBuddy 中安装。选择「安装（用户）」；再确认「我安装的」显示 guthon-guard，插件详情显示「已安装」及命令、技能、Hooks。
  4. 在 CodeBuddy「查看 → 命令面板」搜索 Reload Window，选择「开发人员: 重新加载窗口」。如果出现「已暂时禁用所有已安装的扩展」提示，点击「重新加载并启用扩展」。重载后再次查看 CodeBuddy「插件」页，确认 guthon-guard 仍在列表中。安装/启用与 Hook 实际执行是不同验收项。
8

初始化业务目录治理 核对目标与结果

  1. 先在 Nexus 中核对产品身份、源码 provider 和实际本地路径。治理目录为 D:\Develop\GuthonWork\var，包含运行描述或业务工作区；不要把数据根或单个 SVN checkout 当作治理根。
  2. 以该 var 打开 CodeBuddy，选择 /guthon-team:guthon-guard:guthon-init，先运行 status。核对安装计划、既有规范和冲突；保留现有文件，不直接使用 --force。
  3. 未建立 Git 仓库时，可执行 init --no-git-hook 安装规范和 Linter。检查 AGENTS.md、.guthon/config.json 和 tools/guthon-lint.cmd；gitHook=skipped 是此模式的预期结果。
  4. 需要 Git pre-commit 时，先创建 var/.gitignore，排除业务源码、索引、日志和凭据。在源代码管理中核对路径为 var，初始化独立本地 Git 仓库，确认待跟踪文件均可公开或符合团队私有仓库规则。
  5. 重新运行 status 和 init，不加 --no-git-hook。检查 .githooks/pre-commit、core.hooksPath 和治理状态。已有其他 Hook 路径时按团队规则整合。
  6. 从 Nexus 获取一个已授权源码文件的实际相对路径，执行 /guthon-team:guthon-guard:guthon-check。只读检查应输出 guthon-lint: PASS；不要复制示例路径代替真实目标。

插件安装、Linter 检查、Git pre-commit、CodeBuddy Lifecycle Hook、SVN 提交和平台运行分别核验。被 Git 忽略的 SVN 源码不会自动受到 Git pre-commit 保护，仍需受控编辑流程和对应检查。

六、日常使用

同机在 VS Code 与 CodeBuddy 使用 Guthon Nexus 时，在第二个 IDE 的“工作区”节点执行“设置/切换工作空间”，选择第一个 IDE 使用的同一个本地数据目录（包含 config 和 var）。产品、项目及现有索引源码会从该目录读取；后续变化可用“刷新已有工作空间状态”更新两棵 Nexus 树，无需重新添加项目或重建索引。

打开工作区在 CodeBuddy 打开已授权的业务目录；先看 Nexus 树上的工作区身份和配置状态。
同步与编辑在 Nexus 中对选定产品/项目执行同步。DATABASE 开发用 Workcopy；SVN 源码走受控入口。
刷新与检查工作区列表刷新、本地 SVN 变更刷新、远端 SVN 变更检查各有入口，按需选择。
团队治理新任务先确认 guthon-guard 与当前工作区状态，受保护写入前看治理提示；不要用安装成功代替 Hook 验证。

更新方法

  1. 在 Nexus“运行模式 → 检查更新”点击“检查更新”，先核对版本，等待签名、哈希及后端自检通过后安装；Nexus安装后重载CodeBuddy。手动安装路线首次需安装同版 VSIX，Chrome按提示加载托管目录。手动升级EXE时先停止工具，保持数据目录不变；0.3.2 对应 Nexus 2.6.0。
  2. 在 CodeBuddy Market 刷新 guthon-team 市场并更新 guthon-guard；重载插件后在真实业务工作区复核状态和 Hook。

GuthonCodeSetup 的安装验收只要求工具、插件与基础环境就绪。下方保留既有手动部署示例；业务身份、源码索引与本地 Git 门禁在实际启用对应功能后按需核对，不作为安装完成条件。

  • CodeBuddy CN 已安装、登录，且已信任 D:\Develop\GuthonWork。
  • 同一 Release 的 GuthonCodeTool EXE 与 Nexus VSIX 已就位，Nexus 已在 CodeBuddy 安装。
  • Nexus setup 完成，工作区显示已配置，六份配置模板存在。
  • CodeBuddy Market 已添加 guthon-team 插件源，guthon-guard 按用户范围安装，重载后仍可见。
  • 产品身份、SVN根地址、检出模式和授权清单已在Nexus核对。
  • 非 Git 治理初始化已成功，规范和 Guard 文件已写入 var。
  • var 已创建本地 Git 仓库；待跟踪列表未显示 SVN 源码和索引目录。
  • Git 模式治理初始化成功；.githooks/pre-commit、core.hooksPath=.githooks 与 state=ready 已复查。
  • 已授权源码文件的只读 guthon-check 退出码为 0，显示 guthon-lint: PASS。

安装后逐项核对以上项目，并记录索引最终状态。需要使用 Git pre-commit 或 CodeBuddy Lifecycle Hook 时，另行验证实际触发结果。

八、安装与使用中的卡点

Git Hook 显示 skipped

非 Git 初始化使用 init --no-git-hook 时，gitHook=skipped 属于预期。需要可选 Git 门禁时按第五章说明将 var 初始化为本地 Git 仓库，再执行 status 和 init，检查 Hook 文件及 core.hooksPath。

插件可见但治理未生效

依次检查插件安装与启用状态、当前工作区是否为已初始化的 var、治理状态以及新任务中的 Hook 输出。

SVN 认证失败

核对 Nexus 中的工作区身份、SVN 根地址和用户名，按提示输入密码并重试。不要把密码写入 products.yaml、HTML 或截图。

配置范围与索引扫描数量不同

旧显式 scope 可包含多个范围。新配置默认完整根检出；扫描进度、业务映射和工作副本数量不是同一指标，以当前授权清单和最终索引状态为准。

SVN checkout 根目录不是单一工作副本

新工作区默认按 repository-root 检出到当前工作区；旧显式 scope 配置可包含多个工作副本。查询状态和提交前，以 Nexus 当前授权清单中的实际根目录为准，不从 var\checkout 或业务映射数量猜测。

SVN 提交与 Git Hook

SVN 提交不会触发 var 本地 Git 仓库的 pre-commit。两类检查分别按实际操作结果验收。

九、常用入口与维护操作

本页适用于 GuthonCodeTool 与 Bridge 0.3.2、Guthon Nexus 2.6.0。状态栏显示插件构建标识；工具版本与后端构建标识单独核对。

数据库与 AI 上下文

  • 在工作区“配置数据库只读目标”中选择排查或正式只读验证。正式目标须填写系统、数据源、表范围、租户字段与证据；配置和连接探测通过不代表业务验收通过。
  • 对源码对象执行“导出 AI 上下文文件”，新文件写入当前工作区 context/ai/，默认只有有界索引摘要；影响证据和继承正文需要明确选择，不自动上传。
  • 查看诊断历史使用工作区入口；实际查询可导出 CSV 或带证据页的 XLSX。DBX 交接文件不代表查询已经执行；Oracle 登录 schema 与业务 schema 分开核验。

配对、恢复与历史

  • Nexus 启动 Bridge 后复制配对令牌，在 Chrome 弹窗保存；两端端口一致，默认 17361。同一数据目录的匹配实例可复用，其他端口占用明确报错。
  • 长任务从弹窗“查询待恢复任务”查询原请求；结果未知时先核验，不自动重做。最近成功对象可普通重拉，但不会沿用原强制覆盖确认。
  • 拉取历史按固定快照分页，可导出 JSON/Markdown。归档先预览，再确认完整工作区键；有备份可恢复，共享 Bridge 日志只导出、不清理。
  • 强制覆盖 Workcopy 前先备份；workcopy trash-list 查看备份，workcopy restore <backup> --check 预览恢复，再按提示确认。

索引与更新

首次使用新增语义与正文检索需完整重建索引。SVN 重建支持协作式取消；它不等于取消远程 update 或 commit。PARTIAL 表示存在扫描错误或覆盖缺口，应按目标对象修复和刷新，不能按空结果处理。

Nexus“运行模式 → 检查更新”统一检查后端、Nexus VSIX 与 Chrome Bridge，默认每天首次激活后后台检查；角标显示可更新数量。发行和调试模式点击确认后从所选发行源下载并验签，分别更新应用或pyz与依赖清单；开发模式从明确developmentRoot本地源码构建Nexus和Bridge，不访问发行源，后端继续使用工具源码。Nexus 自安装最后执行，安装后可立即重新加载窗口或稍后；Chrome 首次需要加载固定托管目录并配对，之后空闲时自动重载。 更新缓存、中断记录和备份保留在本地数据目录；Python 可选驱动缺失时会提示，不自动修改全局环境。

明确同步入口可使用 source-sync/source-sync-full/workspace-sync/index-rebuild/index-init，旧命令保持同一行为。源码保存、SVN 提交、平台发布和业务运行分别核验。
