一、创建并信任工作区目录

1

新建目录并在 CodeBuddy 中信任 已完成

  1. CodeBuddy 安装完成后，在文件资源管理器新建唯一根目录 D:\Develop\GuthonWork。
  2. 在 CodeBuddy 选择「文件 → 打开文件夹」，打开 D:\Develop\GuthonWork；出现工作区信任提示时确认信任该目录。
  3. 后续把发行版运行文件放在根目录，运行数据保存在根目录下的 var：D:\Develop\GuthonWork\GuthonCodeTool-windows-x64.exe、D:\Develop\GuthonWork\var。

二、在 CodeBuddy 安装并设置 Guthon Nexus

从 最新 Release 下载同版 GuthonCodeTool-windows-x64.exe 与 guthon-nexus-vscode.vsix，放入 D:\Develop\GuthonWork。工具首次配置后在该根目录生成 config 和 var。

3

图形界面安装 VSIX 已完成

  1. 在 CodeBuddy 左侧点击「扩展」图标，点击扩展栏右上角 … → 从 VSIX 安装…。
  2. 选择 D:\Develop\GuthonWork\guthon-nexus-vscode.vsix。安装结束后在 CodeBuddy 扩展列表确认出现 Guthon Nexus，版本为 2.3.1。
  3. 如图标未立即出现，在 CodeBuddy 使用「开发人员: 重新加载窗口」或关闭后重新打开 CodeBuddy。
4

在 Nexus 中初始化数据目录 已完成

  1. 点击 CodeBuddy 左侧 Guthon Nexus 图标。点击「设置工作区」或「初始化/配置」入口。
  2. 数据目录选择 D:\Develop\GuthonWork；运行程序选择 D:\Develop\GuthonWork\GuthonCodeTool-windows-x64.exe。
  3. 确认后观察 CodeBuddy 的「输出」面板，出现 GuthonCodeTool 完成: setup。Nexus 树显示「工作区 已配置」，切换工作区显示 GuthonWork。
  4. CodeBuddy 文件树应有 config\datasource.yaml、products.yaml、projects.yaml、source-tables.yaml、sync.yaml。首次为空模板属正常，不代表业务源已连接。
5

注册真实产品或项目 GME 已配置

  1. 在 Nexus「添加产品或项目」中填写名称；系统自动生成 ID，建议将其改为易读、稳定的 ID。工作区身份为 products.<id> 或 projects.<id>。
  2. 按团队提供的配置选择 DATABASE 或 SVN，并填写真实目标、只读账号或 checkout 信息。没有授权时保留空模板。GME 配置示例见下一节。
  3. 同步只更新目标工作区的 readonly、database 或 context；源码开发进入 Workcopy，SVN 走受控编辑入口。首次同步前核对 Nexus 显示的工作区身份与目标。

三、用 GME 实际 SVN 工作区验证 Nexus

配置示例：GME 已注册为 SVN 产品，原清单含 43 个 checkout 范围。索引输出曾显示 [42/42]，该计数不能单独证明索引事务已完成；以 Nexus 最终状态和工作副本核对结果为准。

G1

创建产品身份 已完成

  1. 在 CodeBuddy 左侧打开 Guthon Nexus，在「项目」旁点击 +，选择「产品」。
  2. 名称输入 GME；产品 ID 会自动生成，建议改为易读且稳定的 ID。本示例使用 1305773397847855104，来源选择 SVN。
  3. 回到 Nexus 树，确认出现 PRD GME 1305773397847855104 · SVN，并核对稳定工作区键 products.1305773397847855104。
G2

设置 SVN 登录 已完成

  1. 展开 GME，点击「设置工作区 SVN 登录」。
  2. 输入团队分配的 SVN 用户名。导入 checkout 配置后，再输入 SVN 密码完成认证；输出面板应显示 usernameConfigured: true。
  3. 输入 SVN 用户名、密码；Nexus 只保存用户名，密码由 SVN 保存。
G3

导入用户提供的 checkout 清单 已完成

  1. 在 GME 下点击「导入/粘贴 SVN checkout 配置」，选择「粘贴一个或多个 SVN 地址/checkout 命令」。
  2. 在打开的 CodeBuddy 编辑器中，从第 2 行开始粘贴完整的 43 条 svn checkout 清单；保留各 URL 和本地子目录。保存并关闭编辑器，再选择「解析 SVN 地址」。解析只写配置，不会执行原始脚本。
  3. 点击「编辑 SVN 地址配置」检查 products.yaml：唯一根 svn.url 指向团队提供的产品 SVN 根地址，下面有 43 个 scope，包括 skill、public、datasources/... 和 systems/...。
  4. 若提示 No executable SVN checkout commands，检查 https://、域名和 checkout 命令是否完整，再粘贴原始清单重新解析。
G4

检出并检查本地索引 待确认最终状态

  1. 在 CodeBuddy 的 GME Nexus 树点击「检出/更新完整 SVN 仓库」，先核对预览中的目标工作区、根地址和范围，再执行。原清单配置了 43 个范围。
  2. 完成 SVN 认证和检出后，在 Nexus 点击「扫描/重建本地 SVN 索引」。CodeBuddy 资源管理器显示 var\workspace\PRD GME\context\checkout-scope.json、index.db；输出面板末项曾显示 [SVN] [42/42]、该项 错误 0。扫描计数不能代替索引完成状态。
  3. 复核时展开 GME Nexus 树和 var\checkout，核对每个实际工作副本的路径、SVN 版本与索引任务汇总。若清单 43 条与索引显示的 42 个对象不一致，以完整汇总和实际目录为准，不按计数猜测缺失项。

四、在 CodeBuddy 安装 guthon-team 治理插件

这里的「插件」是 CodeBuddy Agent Marketplace 插件，和上节的 Nexus VSIX 属于两个界面。在插件市场中安装，无需手工克隆整个治理仓库。

6

一次性配置 Forgejo SSH 已验证

  1. 我在本机的 %USERPROFILE%\.ssh 下新建个人 SSH 密钥，并把公钥登记到自己的 Forgejo 账号。私钥只留在本机。
  2. 在文件资源管理器地址栏输入 %USERPROFILE%\.ssh；用记事本编辑名为 config 的文件，填入下面内容。若有其他 Host 配置，保留原内容；专用别名应放在 Host * 前。IdentityFile 替换为实际私钥路径。
Host guthon-git
  HostName <团队提供的 Forgejo 地址>
  User git
  Port 2222
  IdentityFile C:\Users\<Windows用户名>\.ssh\id_ed25519
  IdentitiesOnly yes

首次由我在 CodeBuddy 终端或 Git Bash 做两项只读验证；无需日常输入命令：

ssh -T guthon-git
git ls-remote git@guthon-git:guthonagentcrew/guthon-team.git HEAD

第一项显示个人密钥已认证，第二项返回 5daadd37ecbc2eba5b85c082f044f87e270708ad HEAD。该哈希是本次读取结果，后续仓库更新会变化。

若电脑还没有 Git：图形向导安装步骤与截图
  1. 访问 Git for Windows 官方页下载安装程序，保存到本机。
  2. 双击安装程序，Windows UAC 确认发布者为 Johannes Schindelin 后继续；安装目录采用默认的 C:\Program Files\Git。
  3. 在「Choosing the default editor」选择 Notepad；PATH 选 Git from the command line and also from 3rd-party software，使 CodeBuddy 能找到 Git。
  4. HTTPS 后端保留 Windows Schannel；行尾选 Checkout as-is, commit Unix-style line endings；终端保留 MinTTY，pull 保留 Merge。Credential Helper 按实际认证方式选择。其余页面保持默认并完成安装。
  5. 重启 CodeBuddy 后在 CodeBuddy 内置终端或 Git Bash 运行 git --version。输出显示 git version 2.55.0.windows.5。

CodeBuddy 图形市场输入框需要 git@别名:组织/仓库.git 形式；Forgejo 使用 2222 端口，因此依赖上述个人 SSH 别名。

7

通过 CodeBuddy 市场添加团队插件源 已完成

  1. 在 CodeBuddy 右侧 CodeBuddy 面板点击齿轮，选「插件 → 插件市场」。编辑区打开 CodeBuddy Market 标签。
  2. 点击市场页插件源列表旁的 +，在「添加插件源」输入 git@guthon-git:guthonagentcrew/guthon-team.git，核对字符和来源后提交。
  3. 新增 guthon-team 源后，选择该源，找到 guthon-guard，在 CodeBuddy 中安装。选择「安装（用户）」；再确认「我安装的」显示 guthon-guard，插件详情显示「已安装」及命令、技能、Hooks。
  4. 在 CodeBuddy「查看 → 命令面板」搜索 Reload Window，选择「开发人员: 重新加载窗口」。如果出现「已暂时禁用所有已安装的扩展」提示，点击「重新加载并启用扩展」。重载后再次查看 CodeBuddy「插件」页，确认 guthon-guard 仍在列表中。安装/启用与 Hook 实际执行是不同验收项。
8

在真实业务工作区分两阶段初始化治理 Git Hook 已安装

  1. GME 已在 Nexus 注册为 products.1305773397847855104，我已检出源码；索引最终状态仍需确认。先通过 Nexus 树核对目标业务工作区身份与源码路径；治理目标为包含 nexus/tool-runtime.json 或 workspace/*/context/source-mode.json 的 D:\Develop\GuthonWork\var，不是数据根 GuthonWork，也不是单个 SVN checkout。
  2. 在 CodeBuddy 插件页确认 guthon-guard 已启用。以目标 var 打开工作区，在 CodeBuddy 对话中选择 /guthon-team:guthon-guard:guthon-init，输入 status。现场检查结果为 STATUS state=not-installed：var 不是 Git 仓库，gitHook=skipped；计划安装 13 项规范、8 项 Guard 文件，未发现冲突。status 是只读检查，没有写入文件。
  3. 我先按非 Git 路径完成初始化，再建立本地 Git 仓库并补装 Git Hook。完成后在 var 根检查 AGENTS.md、.guthon/config.json、tools/guthon-lint.cmd 与规范文件。随后在 CodeBuddy 使用 /guthon-check 对实际 GME 文件执行 Linter，并在新任务中单独观察 Lifecycle Hook 触发结果；只有各项都有现场输出时才标记验收完成。

第一阶段：非 Git 初始化 已完成

  1. 保持 D:\Develop\GuthonWork\var 现有 SVN 与 Nexus 目录原状。在 CodeBuddy 对话中选择 /guthon-team:guthon-guard:guthon-init，输入 init --no-git-hook；先核对计划和冲突，若有本地冲突，停止并保留原文件，不直接使用 --force。
  2. 我在 CodeBuddy 执行后得到 INSTALLED workspace=D:\Develop\GuthonWork\var standards=2026.09.24.2 gitHook=skipped、exit=0，且无冲突、无备份。重新运行 status --no-git-hook，核对本地规范、AGENTS.md、.guthon 和 Linter 启动器。此模式不会创建 .git，不会安装 Git pre-commit；建议随后将 var 目录初始化为本地 Git 仓库，再安装 Git Hook。Linter 可做直接文件检查，但 --changed、--staged 依赖 Git 根。

第二阶段：在同一 var 目录建本地 Git 仓库并补装 Hook 已完成

  1. 第一阶段完成后，把同一个治理目标 var 建成独立的本机 Git 仓库。先在 CodeBuddy 的“源代码管理”中核对当前工作区为 D:\Develop\GuthonWork\var，在命令面板选择“Git: 初始化仓库”，再选 var (D:\Develop\GuthonWork\var)，创建本地 .git。现场检查源代码管理显示 var · main* 与 24 个未暂存文件；未连接远端、未暂存、未提交。不要在 GuthonWork 数据根或单个 SVN checkout 内另建一个仓库来代替 var。
  2. 我已在初始化 Git 前创建 var\.gitignore，内容为 checkout/、workspace/、nexus/ 三行，用于排除 SVN 源码、业务工作区、索引和运行数据；在 CodeBuddy 源代码管理中检查待跟踪列表，确认仅包含拟版本化的治理文件。不要将凭据、业务源码或索引库加入暂存区。
  3. 再次在 CodeBuddy 对话中选择 /guthon-team:guthon-guard:guthon-init 并输入 status，不要沿用第一阶段的 --no-git-hook。我用 git rev-parse --show-toplevel 核实 Git 根正是 var，原有 core.hooksPath 为空；插件返回 PLAN standards=0 guard=1 gitHook=enabled、STATUS state=update-available，仅计划新增 .githooks/pre-commit，无冲突。随后在 CodeBuddy 执行 init，不加 --force 或 --no-git-hook。输出显示 INSTALLED workspace=D:\Develop\GuthonWork\var standards=2026.09.24.2 gitHook=enabled、exit=0。若已有其他 Hook 路径，先人工整合，不直接覆盖。
  4. 在 CodeBuddy 源代码管理中核对 .githooks/pre-commit，并只读复查本地 core.hooksPath=.githooks 和插件 STATUS state=ready。本次没有暂存或提交，因此只证明 Hook 文件与 Git 配置就绪，没有证明提交时 Hook 实际触发。后续可由仓库负责人在可恢复的临时测试文件上验证 pre-commit。Git Hook 只检查该本地仓库已暂存的 Git 文件；被忽略的 GME SVN 工作副本不会自动受其保护，仍需 Linter、受控 SVN 流程及 Lifecycle Hook 的独立验证。

第三项验证：在 GME SVN 文件上只读检查 已完成

  1. 在 CodeBuddy 资源管理器展开 var\checkout\1305773397847855104\systems\SYS-A7EE-D0E8-BE614B80\system-script，打开实际文件 20.js，核对编辑器面包屑和文件名。
  2. 在 CodeBuddy 对话输入 /，从图形菜单选择 guthon-team:guthon-guard:guthon-check，传入工作区相对路径 checkout/1305773397847855104/systems/SYS-A7EE-D0E8-BE614B80/system-script/20.js。输入后先核对文件名中的句点；路径必须指向实际 20.js 文件。
  3. CodeBuddy 在 D:\Develop\GuthonWork\var 下调用治理 Linter，文件路径作为单独参数传入，未使用 --write-target。实测退出状态 0，输出 guthon-lint: PASS，该文件无报错、无警告。此结果只代表该文件的本地内容检查；不代表 Git pre-commit、CodeBuddy Lifecycle Hook、SVN 发布或业务平台验证。

图形画面显示插件已安装、GME 索引曾有扫描输出，且实际 SVN 文件的只读 Linter 检查通过；Git pre-commit 与 CodeBuddy Lifecycle Hook 的实际触发仍需独立验证。GuthonWork 是工具数据根，不用它代替业务目录的治理验收。

五、日常使用

打开工作区在 CodeBuddy 打开已授权的业务目录；先看 Nexus 树上的工作区身份和配置状态。
同步与编辑在 Nexus 中对选定产品/项目执行同步。DATABASE 开发用 Workcopy；SVN 源码走受控入口。
刷新与检查工作区列表刷新、本地 SVN 变更刷新、远端 SVN 变更检查各有入口，按需选择。
团队治理新任务先确认 guthon-guard 与当前工作区状态，受保护写入前看治理提示；不要用安装成功代替 Hook 验证。

更新方法

  1. 新版本从同一 Release 下载 EXE 与 VSIX，在固定目录替换 EXE，CodeBuddy 扩展栏重新「从 VSIX 安装」，然后重载 CodeBuddy；保留 GuthonWork 数据目录。
  2. 在 CodeBuddy Market 刷新 guthon-team 市场并更新 guthon-guard；重载插件后在真实业务工作区复核状态和 Hook。

七、安装与使用中的卡点

Git Hook 显示 skipped

非 Git 初始化使用 init --no-git-hook 时，gitHook=skipped 属于预期。按第四章建议将 var 初始化为本地 Git 仓库，再执行 status 和 init，检查 Hook 文件及 core.hooksPath。

插件可见但治理未生效

依次检查插件安装与启用状态、当前工作区是否为已初始化的 var、治理状态以及新任务中的 Hook 输出。

SVN 认证失败

核对 Nexus 中的工作区身份、SVN 根地址和用户名，按提示输入密码并重试。不要把密码写入 products.yaml、HTML 或截图。

配置范围与索引扫描数量不同

清单配置 43 个 SVN 范围，扫描输出曾显示 [42/42]。该数字表示本次扫描对象数；继续核对完整任务结果、实际工作副本和 Nexus 索引状态。

SVN checkout 根目录不是单一工作副本

配置包含多个 checkout 范围，var\checkout 顶层不一定有 .svn。查询状态和提交前，在 Nexus 中选定准确的产品与工作副本。

SVN 提交与 Git Hook

SVN 提交不会触发 var 本地 Git 仓库的 pre-commit。两类检查分别按实际操作结果验收。
